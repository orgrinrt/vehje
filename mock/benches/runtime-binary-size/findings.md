# Composed-runtime binary size (expansion): the embeddability size claim

**Date:** 2026-07-21 | Zig 0.16.0, ReleaseSmall + strip | data `size.csv`
**Settles:** the "small embeddable runtime" identity claim, on the specialization-overhead axis.

## Result (engine object code size vs family count, trivial-identical families)
| families | object bytes |
|---|---|
| 4 | 968 |
| 16 | 976 |
| 40 | 1008 |
| 100 | 1072 |
| 250 | 1232 |

## Reading
The specialized engine's code is ~1 KB plus ~1 byte per family for the generated dispatch skeleton. The
`FamilyTag` enum generated by certified generation is a COMPTIME type (zero runtime code), and the total dispatch
structure is tiny. So the certified-generation SPECIALIZATION MACHINERY adds negligible size: 968 -> 1232 bytes
from 4 to 250 families is the dispatch skeleton, not real code.

This is the load-bearing point for embeddability: certified generation does NOT bloat the runtime. The composed
runtime's size is (fixed hand-authored engine: parser, lease, lowering, interp, transport) + (each family's
actual semantics code) + (the ~1 KB dispatch skeleton). The generated/specialized part is negligible; the size is
dominated by the bounded hand-authored engine and the families' own semantics.

## Scope (honest)
This measures the trivial-identical-family case, so the family dispatch collapses (the compiler dedups identical
arms). Real families add their distinct semantics code, so a real composed runtime grows with the families'
actual op implementations, not with the ~1 byte/family skeleton here. But the SPECIALIZATION overhead (the
generated dispatch structure) is confirmed negligible, which is what the embeddability claim needs: the
runtime is small because the generation machinery is free and the engine is fixed and bounded.

## Design impact
Certified generation adds negligible runtime size (~1 KB skeleton + real family semantics). The composed runtime
stays small and embeddable; the specialization does not bloat it. Embeddability holds on the size axis.
