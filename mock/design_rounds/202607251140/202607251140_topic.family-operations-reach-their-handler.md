# Topic: a family operation reaches its handler

**Date:** 2026-07-25
**Phase:** TOPIC
**Scope:** the runtime half of the handler discipline. A `Raw` node evaluates its payload and dispatches to a host-provided handler, which is how arithmetic, comparison, and every host service reach a running program. The framework gains the dispatch; it gains no family.

The runtime evaluates lambdas, application, recursion, conditionals, and literals, and a produced value crosses back to the host. What a program still cannot do is add two numbers. That is not an oversight in the Core: the Core has no `+`, because arithmetic is not an evaluation form, it is a family operation, and the framework owns no family. Every real computation a consumer language performs arrives through `Raw`, and `Raw` currently evaluates to a refusal.

The canon names the mechanism already. An effect is an operation, a handler is what services it, and a host-call is a runtime-effect operation the host handles; the build-versus-runtime split is which stage provides the handler. So the runtime's job is not to know what a family means. Its job is to evaluate the operation's operands and hand them to whoever declared the family, then take the result back as a value. That keeps the framework family-free while making every family executable, which is the whole point of the discipline.

A family node names its family with a sixteen-bit id and carries a payload list. The operation *within* a family is not in the framework's vocabulary at all: a consumer that wants twenty arithmetic operations encodes which one in its own payload, and the framework neither knows nor cares. That is a feature of the seam rather than a gap in it, and it means the dispatch contract stays small: given a family id and the evaluated operands, produce a value or a failure.

The one genuinely open question is what an operand looks like crossing the boundary. A produced value crosses back as a value image, which is the right shape for a whole result: self-contained, position-independent, arbitrarily structured. It is the wrong shape for an operand of an addition, where building and parsing an image per call would cost more than the call. The runtime's value set today is unit, boolean, and integer, all of which fit in a small fixed record. So the operand form is a compact scalar record now, with compound operands named as the extension point they are rather than pretended into existence.

## Current state

`mock/runtime-zig/src/runtime.zig` evaluates `Lit`, `Var`, `Let` including the recursive form, `If`, `Lambda`, and `Apply`, and refuses everything else with `Unsupported`, `Raw` among them. `vehje_runtime_execute` takes the residual bytes and an optional sink, and has no way to reach the host for anything.

`vehje-ir` models a family node as `Raw { family: FamilyId, payload: NodeList }`, where `FamilyId` wraps a sixteen-bit id and `Family` is a marker trait. The wire encoder writes the family id as one word followed by the payload list's start and length, so the residual already carries everything the runtime needs to find the operands.

`vehje-runtime-driver` drives the runtime through `RuntimeEntries` and supplies a transfer sink. It has no host-call surface.

## Changes proposed

Give the runtime a host it can call. `vehje_runtime_execute` takes a host pointer alongside the sink: a pair of one dispatch callback and an opaque userdata, mirroring the sink's shape because the same reasoning applies (the host owns the context, the runtime retains nothing past the call). A null host means the program is expected to need none, and a `Raw` node under a null host is a named refusal rather than a crash.

Define the operand record: a small `#[repr(C)]` pair of a kind tag and a payload word, covering unit, boolean, and integer, which is exactly the runtime's value set. The tag values are the value image's scalar tags, so one vocabulary describes a scalar wherever it appears rather than two that must be kept in agreement. A compound operand has no representation here, and that is stated rather than left to be discovered: when sequences and records become values, they arrive through the value image and the operand form gains an explicit escape.

Evaluate `Raw` by evaluating each payload child in order, collecting the results into a fixed-capacity operand buffer, and calling the host with the family id and that buffer. Left-to-right, because a host call may have effects and the order in which operands are produced is part of what a program means. Over the buffer's capacity is a named refusal, in keeping with every other bound in the runtime being lent rather than assumed.

The host returns a result code and writes one operand-shaped value back. A non-zero code is a named runtime failure that propagates as an evaluation error, so a host that refuses is distinguishable from a host that produced a value.

Add the matching Rust side to the driver: the host record, the callback type, and a `Runtime::execute_with_host` that passes one through. The existing `execute` keeps working with no host, since a program that needs none should not have to supply one.

## Not in this round

Any actual family. Arithmetic belongs to the first-party language consumer, which is the round after this one, and to every other consumer on its own terms. Compound operands, which wait on compound values existing at all. The compile-side counterpart, where a compile-stage handler services a macro operation at its binding time, which is the same discipline aimed at the other stage and deserves its own round rather than being half-built here. Comptime specialisation of known families into the generated runtime, which is an optimisation of this seam rather than a different one.
