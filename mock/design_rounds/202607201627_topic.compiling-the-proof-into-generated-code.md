# Topic: the typestate proof is compiled into the generated runtime, not re-run and not re-embedded

**Date:** 2026-07-20
**Phase:** TOPIC
**Round:** runtime output + lease proof. Follows the debt-reckoning topic
`202607201534_topic.paradigm-validation-debts.md`, which named the load-bearing debt this topic pays: whether
moving the per-script check into the shipped runtime loses the proof fidelity that rustc's typestate gives, and
whether it is redundant to replicate what rustc already holds statically.
**Scope:** where the proof lives, and how the shipped runtime keeps its guarantee without carrying rustc or a
typestate. This topic records the resolution and the two dead ends we ruled out reaching it, because the order
in which the clarity emerged is itself part of the design.

## The question, and why it was hard

The validation audit and the debt-reckoning topic left one question genuinely open. rustc's typestate proves a
program's structural discipline (family inclusion, effect inclusion, lease-schema membership, non-null) at
compile time, by construction: an ill-formed program does not type-check and cannot be built. A typestate is a
compile-time-only artifact; it is erased before any runtime exists. So when a script has to be lowered and run
by the shipped Zig runtime, the natural question is whether we lose that guarantee, and whether re-establishing
it in the runtime merely duplicates what rustc already did.

The conversation ran hard into two poles, and both are wrong, which is why the resolution took work to see.

## The two dead ends

The first dead end is a hand-written runtime check: the shipped runtime computes a script's family and effect
sets and tests inclusion dynamically. This is rejected not because a runtime check is slow but because it
rebuilds rustc's soundness ourselves, unverified. The guarantee stops being "rustc proved this" and becomes "we
wrote a checker and believe it is correct." The provenance of the proof is lost even when the check happens to
be right, and we are on our own for its soundness. That is the wrong trade for a project whose identity is the
strength of its static guarantees.

The second dead end is compiling each program through rustc at the point of use: give every program its full
typestate proof by running rustc on it per program. This gives the strong guarantee, but it requires rustc, and
behind it llvm, to be present wherever a program is lowered. For a framework whose one differentiating identity
is embeddability, a no_std/no_alloc compiler at dev time and a minimal Zig runtime at the embed site, shipping
the full Rust toolchain to every consumer is worse than the thing it was trying to avoid. It is not tenable.

Bouncing between these two is what obscured the answer. One loses the guarantee to keep embeddability; the other
keeps the guarantee by destroying embeddability. The resolution keeps both, and it does so by refusing the
premise that the proof has to be either re-run or re-shipped.

## The resolution: compile the proof away into certified generated code

rustc already does exactly the thing we need, every time it compiles. It type-checks source, proves it
well-typed, and emits machine code that carries no types and performs no type checks, yet is correct, because it
was generated from source that could not express the illegal thing. The types are erased; the correctness is
baked into the structure of the output. That is a proof compiled away: same guarantee, differently expressed, no
prover present at run time.

The resolution is that pattern lifted one level. The typestate proves the language composition sound at
language-compile time. The proof is then compiled into the structure of the generated Zig, differently expressed,
carried without a typestate and without rustc. The shipped runtime does not re-run the proof and does not
contain the prover; it contains generated code whose structure is the proof's consequence.

What makes this the strong path rather than the first dead end is that the generated enforcement is certified,
and certified twice, both at our build time and never at the consumer:

The generator is typed by rustc. The generator that emits the Zig is written against the typestate, so the
typestate constrains what it can emit; a well-typed generator run can only produce correct enforcement. This is
the typed-staged-metaprogramming technique, with real prior art in Lightweight Modular Staging, typed Template
Haskell, and Terra, where the generator's own type system guarantees the generated code's correctness, so
proving the generator once proves its output. rustc typing the generator at language-compile time is the first
certification.

The generated Zig is typed by the Zig compiler. We compile the emitted Zig into the shipped binary at our build
time, so Zig's own type system and comptime catch malformed generated code before anything ships. That is the
second certification, and it also happens at dev time.

The consumer receives a pre-compiled, doubly-certified binary. It carries neither rustc nor llvm nor a
typestate. The guarantee holds because the thing that produced the binary was proven correct, exactly as a
compiled Rust binary is trusted because rustc proved its source, not because the binary re-checks anything.

## The mechanism, in its simplest expression

The cleanest form is to make illegal states unrepresentable in the generated IR. The generated Zig IR node type
for a language contains exactly that language's family node shapes and no others, so a node from an unsupported
family is not a value the generated types can hold. The generated dispatch is a total match over those shapes,
and rustc proves that match exhaustive from the `Supports` set's `ContainsAll` at generation time. The generated
lowering can only construct representable nodes. A script that uses something outside the supported set therefore
cannot be lowered into a well-formed IR at all; it fails to lower.

Stated as an equivalence: the `ContainsAll` typestate becomes, in the generated Zig, a total dispatch over an IR
type in which the illegal family is unrepresentable. Same implication, different expression, and the equivalence
is what the two certifications check at our build time. Effect inclusion and non-null encode the same way, as
unrepresentable illegal shapes plus total handling. Leases are the hard case and are discussed under the honest
limits, because region validity is a richer property than "which shapes exist" and strains the
make-illegal-unrepresentable technique.

## The honest limit, which is not a wall

For a script that arrives at run time, an invalid one is still detected at load, because an input unknowable
until it arrives has no earlier moment to be checked. But the detection is now a by-construction rejection: the
generated lowering has nowhere to put the illegal construct, so the script fails to lower. It is not a
hand-written dynamic inclusion test, and it is not unverified. So the guarantee is neither lost nor re-proven at
run time; the only run-time event is a sound, structural rejection of genuinely-unknowable-until-load input,
which is unavoidable and correct. The objection the first dead end raised, that we would rebuild rustc's
soundness ourselves, is exactly what the certified generator removes: the rejection logic is generated from the
proof and certified, not rebuilt by hand.

## What this resolves against the debts

Debt 1's fidelity question is answered: there is no fidelity loss, because the proof is compiled away into
certified structure rather than re-run, the same way a compiler compiles types away into correct code. The
redundancy question is answered: there is none, because rustc proves the language and the generator once at dev
time, and the generated Zig enforces on scripts at the consumer; these are disjoint acts over a single source of
truth, the generator, not two hand-maintained copies of one check. And embeddability is preserved, because only
the certified Zig binary ships and the Rust toolchain is off the table at the consumer.

The two paths from the debt-reckoning topic restate cleanly under this resolution and stop being two mechanisms.
For dev-time-known terms, the certified generated lowering produces valid IR by construction, yielding a proven
residual the runtime executes with no check. For runtime-arriving scripts, the same certified generated lowering
rejects invalid input at load by construction and runs valid input. Both use the one certified generated Zig;
the only difference is when the input becomes known, and neither carries rustc at the consumer.

## What is genuinely open, and hard (for the experts)

The technique has a difficulty gradient that must be stated honestly rather than waved past. Family inclusion,
effect inclusion, and non-null encode cleanly as unrepresentable-illegal shapes plus total dispatch. Leases,
being region validity rather than shape membership, are a richer property that the make-illegal-unrepresentable
encoding does not obviously carry; this is the residue of debts 2 and 3, and it is the place the resolution is
least proven.

The certification's exact division also needs the smallest concrete instance built rather than argued: how much
of the guarantee is carried by rustc typing the generator, how much by the Zig compiler typing the generated
output, and how much by the structural encoding itself. And it is an open question whether the certified-generation
technique reaches only the structural discipline (with family semantics authored and tested like any runtime's
interpreter) or can be pushed further into the semantics.

The experiment that settles the core claim is small: generate, for one family, its Zig IR type with the illegal
family unrepresentable and its total dispatch, and confirm the two certifications actually hold on it, rather
than trusting the argument. That instance is the next move once this topic is audited.

## Proposals for the expert panel to audit (the Zig-end enhancements)

Beyond the general resolution above, a set of specific enhancements to the Zig-end proof are proposed here for
the panel to audit. They are proposals, not settled decisions; the panel should judge whether each holds, where
it fails, and what is missed.

The reframe, which is the load-bearing proposal: Zig's `comptime` is the specialiser and the certifier, not a
Rust metaprogram emitting Zig source. Rust emits validated data (the family table, effect masks, lease-rule
schema, wire layout) as Zig `comptime` consts. The general engine is a `comptime`-parametrised Zig metaprogram
that specialises to that data and generates the IR type, the dispatch, and the checkers. The Zig compiler,
compiling the specialised engine at our build time, certifies it. This sidesteps proving that a Rust generator
emits correct Zig source (the typed-staged-metaprogramming / LMS-hard path) in favour of Zig's own compile-time
type-and-code generation, which Zig is built for. rustc proves the data sound; the Zig compiler proves the
specialisation sound; both at our build time, neither at the consumer. This also leans the Rust side toward
emitting proven-consistent data rather than logic, which is the all-data direction.

The specific mechanisms, each proposed to carry part of a guarantee:

- Exhaustive `switch` over a tagged union: totality over the declared family set is compile-checked, since a
  missing case is a Zig compile error. This realises the renderer-total-over-its-declared-families obligation
  without a runtime check.
- A comptime-generated tag enum holding exactly the language's families: an illegal family is not a
  representable value (illegal-states-unrepresentable), caught by the same compile-time machinery.
- Comptime folding of the inclusion check, which unifies the two paths into one expression. The check is
  `script_mask & ~target_mask == 0`, with `target_mask` a comptime const. For a dev-time-known program
  `script_mask` is also comptime, so Zig folds the entire check and a violation becomes a `@compileError`: the
  full static guarantee at zero runtime cost. For a runtime script only `target_mask` is comptime, leaving a
  single runtime bitwise op. One source, stratified by the compiler, not two code paths to keep consistent.
- Zig optionals `?T`: non-null-by-construction is carried by Zig's own type system, which forces the null case
  to be handled, and the Maybe-node discipline maps directly onto it.
- Error unions `!T` with declared error sets, exhaustively handled: the by-construction rejection paths are
  type-checked, so a rejection branch cannot be silently forgotten.
- Allocator-free signatures: no_alloc is visible and checked in the signatures, since a function taking no
  allocator cannot heap-allocate, and a region is an explicit arena (a fixed-buffer or bump allocator) whose
  exit is a reset.
- Distinct generated ref types per region kind: a cross-region access becomes a Zig type error
  (illegal-cross-region-access-unrepresentable). This is the single lease-specific enhancement and the one least
  certain to carry its weight, because Zig has no lifetime types; the panel should probe exactly how far it
  reaches.
- `comptime { if (!ok) @compileError(...) }`: structural invariants beyond the type system (the dispatch covers
  the family set, the arena layout matches the wire schema, the masks are internally consistent) are checked at
  our build time.
- `extern`/`packed struct`: the value-arena and the IR wire records get a compiler-checked guaranteed layout.
- Co-emitted Zig `test` blocks for the authored-and-tested family semantics, run at our build time, so even the
  parts that are tested rather than proven get their tests generated with them.
- Zig's built-in safety checks plus explicit traversal and depth limits for the untrusted, runtime-arriving
  path, rather than a hand-rolled bounds checker.

The honest caveat the panel must weigh: family, effect, and non-null get strong Zig-end certification from these
mechanisms; leases stay the hard axis, because Zig has no lifetime types, so full region validity is not
statically Zig-provable and leans on the Rust-side schema proof plus the generated arena structure plus the
distinct-ref-types trick (partial) plus a residual runtime region-tag check. Whether that composition is sound,
and whether the distinct-ref-types trick carries more or less than hoped, is a primary question for the panel.
