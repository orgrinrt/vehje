# Doc changelist: the LanguageAuthor specialisation stage

**Date:** 2026-07-26
**Round:** `202607260500_topic.the-languageauthor-specialisation-stage.md`
**Task:** #52

Scope is the mechanism that carries two independent expert agreements, each
grounded in quoted canon: a closed primitive vocabulary emitted as data and
specialised at Zig comptime fits the canon, `Raw` remains the vehicle, and no new
Core form is added. The three items the two reads disagreed on are the lead
designer's and are deliberately out of scope here; nothing in this changelist
depends on how they resolve.

Feasibility is not assumed. `mock/research/sketches/202607260800_four-way-projection/`
drove one operation definition through all four discharge sites of the
binding-time lattice and found them byte-identical, with the Zig comptime arm
verified by disassembly to compile to three arithmetic instructions across an
`export` boundary.

## `mock/crates/vehje-signature/DESIGN.md.tmpl`

**Add**, to the `Operation` section: an operation carries its semantics as a
program over a closed primitive vocabulary, alongside the `FamilyId`,
`EffectMask`, and `LeaseRule` it carries today. State the property the encoding
must satisfy, since that is what makes it admissible rather than merely present:
it is evaluable by rustc-compiled Rust and by Zig, at compile time and at run
time, because the binding-time lattice has discharge sites on both sides
(`vehje-lower`'s Bundler const-fold and HostLoader lowering, and the runtime's
own evaluation). An encoding evaluable at only one site forces the meaning to be
authored twice, which is the failure the single-signature principle exists to
prevent.

**Add** that the vocabulary is closed by design, and why: the data never encodes
arbitrary computation, only a program over a fixed operation set, which is what
keeps the general engine free of any family while letting the specialised artifact
compute.

**Do not state** which vocabulary. Coverage is a separate question from
admissibility and is not settled by this round.

## `mock/crates/vehje-runtime-gen/DESIGN.md.tmpl`

**Change** the `generate` description from composing caller-supplied slices to
compiling the signature: it reads the `Signature`'s operation catalogue and emits
the family table and the operation programs into the validated-data package. The
current text describes what the function does today rather than what it is for,
and the source carries the gap explicitly as an unread `_signature` parameter.

**Add** a State label naming what is shipped versus intended, per the assurance
verb discipline, so the doc does not read as finished while the emitter half is
in flight.

**Keep** the manifest and differential-check text unchanged; neither is in scope.

## `mock/runtime-zig/DESIGN.md.tmpl`

**Change** the family-operation section. Today it describes every `Raw` node
dispatching to a host-provided handler, with `NoHost` when none is supplied. That
describes the pre-specialisation engine and is what the standing call corrects:
the shipped runtime is the engine after specialisation, and it computes its
language's operations itself.

State the split precisely, because conflating the two crossings is what produced
the drift. A family operation whose semantics the language definition supplies is
evaluated by the specialised runtime with no host involvement. The host boundary
remains, and remains a runtime C ABI call, for genuine runtime-effect operations
that the host actually handles, which is what `extern` declarations in a consumer
language name. `NoHost` therefore stops being the answer to arithmetic and stays
the answer to an unhandled host effect.

**Add** the binding-time framing: the specialisation happens at LanguageAuthor
grade, at our build, and is the first Futamura projection as a build step, which
is the canon's own description of where ahead-of-time work lives.

## `mock/crates/vehje-ir/DESIGN.md.tmpl`

**Change** the `Raw` payload text. Source currently marks it incomplete ("the
payload is a family-interpreted handle; M0 carries only the family id and a
node-list placeholder until the first family defines its payload encoding"). The
first family is now defining it, so the doc states that the payload names the
operation within its family plus the operand nodes.

**Do not add** a Core form. Both reads agreed independently that `Raw` remains
the vehicle and that the distinction between `Raw` and `Perform` is unchanged by
runtime-owned computation: an operation the specialised runtime computes acquires
no effect, which is the property that shaped `Perform` in the first place.

## Out of scope, stated so a reader does not infer it

The three open items: whether nominal binding to hand-authored code is foreclosed
as the home of semantics or merely costly, whether the declarative encoding is a
coequal default or must earn its place, and whether the vocabulary is
framework-level or consumer-opt-in. Also out of scope: the specific vocabulary,
the cost comparison between specialised and interpreted arms (a harness cell, not
a doc change), and the emitter trust seam, which this round narrows but does not
close.

# Addendum: the per-script locus, ruled

The three items this changelist deferred as the lead designer's are resolved.
op ruled on 2026-07-26, reading the canon directly: the Rust per-script compile
pipeline is forbidden, Bellard's read is correct, and the roughly 3,700 lines
implementing it come out.

The ruling needs no canon amendment, and that was checked rather than assumed.
`positive:45` already reads "a dev-time Rust language compiler (emits validated
data and structural proofs, **never sees an end-user script, never ships**)" and
`negative:38` already kills the dual locus by name: "Rust never runs per-script
analyses, the runtime does, for all scripts." The second expert's counter-reading
rested on two errors, both verified: `positive:27`'s reference to
`vehje-typecheck/src/lib.rs` is a **status report** supporting the sentence "the
spine is **intended**, not proven", not a locus mandate; and its cited "canon
§11" does not exist, the positive catalogue having eight sections. So the canon
is explicit as written and the code is what moves.

`positive:45` settles the front-end locus in the same sentence. The three named
per-script operations are "macro expansion (IR to IR, per script, compile stage)"
and "output generation (IR to output, per script)". Both are IR-to-something.
Parsing a script is neither, and Rust never sees a script, so no parser lives in
Rust.
