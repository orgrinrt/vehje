# Current state

`clause-schedule` is currently a nuked stub. `src/lib.rs` is
three lines plus a comment; there are no public items. The crate
fires mockspace's `no-empty-crate` lint at warn (the last remaining
lint warning across the whole clause workspace).

The shipped `DESIGN.md.tmpl` predates the substrate principle. It
describes `PassDag`, `PassRegistry`, `Scheduler`, `Artifact`
types as if `clause-schedule` were to build its own pass
framework. That framing is wrong under the substrate principle.
Clause does not build its own scheduler. Hilavitkutin is the
scheduler. `clause-schedule` is the home for clause-specific
`WorkUnit` declarations that apply hilavitkutin's shipped
contract.

The SUB-H0 audit (#132, closed 2026-04-21) confirmed
hilavitkutin-api's `WorkUnit<Schedule = Always>` trait,
`Column<T>` / `Resource<T>` / `Virtual<T>` descriptors,
`AccessSet` mechanics, and `DiagnosticSink` cover every
clause compile-pipeline need. No hilavitkutin extension is
required to open `clause-schedule`.

The pipeline the crate hosts (for this skeleton round):

- `LexWU` — source bytes → tokens.
- `ParseWU` — tokens → AST.
- `ResolveWU` — AST → `Resolved` bundle.
- `TypecheckWU` — `Resolved` → typed program.
- `CodegenWU` — typed program → emission artifacts.

`TranspileWU` is deliberately out of scope here — it lands in
M3.3 (#150) where control-flow + closure transpilation design
gets settled. `MacroExpansionWU`, analyzer WUs (#164), and the
interpreter WU (#173) all wait for their parent milestones.

Incremental recompute uses hilavitkutin's shipped
`DirtyMask<MAX_STORES>` mechanism. Clause-schedule does not need
to extend that — the engine consults it automatically and skips
WUs whose read columns are clean.

## Module layout

Replaces the 3-line nuked stub with five modules:

- `columns.rs` — ZST column-value types that stand in for the
  per-phase artifact types until the phases populate real ones.
  `SourceFile`, `TokenStream`, `AstArena`, `ResolvedBundle`,
  `TypedProgram`. Each is a marker ZST implementing
  `ColumnValue` (from hilavitkutin-api). Bodies are empty in
  this round; follow-up rounds wire them to the phase-specific
  types.
- `access.rs` — AccessSet tuple aliases: `LexRead`, `LexWrite`,
  `ParseRead`, `ParseWrite`, etc. Each is a plain `type` alias
  over the column / resource descriptors.
- `wus.rs` — Five ZST WU structs (`LexWU`, `ParseWU`,
  `ResolveWU`, `TypecheckWU`, `CodegenWU`) each with
  `impl WorkUnit<Always>` declaring the associated types.
  `execute` bodies are empty pending phase-specific wiring.
- `pipeline.rs` — `const CLAUSE_PIPELINE` tuple listing the five
  WU types in DAG order. Consumed by the hilavitkutin scheduler
  builder once composition plumbing lands upstream.
- `lib.rs` — module decls + pub re-exports. Drops the nuked
  comment. `#![no_std]` posture — the crate compiles under
  no_std because hilavitkutin-api is `no_std`, and clause-schedule
  declares only type aliases plus empty `execute` bodies.

Follow-up rounds add `TranspileWU` (M3.3), analyzer WUs (M5.4),
the interpreter WU (M7.1), and the macro-expansion WU (M4).

## Column-value types

The five ZSTs mirror the phase artifacts. For this skeleton
round they are opaque markers. Each implements
`hilavitkutin_api::ColumnValue` (`Copy + 'static`). Real content
arrives when each phase's follow-up round populates the type
(`TokenStream` becomes a `clause-lex` type, `AstArena` becomes a
`clause-syntax` type, and so on).

Skeleton bodies:

```rust

#[derive(Copy, Clone, Default, Debug)]

// ... one per phase
```

Naming: singular noun for the per-record shape
(`TokenStream` is one token stream per file record, not the

## AccessSet tuple aliases

Each WU declares read/write sets as tuple aliases over the shipped
descriptor types:

```rust
pub type LexRead = (Resource<StringInterner>, Column<SourceFile>);
pub type LexWrite = Column<TokenStream>;

pub type ParseRead = Column<TokenStream>;
pub type ParseWrite = Column<AstArena>;

pub type ResolveRead = Column<AstArena>;
pub type ResolveWrite = Column<ResolvedBundle>;

pub type TypecheckRead = Column<ResolvedBundle>;
pub type TypecheckWrite = Column<TypedProgram>;

pub type CodegenRead = Column<TypedProgram>;
pub type CodegenWrite = Column<CodegenArtifact>;
```

`StringInterner` ships in hilavitkutin-str. `CodegenArtifact`
ships in clause-codegen. The rest are the column-value ZSTs
declared above.

A shared diagnostic sink threads through every WU as a resource
read: `Resource<&'static dyn DiagnosticSink<Diagnostic>>`. This
round may simplify by making it a `Resource<ClauseDiagSink>`
where `ClauseDiagSink` is a ZST marker the scheduler binds to a
concrete sink at wire time. The exact shape resolves in a
follow-up round (#168 structured diagnostic registry); for this
skeleton, every WU's `Read` includes a `Resource<DiagSinkMarker>`
placeholder.

## WU structs

Five ZSTs:

```rust
#[derive(Copy, Clone, Default, Debug)]
pub struct LexWU;

impl WorkUnit<Always> for LexWU {
    type Read = LexRead;
    type Write = LexWrite;
    type Hint = (Immediate, Normal, Important);
    type Ctx = /* auto-satisfied by monomorphisation; leave
                 as a where-clause TBD until an engine
                 crate monomorphises it */;
    fn execute(&self, _ctx: &Self::Ctx) {
        // Skeleton: real body in M1.1 lexer feature-complete
        // round (#136). Invokes clause_lex::Lexer::new on the
        // current-record source bytes, pushes tokens into the
        // Write column via ctx.writer().
    }
}
```

The `Ctx` associated type is the awkward part. Hilavitkutin's
design expects the consumer-side engine to provide the concrete
`Ctx` shape that monomorphises the `HasColumnReader<Read>`,
`HasColumnWriter<Write>`, `HasResourceProvider<Read>`, etc.
bounds into a real struct. The scheduler construction is not
shipped yet, so for this skeleton round the `type Ctx` lines
stay as TODO placeholders that the downstream scheduler wiring
fills in. Alternatives explored:

- Parameterise `LexWU` over its `Ctx` (drop the associated-type
  declaration, add a `<C: ...>` parameter to `LexWU<C>`). Works
  but explodes the pipeline tuple shape when five phases have
  five distinct `C` parameters.
- Define a `ClauseCtx` ZST in `clause-schedule` that unifies
  all five phases' provider bounds. Shipped in this round as a
  type alias for "the concrete Ctx the scheduler builder wires
  up." Body is a PhantomData marker until the scheduler's
  composition lands.
- Lean on `core::convert::Infallible` / marker ZST and leave the
  `type Ctx = ClauseCtx` line as a stable placeholder.

Recommendation: ship a `ClauseCtx` ZST in `clause-schedule`'s
`ctx.rs`. All five WUs set `type Ctx = ClauseCtx`. The real
provider bounds get implemented on `ClauseCtx` in a follow-up
round (likely #134 persistence spine, when the actual Column
and Resource storage shapes arrive). Until then, the skeleton
compiles because the associated-type bound `HasColumnReader<...>`
etc. admits "no impl yet" at consumer skeleton level — wait,
actually it doesn't. `WorkUnit`'s `type Ctx:
HasColumnReader<...> + ...` bound must be satisfied at
`impl WorkUnit`.

Revised recommendation: for this skeleton round, leave the
`type Ctx = ClauseCtx` line with a `ClauseCtx` that satisfies
all provider bounds via blanket / empty impls. The impls are
no-ops (`unsafe fn read<T>(&self, _: USize) -> T { unreachable!() }`
etc.) annotated as "skeleton: execution paths never run in
skeleton mode." This keeps `cargo check` green without
shipping a real scheduler.

That surfaces risk: if the skeleton accidentally runs, it
panics. The answer is "it cannot run because the engine-side
scheduler builder is itself skeleton (`Scheduler::build()`
returns `Scheduler::default()` with no WUs composed)." So the
skeleton is internally consistent: nothing invokes the WU's
`execute`, nothing consults the Ctx's impls.

## CLAUSE_PIPELINE const

```rust
pub const CLAUSE_PIPELINE: (LexWU, ParseWU, ResolveWU, TypecheckWU, CodegenWU) =
    (LexWU, ParseWU, ResolveWU, TypecheckWU, CodegenWU);
```

This is what the hilavitkutin scheduler builder consumes once
composition plumbing lands upstream. Exposing as `const` (not
`static`) because the WU types are `Default` ZSTs and the
tuple is `Copy`.
