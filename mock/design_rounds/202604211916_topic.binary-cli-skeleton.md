# Current state

`clause` is the top-level binary crate (`mock/crates/clause`).
Nuked during scaffolding; `lib.rs` and any `main.rs` carry only
the "nuked by `cargo mock --nuke`" stub. `Cargo.toml` carries no
dependencies. The `no-empty-crate` lint has flagged this since
the workspace bootstrapped.

The phase crates ship in varying states:

- `clause-lex` — real body (1032 lines). Tokenizer handles
  identifiers, keywords, decimal integer literals, operators,
  punctuation, line/block comments, trivia, and diagnostics.
  `Lexer::from_str(src, file).next()` returns tokens;
  `.next_with_diag(sink)` forwards lex-level diagnostics.
- `clause-ir` — type definitions for `Diagnostic`, `Span`,
  `FileId`, `TokenKind`, `NodeId`, `ScopeId`, `AstNodeKind`.
- `clause-syntax` / `-resolve` / `-typecheck` / `-codegen` —
  skeleton entry points that compile but do not walk real
  content yet.
- `clause-schedule` — empty crate.

End-to-end "clause actually works" requires the binary to exist
and to invoke the lexer (the only phase with a real body). The
parser / resolver / typecheck / codegen bodies expand in later
rounds; the binary shape should not change when they do — it
should compose phases behind subcommands and dispatch without
special-casing.

# Changes proposed

## Binary surface

A single clap-compatible CLI crate, `clause`, with one subcommand
per pipeline phase the user may want to stop at. Only `lex` has a
real implementation this round; the other subcommands reserve
their CLI names so the shape is frozen.

```
clause lex <file>      # lex + print tokens
clause parse <file>    # lex + parse + print AST (stub)
clause check <file>    # through typecheck + report diagnostics (stub)
clause build <file>    # through codegen, emit target (stub)
clause run <file>      # compile + interpret (stub)
```

`check` / `build` / `run` print a "not yet implemented" line
this round. `parse` prints the AST shape the current skeleton
produces (empty slice → empty Ast; a single literal → one-node
Ast; any other input → SyntaxError). Only `lex` executes real
logic.

## Lex subcommand shape

```
clause lex <file>

  Tokenise <file> and print the token stream, one token per
  line. File contents are read via std::fs. Lex diagnostics
  (unterminated block comment, unclassifiable byte) go to
  stderr with a file:line:col prefix.

  Exit code 0 on clean tokenisation; exit code 1 if any lex
  diagnostic fired.
```

Output format, per line:

```
<offset_start>..<offset_end>  <TokenKind>  <byte_literal?>
```

where `byte_literal?` is the source slice for the token when it
carries user text (identifiers, integers, operators, keywords)
and empty for trivia-only or structural tokens. Trivia-attached-
to-this-token is listed on a following line with two-space
indent.

Example for `let x = 42;`:

```
0..3    Let         let
3..4    Whitespace
4..5    Ident       x
5..6    Whitespace
6..7    Eq          =
7..8    Whitespace
8..10   IntLiteral  42
10..11  Semicolon   ;
11..11  Eof
```

## Orchestration crate role

`clause` is a pure orchestration binary. No algorithmic content
lives in it. Every compiler phase owns its logic; `clause` only
wires the phases in order and routes their IO through
caller-owned sinks (diagnostics, byte emitter for codegen).

The binary can use `std` — it is host-side, not runtime. The
`no_std` / fixed-arena discipline on `clause-ir`, `clause-lex`,
`clause-syntax` does not propagate upward.

## Dependency graph

Direct dependencies added this round:

- `clause-ir` — shared types (`Diagnostic`, `Span`, `FileId`).
- `clause-lex` — lexer itself.
- `clause-syntax` — parse entry point (stub call).
- `clause-resolve` — resolve entry point (stub call).
- `clause-typecheck` — typecheck entry point (stub call).
- `clause-codegen` — emit entry point (stub call).
- `notko` — `Maybe<T>`, `Outcome<T, E>`.

CLI parser: stdlib `std::env::args()` hand-rolled for this round
(under 30 lines). No `clap` or `argh` dependency this round — the
subcommand surface is small, adding a dep just for arg parsing
is premature. If the CLI grows to >5 subcommands or
flags-per-subcommand exceed ~3, revisit.

## Pass-DAG + clause-schedule interaction

`clause-schedule` stays empty this round. The binary does not yet
need a pass-DAG because every subcommand at this stage corresponds
to a single hard-coded phase chain. When the pass-DAG lands
(future round), the binary changes from "run phase X, then X+1"
to "schedule graph and walk".

## File layout

```
mock/crates/clause/
├── Cargo.toml          # gets the seven deps above
└── src/
    ├── main.rs         # CLI entry
    ├── lib.rs          # shared orchestration helpers (pub use from main)
    ├── args.rs         # hand-rolled CLI parser
    ├── lex.rs          # `clause lex` impl (real)
    ├── parse.rs        # `clause parse` stub
    ├── check.rs        # `clause check` stub
    ├── build.rs        # `clause build` stub
    ├── run.rs          # `clause run` stub
    └── diag.rs         # diagnostic printer (file:line:col)
```

Each subcommand file gets at most ~80 lines. `lex.rs` is the
only one with real content; the four stubs print
`"<phase> not yet implemented"` and exit 2.
