## Why this topic exists

The Core-forms cut, the effect lattice, and the twelfth-form dismissal were settled on 2026-07-19 from the
ten-consumer census and the converged prior art, before the architecture crystallised. The architecture has since
evolved a great deal (the graded proof spine, certified generation, the one graded algebraic signature with three
projections, reachability leases, the relational engine, the CFG-of-blocks interpreter, the recentered identity),
and the authoring-consumers topic's first analysis (`202607210045`) mirrored the old decisions against that
evolution. The verdict there: the eleven evaluation forms fit as evaluation shape, but three things must change,
and two of them are foundational enough to re-derive the Core rather than patch it. This topic is that
re-derivation. It is foundational Core work and wants its own careful conversation, and likely sketches for the
no-alloc handler typing.

## The three settled mandates (from `202607210045`)

1. **The twelfth Core form is `Handle`** (D3): user-defined resumable algebraic-effect handlers. The first change
   to the ratified Core set. It is a general evaluation primitive (invoke an operation; a handler services it,
   optionally resuming), so it is Core, not a family.
2. **The effect lattice splits** (D4): effect becomes a pure graded monad; build-versus-runtime staging moves onto
   the binding-time graded modality over the knowledge-source join-semilattice (language-author, bundler,
   host-loader, runtime, joined), superseding the two-member `BuildEnv`/`RuntimeEnv` axis.
3. **Content-as-values is the signature's introduction projection** (D5): not a deferred value-node-kind schema.
   The Doc family is the document consumer's introduction fragment. A framing correction folded in here.

## The unification the handler discipline buys

The load-bearing idea D3 unlocks: the effect set, the host-call boundary, and macro expansion collapse into one
handler discipline. An effect is an operation; a handler is what services it. A host-call is a runtime-effect
operation the host handles. Macro expansion is a compile-stage-effect operation the compile stage handles. So the
build-versus-runtime split the old effect lattice drew by hand becomes "which stage provides the handler," which
is the binding-time coordinate (D4). One theory carries all three, and the effect axis stops being "a static set
plus reduction" and becomes "effects are operations, discharge is handling," composing with the effect graded
monad as graded algebraic effects.

Inclusion-not-coverage survives, restated: a program's effect is the operations it invokes that are not locally
handled, and a target `Permits` a set of runtime operations that the residual's unhandled operations must be
included in. The certified-generation and proof story is unchanged in kind: the generated Zig makes an unhandled,
unpermitted operation unrepresentable, and the graded soundness theorem gains a graded-algebraic-effects clause.

## The pieces to work out (the conversation this topic owes)

- The `Handle` form's exact shape: operation invocation, handler clauses (operation to handler body with access
  to the resumption), and the discharge. The Plotkin-Pretnar shape adapted to no-alloc and to comptime-generated
  dispatch, not a heap-and-closure handler stack.
- One-shot/linear versus multi-shot scoping. The resumption reuses `2001`'s one-shot/linear continuation
  machinery (the defunctionalised one-shot coroutine), which is no-alloc-tractable and covers generators,
  coroutines, events, and most async. Multi-shot resumption (full backtracking) needs heap-shaped continuations
  and is the case to scope deliberately (exclude, or admit only behind an explicit escape). This is the first real
  sub-decision.
- The effect axis re-founding: effects-as-operations, the effect graded monad as graded algebraic effects, the
  `Permits` inclusion restated as unhandled-operation inclusion, and how a locally-handled operation drops out of
  the residual's effect the way a reduced build-env effect does today.
- The binding-time modality over the knowledge-source join-semilattice, replacing the two-member
  `BuildEnv`/`RuntimeEnv`. Which stage handles an operation (language-author, bundler, host-loader, runtime) is a
  point on this lattice, so partial bundling is a join, not a special case.
- Host-calls and macro expansion as concrete handler instances: the host installs handlers for the runtime-effect
  operations it services; the compile stage installs handlers for the compile-stage-effect operations (macros,
  const-eval) it services. State both as handler installations rather than as two separate mechanisms.
- Content-as-values as the introduction projection: the value domain, the Doc family as an introduction fragment,
  and the three projections of the one signature (eliminator IR, introduction value-domain, introduction-compiled
  stencils), stated as the settled model rather than a deferred round.
- How the twelve-form re-derivation lands in the rest of the stack: certified generation (the generated Zig
  carries the handler dispatch, illegal-states-unrepresentable for unhandled operations), the relational engine
  (whether handler discharge is a query or stays outside it), the proof spine (the graded-algebraic-effects
  soundness clause), the value-arena (resumption frames as one-shot continuation state).

## Decisions

### CR1: `Handle` supports bounded multi-shot via a host-lent, statically-validated budget (settled, op 2026-07-20)

The resumption scope is not one-shot-only, and not heap-multi-shot. `Handle` supports multi-shot resumption
(resume any number of times, admitting backtracking, nondeterminism, and collect-all over bounded spaces), without
heap, by three moves that are the stack's own pattern applied to continuations:

- The continuation state that must persist across resumptions lives in a host-lent bounded budget: a fixed-capacity
  region the host provides up front, exactly like the value-transfer reserve/commit sink lends a window. The
  framework never allocates; the host owns the memory. No heap.
- A static validation proves that the multi-shot pattern's total continuation footprint (resumption count times
  the per-resumption frame, or a shared-frame-plus-deltas representation) fits the lent budget. If it cannot be
  proven to fit, it is a compile error (strict-by-design), or the required budget is reported to the host.
- The well-behaved case is a pattern whose resumption count is bounded by construction (a bounded loop over a
  bounded choice set), which makes it deterministic and the budget statically computable, fitting the stack's
  determinism ethos.

This is the reachability-lease, depth-cap, fixed-capacity discipline applied to continuations: bounded, budgeted,
validated, no-alloc, and deterministic in the well-behaved case, with full multi-shot expressiveness and none of
the heap. No shipping effect system is known to do no-alloc bounded multi-shot this way, so it is genuine vehje
novelty and an item for the spike inventory (feasibility of the no-alloc bounded multi-shot continuation
representation under comptime).

Consequence: it re-opens a role for resource-bound analysis. The multi-shot budget-fit is exactly a resource
bound, and AARA (potential/amortized analysis) was earlier deprioritized to "three constants" because nothing
load-bearing needed it; the bounded-multi-shot budget-fit is the first thing that genuinely does. The validation
mechanism (a full potential analysis, a structural bound over deterministic patterns, or a runtime cap) is the
next sub-decision.
