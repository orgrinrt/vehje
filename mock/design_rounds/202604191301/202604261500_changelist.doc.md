## Decisions

### 1. Eight crates, including the placeholder.

| Crate | Role |
|---|---|
| `clause-ir` | Shared IR types (span, token kind, AST node ids, diagnostic types). Leaf dep of every phase. No algorithms. |
| `clause-lex` | Tokenisation, trivia, lex diagnostics. Consumes source text, produces a token stream. |
| `clause-syntax` | Parser, AST construction, concrete syntax. Consumes token stream, produces AST. |
| `clause-resolve` | Module resolution, use-tree expansion, visibility, manifest-driven crate graph, name binding. Consumes AST, produces a resolved program graph. |
| `clause-typecheck` | Coherence, generics, bind-target resolution, validator framework integration. Consumes resolved graph, produces a typed graph. |
| `clause-schedule` | Compiler pass DAG. Consumes arvo-graph for topological analysis. Schedules typed-graph → codegen handoff. |
| `clause-codegen` | Target-agnostic codegen. Emits the intermediate representation consumed by extension targets (`clause-jomini`, future `clause-w3`, etc.). Defines the extension-point contract finalised in R3. |
| `clause` | Top-level binary. CLI (`check`, `build`, `compile`, `new`), workspace orchestration, phase scheduling hand-off. |

Rationale: one crate per phase keeps compilation granular, lets
each phase be tested in isolation, and allows downstream extension
repos (`clause-jomini`) to depend on exactly the phases they need
without pulling the whole stack.

### 2. `clause-ir` as leaf dep.

Everything depends on `clause-ir` for shared types:
- `Span` (source span + file id)
- `FileId`, `NodeId`, `ScopeId` (interned identifiers)
- `Diagnostic` (error/warning/info with severity + span + message)
- `TokenKind` enum (shared between lex and syntax)
- `AstNodeKind` enum (the common AST node discriminator)

Rationale: extracting these out of clause-lex / clause-syntax avoids
the "every phase imports everything" anti-pattern that Rust's
orphan rule rewards. clause-ir stays small (expected: ~500-1000
lines); phase crates own the algorithmic content.

### 3. `clause-diag` and `clause-manifest` NOT separate crates.

- **Diagnostic framework** lives in `clause-ir` as the `Diagnostic`
  type + emitter trait. Each phase emits diagnostics via a trait
  method; the CLI crate (`clause`) implements the terminal renderer.
- **Manifest parsing** (Clause.toml) lives in `clause-resolve` since
  resolution drives the crate graph. The manifest seed topic
  (`202604191300_topic.clause-manifest-spec-seed.md`) describes the
  `.toml` format; the parser + validator land in `clause-resolve`
  as a `manifest` module.

Rationale: neither is big enough to warrant its own crate; the
dependency chain stays cleaner without them.

### 4. Dependency graph.

```
clause-ir         (leaf)
  ↑
clause-lex
  ↑
clause-syntax
  ↑
clause-resolve    ← manifest parsing here
  ↑
clause-typecheck
  ↑
clause-schedule   ← consumes arvo-graph
  ↑
clause-codegen
  ↑
clause            (binary; depends on all of above)
```

Each phase depends on its immediate predecessor + `clause-ir`. No
skipping. `clause` binary depends on all phases for orchestration.

arvo + arvo-graph + arvo-bitmask + arvo-sparse appear as direct
deps in `clause-schedule` (pass DAG analysis) and `clause-typecheck`
(validator framework uses arvo-bitmask for access sets). Other
phases stay arvo-independent unless a concrete need surfaces.

### 5. Runtime crates NOT in this round.

The Zig runtime side + C ABI definition crates land in R2
(Task #28). `clause` binary this round assumes the runtime exists
but links against nothing until R2.

### 6. Extension-point contract deferred to R3.

`clause-codegen` defines the extension point stub (a trait that
`clause-jomini` will implement), but the full contract shape
— including how extensions plug into the phase DAG, how
target-specific diagnostics surface, and how built-in targets are
selected — is R3 scope (Task #29).

### 7. Validator framework deferred to R4.

`clause-typecheck` hosts the validator framework, but the concrete
Rust shape (tagged-union trait? compile-time dispatch? which
validators live in core vs plugins?) is R4 scope (Task #30).
