## Why this repo exists

Clause was first developed inside the `stellar-heritage` Stellaris-mod repo as a Python-implemented language targeting Clausewitz script output. After ~15k lines and extensive design work, the decision was made to:

1. Extract Clause into its own repo — game-agnostic, distributable as a standalone toolchain.
2. Port implementation to Rust (compiler) + Zig (runtime) — single-binary distribution, no Python runtime requirement for end users.
3. Keep Clausewitz-specific surface in a future `clause-jomini` extension repo.
4. Write the compiler first, dogfood it to author tooling (deploy / playset / content pipelines) in Clause itself — rustc/cargo pattern.

The Python implementation remains in `stellar-heritage/tools/clause/` as an authoritative reference + parity oracle during the Rust port.

## What did NOT come across

- **Clausewitz/Stellaris-specific content** — stays in stellar-heritage. Future `clause-jomini` repo will describe Clausewitz grammar + codegen as a Clause extension.
- **The crate workspace under `stellar-heritage/crates/`** (std, stellaris, heritage, DLC crates) — those are Clause *programs*, not the Clause language. Graduated content stays with its game.

## Gaps to close in the first fresh session

This is a seed, not a consolidation. Topics intentionally deferred:

1. **Compiler crate split.** What are the Rust crate boundaries? Single-crate vs multi-crate (`clause-lex`, `clause-syntax`, `clause-resolve`, `clause-typecheck`, `clause-codegen`)? Probably multi — lays out as separate `mock/crates/*` scaffolds in the first session.
2. **Runtime split.** Rust compiler + Zig runtime + C ABI between them. Where do macros execute? Scratch? Generative pipeline? Runtime-side or compile-time-side? Design round needed.
3. **Validator framework reconsidered.** The Python prototype for a unified validator framework landed (see seeds for design). Rust shape is different — tagged-union trait + compile-time dispatch, not Protocol-based. Design round: canonical Rust validator shape.
4. **arvo + hilavitkutin integration.** Clause's compiler pass DAG uses arvo-graph + arvo-bitmask. Clause's runtime uses hilavitkutin for morsel-driven macro / scratch / generative execution. Both are new sibling repos (`github.com/orgrinrt/arvo`, `github.com/orgrinrt/hilavitkutin`). Integration points TBD.
5. **Extension point design.** How does `clause-jomini` plug into the base language? Trait contracts for game-specific targets? Pass-DAG extension? Design round.
6. **Strict-mode validation layer.** The STRICT1–STRICT7 Python-era designs (no-shadow, unused, assign-to-immut, int overflow, use-after-move, ambiguous imports, clippy batch) need Rust shape + which live in the compiler core vs which in optional lint plugins.
7. **Macro model final form.** `macros_slice3.md` + `scratch_variables.md` seeds describe proc-only macros. Post-language-first refactor means macros land AFTER the core language is usable — revisit ordering.
8. **Dogfood endgame.** Which Clause-authored tools does the project ship? Deploy / playset orchestration / artgen are candidates that live in the stellar-heritage repo today.

Each item above wants its own topic file in the next session.
