## Deliverables this round

### Change R1 — `ClauseResult` ABI layout: unify to scalar i32

The Rust side declares `#[repr(i32)] enum ClauseResult { Ok = 0,
Err = -1, NullHandle = -2, InvalidInput = -3 }`. The Zig side
mirrors it as `pub const ClauseResult = extern struct { code: i32 }`.

On System V x86-64 and Apple ARM64 these lower identically
(scalar-in-register return). On MSVC Windows x64 they diverge:
a `#[repr(i32)]` enum returns in `eax`, while a one-field
extern struct returns via hidden-pointer (sret). Cross-target
ABI symmetry is a skeleton-round invariant for the runtime
boundary (`runtime-zig` gets loaded by the Rust driver across
every target triple we ship).

**Path chosen: UNIFY TO SCALAR.** Change the Zig side to
`pub const ClauseResult = i32` with named constants exported:

```zig
pub const CLAUSE_RESULT_OK: i32 = 0;
pub const CLAUSE_RESULT_ERR: i32 = -1;
pub const CLAUSE_RESULT_NULL_HANDLE: i32 = -2;
pub const CLAUSE_RESULT_INVALID_INPUT: i32 = -3;
```

Update `clause_runtime_execute` to return `i32` (returning `-1`
directly via `CLAUSE_RESULT_ERR`). Rust side stays unchanged.

Alternative considered and rejected: flip Rust to
`#[repr(transparent)] struct ClauseResult(i32)`. Rejected because
(a) the Rust enum gives exhaustiveness checking at match sites
that a newtype wrapper does not, and (b) the scalar-return form
is the trivially portable one across every ABI.

Update `mock/runtime-zig/DESIGN.md.tmpl` and `README.md.tmpl`:
replace the `ClauseResult = extern struct { code: i32 }` snippet
with the scalar choice and add a note that struct wrapping was
considered and rejected for MSVC x64 ABI symmetry.

### Change R2 — `ClauseRuntime` handle auto-traits

In `mock/crates/clause-runtime-abi/src/handle.rs`. Current body
is `pub struct ClauseRuntime { _private: [u8; 0] }` with `#[repr(C)]`.

The handle pointer (`*mut ClauseRuntime`) crosses the FFI
boundary and points to foreign-owned memory (the Zig runtime's
session struct). Rust must never dereference it. The current
type is `Send + Sync + Unpin` by default — an incorrect set of
auto-traits for an opaque foreign handle. A caller could
construct a safe wrapper around the pointer and move it across
threads or `Pin`-project it, both of which violate the "only
the owning runtime dereferences" invariant.

**Path: add a `PhantomData<(*mut u8, PhantomPinned)>` marker.**

```rust
use core::marker::{PhantomData, PhantomPinned};

/// Opaque handle to a runtime session.
///
/// The handle points to foreign-owned memory (the Zig
/// runtime's session struct); only the Zig runtime may
/// dereference it. Rust treats it as an opaque token —
/// never inspected, never moved, never pinned on this side.
///
/// The `PhantomData` marker makes the handle `!Send`, `!Sync`,
/// and `!Unpin`, blocking the default auto-trait implementations
/// that would otherwise let a caller move the handle across
/// threads or pin-project through it.
#[repr(C)]
pub struct ClauseRuntime {
    _opaque: [u8; 0],
    _marker: PhantomData<(*mut u8, PhantomPinned)>,
}
```

No consumer change — the handle has no construction site on the
Rust side (the skeleton returns `null_mut()` and never
materialises a real value). The auto-trait change is forward-safe
before any real body lands.

### Change R3 — SAFETY-GATE comments on extern "C" exports

In `mock/crates/clause-runtime-abi/src/exports.rs`. Every
`clause_runtime_*` function is currently a stub, but any future
real body must pass through two gates before landing:

1. `catch_unwind` wraps any Rust code that can panic (UB across
   FFI otherwise — a panic that unwinds across the `extern "C"`
   boundary is immediate undefined behaviour).
2. null + nonzero-len input guards are present where applicable
   (`clause_runtime_execute` for the `input: *const u8, len: usize`
   pair; a null pointer with `len > 0` is a caller bug that must
   surface as `ClauseResult::InvalidInput`, not a segfault).

Without a source-side reminder, a future round is free to drop a
real body in and silently skip either gate. Add a `SAFETY-GATE`
comment block above each export declaring both as hard gates
tracked in `BACKLOG`.

Example body (above `clause_runtime_new`):

```rust
// SAFETY-GATE: no real body may land in this function before
//   1. catch_unwind wraps any Rust code that can panic (UB across
//      FFI otherwise).
//   2. null+nonzero-len input guards are present where applicable.
// Both are tracked in BACKLOG as hard gates before non-stub
// implementation.
```

On `clause_runtime_execute`, explicitly mention the null-input
guard applies to the `(input, len)` pair.

### Change R4 — libloading placeholder in driver Cargo.toml

avoiding the "where does this dep come from" moment when the

### Change M1 — `clause-codegen` `emit()` caller-obligation docstring

In `mock/crates/clause-codegen/src/lib.rs`, the public `emit`
function. It forwards to `TargetRegistry::emit_for(target_name,
&ctx)` which returns `Err(CodegenError::TargetNotFound { name:
"" })` on miss. The empty-string sentinel is deliberate:
`CodegenError` is `Copy`, so variants can't own a runtime
`String`. A caller who needs to render `"target not found: {name}"`
must hold the `target_name` they passed in and interpolate at
render time.

This is a surprising asymmetry. Document it on the public
`emit` function's docstring so consumers learn the convention at
the API surface, not by discovering the empty-name sentinel in
the error variant.

Add a `# Caller obligation` section to `emit`:

```rust
/// # Caller obligation
///
/// `TargetNotFound`'s `name` field is a sentinel (`""`) for
/// efficiency — `CodegenError` is `Copy` and can't own a runtime
/// string. Callers who need to render `"target not found: {name}"`
/// should hold the `target_name` they passed in and interpolate
/// at render time.
```

### Change M2 — `Validator` trait `&'static str` note

In `mock/crates/clause-typecheck/src/validator.rs`, on the
`validate()` method. `Diagnostic.message` is `&'static str` (set
at `clause-ir`'s design); validator implementors must use string
literals or `const` slices — no `format!`-produced strings.
Span-enriched message rendering (the "$span_file:$line: $text"
form) is the diagnostic renderer's job, not the validator body's.

A trait-author who doesn't know this will reach for `format!`
the first time they want a dynamic-looking message and hit a
lifetime error they have to track upstream to understand.
Document the constraint on the trait method so it surfaces at
the implementor's point of contact.

Append to the `validate` docstring:

```rust
/// # Implementor note
///
/// `Diagnostic.message` is `&'static str`. Validators must use
/// string literals or `const` slices — no `format!`-produced
/// strings. Span-enriched rendering is the responsibility of
/// the diagnostic renderer, not the validator body.
```

### Change M3 — `CodegenTarget` trait `&'static str` note

Same `# Implementor note` block on `emit()` in
`mock/crates/clause-codegen/src/target.rs`. Codegen targets that
surface diagnostics in their `CodegenArtifact`-related flow face
the same `&'static str` constraint on `Diagnostic.message`.

`mock/crates/clause-codegen/BACKLOG.md.tmpl`, under a new
`## Post-review notes` section:

- `DiagPhase` is not enforced at the trait level. Validator /
