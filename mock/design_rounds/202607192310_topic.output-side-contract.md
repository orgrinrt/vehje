## The spine

A target declares what it supports, and everything else is a proof obligation against that declaration.
Exhaustiveness, feature checking, and staging predicates are three faces of one mechanism. This is the
design's spine and it drives the whole output side.

## Inclusion, not coverage (the exhaustiveness mechanism)

A family is a type. A program carries a type-level set of the families it uses; a target declares a
type-level set of families it supports; emission is bounded on the target's set containing all of the
program's. The guarantee is inclusion (what the program contains is within what the target supports), not
coverage (the target handles every case in a closed universe). Inclusion does not need the universe closed,
so families stay open.

This is stronger than closed-enum coverage, not merely equal. Under coverage every backend must handle every
constructor including ones it cannot render, which forces the Pandoc "drop what isn't mine, silently"
contract. Under inclusion a backend declares a smaller set honestly, and a program using a family outside it
is refused with the construct named. The guarantee gets stronger as the world opens.

The machinery is `hilavitkutin-api`'s `AccessSet` (`access.rs`): sealed `AccessSet` over `Empty`/`Cons<H, T>`,
the `#[marker]` `Contains<S>` witness (head-match and tail-recurse impls coexisting), `ContainsAll<L>` for set
inclusion, `Concat<L>` for type-level append. `Cons<H, T>` accepts any `'static` member, so vehje instantiates
it with its own family marker types, zero upstream change. The `Contains` trait carries a
`#[diagnostic::on_unimplemented]`, so the "target does not support family X" diagnostic comes from the same
attribute: the refuse-with-the-construct-named property is free.

### Two-stage: compile-time proof, runtime evidence, compile-time obligation

Statically known terms (renderers, fragments, anything in source) get the full compile-time proof:
`ContainsAll` discharges at compile time and a mismatch is a compile error.

Runtime-parsed programs cannot carry a compile-time family set (it is not known until the parse finishes).
The family set is computed during parsing as a runtime bitmask over family ids; the target's declared set
lowers to a const bitmask; the check is one bitwise operation. Typestate makes it unskippable: `emit` accepts
only a `Checked<T>`, and a `Checked<T>` can only be produced by running the check for that target. The
evidence is computed at runtime; the obligation to compute it is enforced at compile time. Weaker than a pure
static proof, stronger than every surveyed system (none check before emitting).

### The dependency dimension is supertraits (free)

SPIR-V's dependency-carrying capabilities (declaring a capability implicitly declares what it rests on, so
declarations stay short as the vocabulary grows) are supertraits here: a family trait requires its dependency
families as supertraits. Declaring support for a family pulls its supertrait obligations. No separate
dependency-DAG model to design; the trait system carries it.

## Renderers: total over the declared family set

A renderer (a target backend) must handle every constructor in the families it declares, and that totality is
checked. Totality is over the declared set, not a closed universe: a renderer declares `Supports = (Core,
Doc)` and must be total over those, with no obligation toward a family it never claimed. This composes with
inclusion rather than conflicting: it is the same inclusion-not-coverage move one level down. The Jsonnet
manifestation-as-library shape (renderers written in the language, composing/wrapping total renderers) stays
available on top, but cannot replace the total renderers; the guarantee survives and the flexibility sits
above it.

A backend is a trait impl performing one generic fold over the closed Core plus the declared families.
Pandoc's cost model applies: roughly 380 lines per standalone writer, clustered writers sharing about 1900
under a mode flag, so targets cluster (markdown/terminal/plain are one path, html its own, program-source a
third), which is three paths rather than ten formats.

## Dispatch: compile-time composition, no `dyn` (corrects the shipped skeleton)

The shipped `vehje-codegen` has `TargetRegistry::lookup(name) -> Maybe<&'static dyn CodegenTarget>` (the R3
2026-04-26 skeleton chose `dyn` trait objects). The standing compiler posture in canon is explicit: no `dyn
Trait`/`TypeId`/`std::any` in framework code, compile-time dispatch wins, single static binary, no plugin
shared-object loading at the compiler layer. Those jointly mandate a compile-time-composed target set.

The framework defines the target trait (associated types allowed, since no `dyn`, and a `Supports` type-level
family set as an associated type). A distribution binary composes the concrete targets it links, each still a
separate repo, which under Rust is a separate crate, so the extension model holds without runtime plugins.
Target selection by name is a runtime string resolving through a generated match; the emit itself is
monomorphised. This is the rustc model: a backend is compiled into the distribution and adding one is a crate
dependency plus a rebuild. The runtime (Zig) is explicitly exempt and may load dynamically for
evaluation/staging; the rule cuts along the compiler/runtime seam. The `dyn` registry is drift to correct.

## Effect model: a second type-level axis, folding down to a clean Zig contract

The effect intent (`08_decisions.md` §2 left it open) is resolved by the same typestate spine, judged against
two criteria op named: leverage Rust's strong typestate, and fold down nicely for the Zig embeddable runtime.

Every construct carries, alongside its family, an **effect set**. The effect vocabulary is parametrized, not
enumerated (op, 2026-07-19): `Pure`, `Reads<E>`, `Writes<E>`, where `E` ranges over an open **environment**
axis (`BuildEnv`, `RuntimeEnv`, and any later env kind: a host env, a capability env). `Pure` is the empty
effect set. The effect is computed from what the construct references (a registry query is `Reads<BuildEnv>`,
a runtime input is `Reads<RuntimeEnv>`, a runtime output is `Writes<RuntimeEnv>`), decidably, not inferred
probabilistically, so decision 1's no-heuristics rule holds.

Parametrizing over the env axis rather than enumerating each env-times-verb pair as a flat member does three
things at once. `Writes<BuildEnv>` exists for free (the earlier open question of whether to reserve a fifth
`WritesBuildEnv` member dissolves: it is just `Writes<BuildEnv>`, expressible when a consumer needs build-time
registry mutation, costing no lattice widening). A new environment kind is a new marker type, not an edit to a
fixed lattice. And each `Reads<E>` / `Writes<E>` at a concrete `E` is a distinct concrete `'static` type, so
it drops straight into `Cons<H, T>` as a member with zero upstream change, exactly like a family marker.

The effect set is a **second orthogonal axis using the identical `AccessSet` machinery as families**, and
under parametrization it becomes a *perfect mirror* of the family axis, not merely a parallel use of the same
primitive. Families answer "what constructs does a program use, what does a target support"; effects answer
"what environments does a construct touch, what does a runtime permit". Both are `residual_set ⊆ declared_set`
checked by the same `ContainsAll`. A target/runtime declares a `Permits` effect set the same way it declares a
`Supports` family set; the residual's effect set must be included in it. A construct carries both a family and
an effect set, orthogonal because a different family may also read the same env.

Staging layers cleanly. Target policy (decision 1) governs control-construct fate uniformly (reduce-all vs
preserve-control-flow). The effect axis governs environment-read fate under it: any `BuildEnv`-parametrized
effect is always reduced regardless of the target's control policy, because it can survive to no runtime; a
`RuntimeEnv` effect follows the target policy; a conflict (the author asserts a build-env read residual for a
runtime target) is refused, naming both sides, in decision 1's checked-predicate shape.

The payoff is the Rust-to-Zig fold-down, and it is now literally the family check one axis over. The runtime
declares `Permits` as the set of runtime-tier effects it can execute (`Reads<RuntimeEnv>`, `Writes<RuntimeEnv>`,
and whatever other runtime-tier envs exist), a set that by construction contains no `BuildEnv`-parametrized
member. The emit boundary produces a `Checked` residual whose effect set is proven included in `Permits`, so
every `Reads<BuildEnv>` / `Writes<BuildEnv>` is proven reduced away by the Rust compiler before emission. The
Zig runtime's contract is narrow and guaranteed: `residual.effects ⊆ runtime.Permits`, the same `ContainsAll`
proof families already discharge, enforced entirely in Rust. The Zig runtime never implements build-env
semantics, because build-env effects provably cannot reach it; the compiler is the only thing that ever
touches the registry, `self`, or build resources. This is the option that most leverages Rust typestate (the
proof lives in Rust, same machinery and now the same *check shape* as families) and folds down cleanest for
Zig (a provable, minimal runtime contract, one const `Permits` set), which is why it wins over refuse-by-default
(no positive model to prove exclusion against) and fold-into-families (staging smeared across per-target
lowerings).
