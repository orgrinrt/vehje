# Topic: the three forms of codegen, and what compiles where

**Date:** 2026-07-20
**Phase:** TOPIC
**Round:** runtime output + lease proof. The foundational topic of the round; the transfer and lease topics sit
under it and are re-voiced against it.
**Scope:** Name the three distinct operations we have all been calling "codegen", state how each acts and at
which level, fix what the Rust side compiles versus what the runtime compiles, and retire "native" as a
special concept. Written to stop the recurring conflation, for this session and for later readers.
**Grounds on:** the committed contract spine (`202607192358/` topics: framework identity, output-side
contract, ABI and runtime execution), read as paper trail not canon where it uses the older program-centric
framing; the value-transfer study (`mock/research/202607201227_runtime-value-transfer-study/`); and op's
clarifications in the 2026-07-20 design conversation.

## The confusion this fixes

"Codegen" has been used for three genuinely different operations, and collapsing them into one word is what
keeps derailing the design. It has meant, at different moments: the Rust side generating the runtime's own
code from a language definition, a macro rewriting IR into IR, and a target turning IR into some output shape.
Those are three operations at two different levels performed by two different artifacts, and the word hid that.
A second phantom rode along with the confusion: "native" got treated as a special execution concept, a tier at
the top of a ladder, when it is nothing of the kind. This topic names the three operations, places each at its
level, and drops "native" as anything other than one ordinary output target.

## The three artifact layers

The operations only make sense against the layers that perform them, so name those first. This is the
layering that illustrated the split during the design conversation.

The **language compiler** is the Rust side. It runs at dev time, it is never shipped to a consumer or host,
and its input is a language definition (a grammar, the families and their effect classification, the region
and lease rules, the targets). It does not see or touch any end-user script. The **general engine** is the
language-agnostic runtime core, authored once by hand: the IR interpreter, the analyzers' general algorithms,
the value transport, and the machinery every language's runtime shares. The **composed runtime** is the
shipped artifact, a binary and a library: the general engine plus the language-specific code the language
compiler generated, made whole for one language. Consumers and hosts get the composed runtime. Scripts arrive
there, at run time, and the language compiler never sees them.

## The three forms of codegen

Each is named, with what it consumes and produces, and the layer and time it acts at. The proposed canonical
names are below; the point is that they are three names, so the bare word "codegen" is retired.

**Runtime generation** is the Rust language compiler generating the runtime's own code from the proven
language definition. It consumes a language definition that has passed the static soundness proofs (its family,
effect, and lease disciplines are shown hole-free) and it produces the language-specific parts of the composed
runtime. This is "compiling the language": it generates the code the runtime needs in order to be a runtime
for that language. It runs once per language, at dev time, in the language-compiler layer, and it never runs on
a script.

**Macro expansion** is a script's own build-stage metaprogramming, rewriting IR into IR. It consumes IR and
produces IR: a macro expands against build state, a const folds, a preprocess rewrites. This is the only form
for which "codegen is IR to IR" is a true statement, and it is true only here. It runs per script, at run time,
inside the composed runtime, during the script's compile stage (the build-environment reductions the effect
axis already isolates).

**Output generation** is a target turning IR into its output shape. It consumes IR and produces the output,
whatever the output is. This is the form that spans interpretation and transpilation, because those are not
different operations, they are the same operation aimed at different targets (below). It runs per script, at
run time, inside the composed runtime, during the output stage, and every target is one instance of it.

## Output generation is a spectrum, and interpretation and transpilation are its poles

The load-bearing correction: interpreting and transpiling are the same concern, output generation, at two ends
of one spectrum, not two mechanisms. Full interpretation evaluates everything in the run and produces a
behavior or a value as its output (the value crosses back through the value transport the transfer topic
designs). Pure transpilation evaluates nothing and re-expresses the IR in another language's definition, its
output being that other language's source. Between them sit the mixes: a target that transpiles most of a
program to another language and still interprets some of it. A target is just a point on this spectrum, a
declaration of what it supports and an obligation to produce output for it, which is exactly the output-side
contract already settled (a target declares `Supports` and `Permits`, is total over its declared families, and
inclusion-not-coverage governs what it must accept). Where a given target sits on the interpret-to-transpile
spectrum is set by the effect axis and the target's staging policy: build-environment effects are always
reduced away, and runtime-environment effects are evaluated or preserved-as-emitted-code according to the
target's policy. Reduce-everything is the interpreting end; preserve-control-flow is the transpiling end.

## "Native" is not a concept; it is a target

There is no native execution mode, no native tier, no native endgame. "Native" is one output-generation target
like Lua, like C#, like a fully-interpreted value. It sits on the same spectrum as every other target and is
declared and checked the same way. The committed ABI topic's tier-3 "native code via LLVM or cranelift, with
the runtime collapsing to plumbing" is superseded on this point: it invented a distinct native concept that
does not exist. If a target wants machine code, it is an output definition producing machine code, and the
practical route is generating Zig and letting the Zig compiler own the platforms, not a hand-built machine-code
backend. Treat "native" as an ordinary target and the phantom disappears.

## What the settled trail this confirms, and what it supersedes

This does not overturn the contract spine; it names the operations the spine already implied and removes two
misframings. It confirms: vehje is the framework, the general-purpose language is a consumer, the core is
eleven closed Core forms plus open families, families and effects are two orthogonal `AccessSet` axes with
inclusion-not-coverage, and the design is two-stage (a compile-time proof and a runtime evidence check). What
this topic adds is the correct reading of that two-stage shape at the artifact level: the compile-time proof is
the language compiler proving the language's disciplines sound and performing runtime generation; the runtime
evidence is the composed runtime, on each arriving script, running the analyzers, doing macro expansion, and
doing output generation. The Rust side compiles the language; the runtime compiles and runs the scripts.

It supersedes, as older program-centric framing: "the compiler reduces a program to a residual that crosses to
the runtime" (the Rust side compiles a language, not a script; what crosses to the shipped runtime is the
generated language code, once, not a per-program residual), the tier-tagged arena/bytecode/native ladder with
native at the top (native is a target, not a tier; execution-speed optimizations like caching expanded IR are a
separate, orthogonal concern from the output-target spectrum), and the bare word "codegen" (retired for the
three named forms).

## Vocabulary

| Operation | Consumes to produces | Layer and time | Was called |
|---|---|---|---|
| Runtime generation | language definition (proven) to composed-runtime code | language compiler (Rust), dev time, once per language | "codegen", "the compiler" |
| Macro expansion | IR to IR | composed runtime, run time, per script, compile stage | "codegen", "macros" |
| Output generation | IR to target output (interpret to transpile spectrum) | composed runtime, run time, per script, output stage | "codegen", "targets", "emit", "native" |

## Where the lease proof and the value transport sit

The lease and region proof is the third static axis, parallel to families and effects, on the same two-stage
pattern: the language compiler proves the language's lease discipline sound (part of the soundness that gates
runtime generation), and the composed runtime runs the per-script region inference (part of the runtime
evidence, alongside the family and effect bitmask checks). The value transport (the value-arena and the
reserve-commit sink) is a general-engine mechanism used by the interpreting end of output generation to hand a
produced value back to the host; the wire format it uses may be specified by the language compiler as data the
runtime carries.
