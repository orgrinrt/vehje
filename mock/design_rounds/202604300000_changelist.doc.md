# Doc Changelist: vehje skeleton debt sweep

**Date:** 2026-04-24
**Phase:** DOC
**Scope:** workspace-wide `PRINCIPLES.md.tmpl` + eleven skeleton crates
(`clause`, `clause-ir`, `clause-lex`, `clause-syntax`, `clause-resolve`,
`clause-typecheck`, `clause-schedule`, `clause-codegen`,

**Source topics:**
No separate topic file. Sweep has a single directive with three decisions

## Purpose

Close the skeleton-debt gap accumulated across all eleven crates between
the shipping doc templates (which already specify arvo-grounded types
everywhere) and the current stub source (which uses bare primitives
pending the sweep). Retire the temporary lint-severity lowering that
rode on the vehje rename commit (`arvo-types-only`, `no-bare-numeric`,
`no-bare-string`, `no-public-raw-field` currently pinned to `warn` at
every gate; target: `error` at commit + push).

Address three related gaps along the way:

1. **no_std-first framing is implicit in docs but absent from
   `PRINCIPLES.md.tmpl`.** The doctrine needs to be stated. Vehje is
   written `no_std` + `no_alloc` first. If only one build variant ever
   ships, it is the `no_std` + `no_alloc` one. `std` support is a
   feature-gated opt-in added later for third-party ecosystem fit, never
   the baseline.

2. **`clause-resolve` `lib.rs` module doc** currently reads "this crate
   uses `std`; it is host-side" and treats `no_std` as a constraint the
   host-side compiler phase does not inherit. This reverses the
   doctrine. Reframe: the host-side compiler phases are `no_std` + `no_alloc`
   just like the runtime; any `std` use inside a compiler crate is a
   deliberate feature-gated opt-in, not a default.

3. **`clause-runtime-abi` FFI boundary** has the same two-tier policy
   need that `hilavitkutin-extensions` resolved in round 202604510000:
   wire-stable primitives at the C-ABI boundary can use an arvo
   transparent newtype (like `USize`, `Bool`) where layout is wire-
   identical, but bare primitives (`i32` for `ClauseResult`, `u32` for
   the abi-version scalar) stay bare because no arvo type has fixed-
   width wire-stable layout at those widths yet. A future `UWire<N>`
   primitive in arvo flips the bare sites later (see `BACKLOG.md.tmpl`).

No new types are being designed. No API shape changes. No doc template
changes invalidate shipped items. This is a doc-level framing sweep
plus explicit statement of the FFI-boundary policy for the runtime
ABI, nothing more.

## Deliverables this round

### Change D1 — state no_std-first doctrine in `PRINCIPLES.md.tmpl`

Add a top-level subsection to `mock/PRINCIPLES.md.tmpl` stating:

> Vehje is written `no_std` + `no_alloc` first. Every crate in the
> stack declares `#![no_std]` at `lib.rs` root. The runtime, the
> compiler phases, the build-dep crates, and the bin entry point all
> operate inside this discipline. If only one build variant ever ships
> Vehje, it is the `no_std` + `no_alloc` one; `std` support is a
> feature-gated opt-in added later for third-party ecosystem fit, not
> the baseline.
>
> A crate MAY gate `std`-requiring code behind a `std` cargo feature
> when a genuine ecosystem-fit reason exists, but the core crate surface
> compiles and runs without that feature, with `#![no_std]` at the
> root. The `alloc` crate is likewise a feature-gated opt-in, not a
> baseline. Heap allocation remains excluded by default.

Place this subsection directly under the existing "Static composition"
or equivalent invariant section, before any later discussion of
workflow or tooling.

### Change D2 — reframe `clause-resolve` lib.rs doc comment

The `//!` module doc in `mock/crates/clause-resolve/src/lib.rs`
currently closes with:

```
//! This crate uses `std`; it is host-side (compiler phase), not
//! runtime. The `no_std` / fixed-arena discipline on `clause-ir`,
//! `clause-lex`, `clause-syntax` does not propagate here.
```

Replace with:

```
//! `clause-resolve` is `no_std` + `no_alloc`. The host-side
//! compiler phases follow the same discipline as the runtime: every
//! crate in the stack declares `#![no_std]` at its root, heap
//! allocation is excluded by default, and fixed-arena + consumer-
//! provided storage patterns (`MemoryProvider` on hilavitkutin-api,
//! `Seq<T, N: Cap>`, `Map<K, V, N: Cap>`) carry all collection
//! concerns across API boundaries.
//!
//! If a future need surfaces for `std`-requiring behaviour (for
//! instance, a platform-sensitive manifest lookup that wants
//! `std::fs` ergonomics behind an opt-in), it lands behind a
//! `std` cargo feature flag gated on `#[cfg(feature = "std")]`. The
//! baseline `no_std` surface stays canonical.
```

This also applies, verbatim or near-verbatim, to any other compiler-
phase crate whose module doc makes the same "host-side, so `std` is
fine" framing. Audit and update during DOC execution:
`clause-typecheck`, `clause-codegen`, `clause-schedule` (if the same
framing appears there).

### Change D3 — state FFI-boundary two-tier policy on clause-runtime-abi

Add a subsection to `mock/crates/clause-runtime-abi/DESIGN.md.tmpl`
titled "FFI-wire primitive policy" mirroring the
`hilavitkutin-extensions` subsection added in round 202604510000:

> `clause-runtime-abi` defines the C-ABI surface for the Zig runtime.
> Every type that crosses the `extern "C"` boundary has a wire-stable
> layout requirement that bare Rust primitives satisfy by construction
> but arvo types satisfy only where a `#[repr(transparent)]` newtype
> preserves the underlying primitive's width byte-for-byte.
>
> Policy:
>
> 1. **arvo newtype where wire-identical.** `USize` is
>    `#[repr(transparent)]` over `usize` and can stand in for a wire
>    `usize`; `CapabilityId` is `#[repr(transparent)]` over `u64`;
>    `AbiVersion` (if introduced here) is `#[repr(transparent)]` over
>    `u32`. Use the arvo newtype wherever the FFI wire type matches
>    exactly and the arvo type carries semantic weight.
>
> 2. **Bare primitive with policy acknowledgement where not wire-
>    identical.** `ClauseResult` is `#[repr(i32)]` and returns via the
>    scalar register on every ABI target; wrapping it changes MSVC
>    Windows x64 layout. `i32` / `u32` scalars that transit `extern
>    "C"` fn signatures without a wire-stable arvo newtype available
>    stay bare with a `// lint:allow(arvo-types-only, no-bare-numeric)
>    tracked: #207` inline annotation (single-token form; multi-token
>    variants are NOT parsed reliably and should not be introduced).
>
> A future `arvo::UWire<N>` primitive (see arvo BACKLOG) will provide
> fixed-width wire-stable newtypes without a `S: Strategy` axis and
> flip the bare sites.

Also add a `BACKLOG.md.tmpl` entry: "Flip bare-primitive FFI-wire sites
to `UWire<N>` — pending arvo `UWire<N>` primitive (see arvo BACKLOG)."

### Change D4 — annotate each compiler-phase crate with the substrate stance in its DESIGN.md.tmpl

Each of the eleven skeleton crates already has a `DESIGN.md.tmpl`.
Audit each and add, near the top, a short subsection titled
"Substrate stance":

> This crate is `no_std` + `no_alloc`. All numeric primitives flow
> through arvo (`UFixed`, `IFixed`, `FastFloat`, `StrictFloat`,
> `USize`, `Cap`, `Bool`) or their domain aliases; all string positions
> flow through `hilavitkutin_str::Str` or `&'static str`; all fallible
> returns flow through `notko::Outcome` / `notko::Maybe` / `notko::Just`.
> No bare primitives cross API boundaries. Private storage is fixed-
> size via const generics or consumer-provided trait-bound primitives.

For `clause-runtime-abi`, replace the last two sentences with the
FFI-wire primitive policy subsection content (D3). The policy overrides
the generic "no bare primitives cross API boundaries" rule at the
extern "C" surface.

For `clause` (the bin crate), the substrate stance is identical but
add: "The bin crate is `no_std` + `no_alloc` like every other crate;
the main entry point uses `notko::Just` / `notko::Outcome` for its
top-level error path, and the CLI argument surface uses `Str` /
`&'static str`, never `String`."
