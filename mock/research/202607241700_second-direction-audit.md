# Second-direction audit: doc claims vs shipped source (Stephen Dolan)

## One-line reading

The canon is honest about the axes it chose to label (binding grade, inclusion, the emitter seam, the hash boundary) and wrong or silent about several it did not: `vehje-schedule` is a complete stub wearing a finished design doc, `vehje-fixpoint`'s engine ships only the strategy its own design doc says is the fallback, `vehje`'s and `vehje-codegen`'s "compose a set of targets at compile time" mechanism does not exist anywhere and carries zero FIXME, and the canon's own Section 11 agenda is already stale against a commit that landed 23 minutes before the canon was authored. None of this is a moral failing; it is exactly the class of gap the prompt says a FIXME walk cannot find, because in three of the four headline cases above the source carries no FIXME at all. The doc said "this exists" in the present tense and nothing in the source disagreed out loud.

## Method (what you read, how you verified)

Read the canon (`mock/design_rounds/202607241615/202607241545_topic.the-vehje-canon.md`) in full, treating every Section 4 conviction and Section 11 agenda item as a claim to verify rather than as ground truth, per the canon's own precedence rule (line 11: "a shipped-state fact answers 'what exists today'... never collapses one into the other"). Then read, in full or in the load-bearing part, `DESIGN.md.tmpl` for all twelve crates (`vehje`, `vehje-ir`, `vehje-codegen`, `vehje-schedule`, `vehje-resolve`, `vehje-typecheck`, `vehje-lower`, `vehje-fixpoint`, `vehje-signature`, `vehje-runtime-abi`, `vehje-runtime-gen`, `vehje-runtime-driver`), plus the `DEEPDIVE_*.md.tmpl` for the crates whose deepdive makes a concrete, checkable claim (`vehje-typecheck/DEEPDIVE_GRADED_SPINE.md.tmpl`, `vehje-fixpoint/DEEPDIVE_RELATIONAL_ENGINE.md.tmpl`, `vehje-runtime-gen/DEEPDIVE_PACKAGE_MANIFEST.md.tmpl`).

For every backticked type, every present-tense behavioral sentence, and every "Module layout" section, verified against `mock/crates/*/src/*.rs` directly: `grep` for the named type/function/field, then read the surrounding function body to confirm what it actually does versus what the doc says it does. Cross-checked bench-backed numeric claims (the reach-fixpoint 8M/16M/50ms figure, the incremental-scaling figures) against the committed CSV and `findings.md` under `mock/benches/`. Used `git log` / `git show` on `vehje-ir/src/hash.rs` and `vehje-runtime-abi/src/wire/residual.rs` to establish the exact commit timeline against the canon's own authoring timestamp, because the canon's Section 11 makes a claim about current source state that turned out to be time-sensitive.

Did not walk `// FIXME` markers as the search method (per the brief); FIXMEs were only consulted after a claim was already flagged, to classify whether the gap was marked or silent.

## Doc claims that overstate shipped state without a label (the dangerous subset)

These are the claims a reader would take as fact on a first pass, because nothing in the same sentence or the same file says otherwise.

**`vehje-schedule/DESIGN.md.tmpl`, lines 19-28 (item 15).** "`Pass`. A registered compile pass: a name, a declared read set and write set over the IR, and its dependencies." "`PassDag`. The directed acyclic graph of passes, built from registration plus dependency declaration, backed by an `arvo-bitmask` `BitMatrix` over a compile-time capacity." "`Schedule`. The topological order produced by `arvo-graph::topo_sort`. A cycle is the `valid_count < N` signal that sort returns; the crate reports it as a schedule diagnostic naming the passes in the cycle." Source fact: `Pass` is `pub trait Pass: core::fmt::Debug {}`, zero fields or methods beyond the supertrait. `PassDag` is `pub struct PassDag;` (a unit struct) with one constructor that does nothing. `Schedule::build()` is `pub fn build() -> Maybe<Self> { Maybe::Is(Self) }`, unconditional success, no DAG, no adjacency, no sort, no cycle detection. This is the sharpest instance in the audit: a three-paragraph design description of a working scheduler, backing a set of types that carry no data and no logic.

**`vehje/src/lib.rs:1-8` (item 14).** "...the distribution-composition entry point that links a set of targets at compile time." Source fact: no such entry point exists. The crate exports one reference target (`DebugTarget`) and one orchestration function (`run`) that itself only calls `resolve` and stops (FIXME at :67-71 names everything after resolve as owed). Nothing in the file's FIXMEs (four total, at :54, :67, :81, and none elsewhere) ever names the missing distribution mechanism. Of every gap in this audit, this is the one an agent grepping for `FIXME` would walk straight past, because the gap has no marker at all.

**`vehje-codegen/DESIGN.md.tmpl:104-112` (item 13).** The "Module layout" section names five source files (`target.rs`, `check.rs`, `fold.rs`, `compose.rs`, `error.rs`) plus `lib.rs`. One file exists. `compose.rs`'s described behavior (compile-time linking of a target set, a generated match resolving a target name to a monomorphised emit) is not merely unfiled, it is unwritten: no name-resolution code, no target-set composition code, anywhere in the crate.

**`vehje-fixpoint/DESIGN.md.tmpl:31-34` and `vehje-fixpoint/src/lib.rs:1-2` (items 10-11).** The DESIGN doc describes `Engine::evaluate` as dispatching between whole-column and semi-naive-delta strategies; the crate's own top-of-file doc comment calls the whole crate "semi-naive." `engine.rs`'s own FIXME, three lines from the doc comment it contradicts, states outright that only whole-column ships and names the DESIGN sentence it falls short of. This is the one case in the audit where the source already told on itself; the doc simply was not updated to match.

**`vehje-lower/DESIGN.md.tmpl:70-83` (item 8).** "Recursive macros are supported." Nothing downstream of that sentence exists: no depth cap, no productivity-condition schema field, no cyclicity sketch, and the macro-expansion mechanism itself (`MacroExpand::apply`) is a no-op. This sentence is the single most confidently-stated claim in the entire doc set that has zero source counterpart of any kind.

## Undocumented load-bearing source behavior

Two smaller findings run the other direction: source doing something the docs do not name.

**`vehje-fixpoint`'s bench provenance is unstated.** The 8M/16M/50ms figure and the whole-column-beats-delta finding (canon Section 7, item 12 above) come from a hand-written Zig prototype (`mock/benches/reach-fixpoint-scale/reach.zig`), not from a bench harness run against the shipped `vehje-fixpoint::Engine` Rust type. The number is real and the finding drove a real source decision (engine.rs's whole-column-only implementation matches the bench's recommendation), so this is not a fabricated number. But neither the canon nor `vehje-fixpoint/DESIGN.md.tmpl` states that the evidence is a standalone Zig re-implementation of the idea rather than a measurement of the crate itself. A reader has no way to know the Rust `Engine` was never directly benched; only the algorithm it now implements was.

**`e7fd7a92`'s hash.rs fix was silently absorbed into the canon's authoring window.** The canon's Section 11 agenda item names a defect that was fixed 23 minutes before the canon's own topic-file timestamp (item 17). This is not dangerous (the fix is correct and current source is right), but it means the canon was not re-verified against `git log` at the moment of its own writing, which is exactly the discipline its own line 11 claims to apply ("verified against source at authoring time").

## The implied implementation-round priority

Ranked by what unblocks the most of the rest, not by doc-vs-source distance alone.

1. **`vehje-schedule`'s actual DAG (item 15).** Every other crate's pass-ordering story (resolve before check, check before lower, lower before codegen) currently works only because `vehje/src/lib.rs::run` calls the stages by hand in a fixed order. The moment a consumer family pass needs to interleave with the Core stages (which the DESIGN doc's own "narrowed remit" section says is this crate's entire reason to exist), there is no scheduler to do it. This is also the cheapest fix in the whole gap map: `arvo-graph::topo_sort` already exists and is already a workspace dependency; the crate's own FIXMEs describe exactly the wiring needed.
2. **The `vehje-lower` recursive-macro terminator (item 8), because canon Section 11 already ordered this first** ("Give `fold_core` the catamorphism shape that lets `Anf` and `MacroExpand` create nodes; implement recursive macro expansion with the three-layer terminator..."). This audit confirms the prerequisite chain is real: nothing here can start until the mutable-arena rewrite path exists (blocking both `Anf` and `MacroExpand`), and nothing in `vehje-signature` currently has anywhere to put the per-operation productivity-condition data the terminator's middle layer needs.
3. **Wire `vehje-fixpoint::Engine` to an actual consumer.** Right now the crate is fully built, benched (at the algorithm level), and unused. The cheapest win is lease inference in `vehje-typecheck`, since the reach/effect fold already exists as a hand-written recursive walk (`infer` in `vehje-typecheck/src/lib.rs:217-316`) that is a drop-in candidate for re-expression as an `Engine`/`Rule` pair. This closes item 9 (the canon's unlabeled "serves lease inference" claim) by making it true.
4. **The distribution-composition entry point (items 13-14).** Lower priority than 1-3 because nothing downstream currently needs more than one target at a time (`DebugTarget` alone exercises the whole pipeline). But it is the single largest "doc says it exists, no FIXME anywhere" gap, and per the canon's own base identity (Section 3: "a framework serving a census of consumers equally"), a framework that cannot compose more than one target at compile time has not yet demonstrated the multi-consumer claim its own identity section makes.
5. **Correct the doc drift itself** (items 4, 7, 10, 11, 16, 19, 20, and the canon's own Section 11 agenda per item 21): a doc-only pass across the affected `DESIGN.md.tmpl` / `DEEPDIVE_*.md.tmpl` files, adding the "State:" labels the canon's own convention already uses elsewhere in the same documents (e.g. `vehje-runtime-gen/DESIGN.md.tmpl`'s own `Manifest` bullet, which self-corrects). This is cheap, does not touch source, and directly prevents the next reader from repeating this audit's early confusion.

## Open questions

Whether `vehje-schedule`'s complete absence from the canon (item 21) is an oversight or a deliberate signal that the crate's design is itself suspect (per the crate's own DESIGN doc line 13-15: "If family passes turn out to be handler instances of the compile-stage effect discipline, this scheduler folds into the orchestrator; it is kept because it exists, is small, and deleting it now bets on an unproven unification"). If the latter, the honest doc fix is not to flesh out `Pass`/`PassDag`/`Schedule` to match the DESIGN doc, but to mark the whole crate's DESIGN doc as describing a contingent, possibly-dissolving mechanism, which it currently does not do either.

Whether the `vehje-fixpoint` Zig-prototype-vs-Rust-crate gap (the undocumented-behavior finding above) is unique to `reach-fixpoint-scale` or a pattern across the other Zig-native benches under `mock/benches/` that fed canon Section 7's numbers. This audit checked only the one bench that directly backs a Section 4 conviction; a fuller pass would check whether `incremental-scaling`'s 0.003 ms figure and the other Section 7 numbers share the same "measures the algorithm, not the shipped crate" scope, since `vehje-fixpoint::Incremental` (the Rust `Store`/`ArtifactSet` traits in `incr.rs`) also has zero consumers today, same as `Engine`.

Whether the correct fix for item 8 (recursive macros) is to weaken the DESIGN doc to match source now, or to treat it as a to-do list disguised as a present-tense description, in which case the fix is re-tensing the prose ("recursive macros are designed to be supported, by...") without changing a single claim's substance. The latter reads as the smaller, more honest edit and matches how the canon itself writes about undone work elsewhere (its own assurance-verb discipline in the preamble: "Intended means design not yet realised").
