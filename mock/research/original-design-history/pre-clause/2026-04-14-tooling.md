# Tooling for Item-Centric Patch Workflow — Design

Date: 2026-04-14
Status: proposed
Depends on: `2026-04-14-item-centric-patches.md` (#262).

Scope: design every CLI subcommand developers will reach for daily after the
item-centric reorg lands. Priorities: migration blockers first, debugging
tools second, hygiene third, editor integration deferred.

Principle: every tool reads from SQLite (via the `parse-patches` ingest
path) or from the new per-item YAML directly. No tool re-parses the old
topic-file layout — once migration lands, that layout is gone.

---

**P0 ships with the reorg** (in the same batch as the layout change, so the
first day of the new layout is usable). **P1** ships shortly after to make
the `feature:` infrastructure load-bearing. **P2/P3** are follow-up tasks.

## P0 — must ship with #262

### `megapatch migrate-patches`

**Purpose**: one-shot conversion of the current `megapatch/patches/` tree
from topic-based to item-centric, with round-trip verification.

**Why it's P0**: this IS the reorg. Without it, there's no reorg to ship.
Without round-trip verification, the reorg is a risk to correctness — we
have 14,721 patches and no human will audit them all.

**Signature**:
```
megapatch migrate-patches [--tree megapatch/patches] [--out megapatch/patches_v2]
                          [--dry-run] [--verify-only]
```

**Behavior**:
1. Snapshot current DB state (item_id, directory, type, mod, content hashes
   for every row) into a fingerprint table.
2. Read DB → group by `(directory, item_id)`.
3. For each group: emit per-item file OR append to `_declarations.yml`
   per the decision in #262.
4. Auto-derive `feature:` from old `source_file` where parseable
   (`mesh/105_political_system_deep_integration.yml` →
   `political_integration`).
5. Auto-split old `note:` into `status` + `rationale` when status markers
   are present (`REVIEWED:`, `TODO:`, `PROVISIONAL:`); leave `status:`
   unset otherwise.
6. Rename `mods_considered` → `source_mods`.
7. Run `parse-patches --tree <out>` against new tree. Compare DB to
   fingerprint snapshot. Required fields (`item_id`, `directory`, `type`,
   `mod`, `content`, `find`, `replace`, `field`) must be byte-identical.
8. `--dry-run` stops before step 7 (emits tree, skips verification).
9. `--verify-only` re-runs verification against an existing out tree
   (for CI).

**Failure modes**:
- Round-trip mismatch → emit diff report, exit non-zero, leave output in
  place for inspection.
- Unknown old-file pattern for feature inference → leave `feature:` unset,
  log which patches couldn't infer, surface count at end.

**One-time tool**. Lives at `ingest/migrate_patches.py`. Can be deleted
after the cut-over commit if we're confident we won't need to re-run it.
Keep for now.

### `megapatch trace <directory>/<item_id>`

**Purpose**: show the full patch chain for one item, in apply order, with
cumulative compiled state after each step.

**Why it's P0**: without trace, debugging "why does this item look wrong"
reverts to mentally running every patch in order. With trace, tool does it
and presents the diff per patch. This is the #1 daily-use debugging tool
and the main payoff of the item-centric layout.

**Signature**:
```
megapatch trace <directory>/<item_id>
                [--patches 1,3,5]       # only apply these indices
                [--show full|diff|last] # output format
                [--target release|debug] # which build to trace
```

**Output** (default `--show diff`):
```
═══ trace: common/buildings/building_bureaucratic_1 ═══
Rule: LIOS.  Winner: mod 2798297351.  4 patches.

Base (from winner):
    building_bureaucratic_1 = {
        category = government
        base_buildtime = 240
        ...
    }

Patch 1 — inject_field [01_sort_those_buildings.yml]
    status: reviewed
    feature: building_order
    + tags = { building_government }
    --- diff preview above ---

Patch 2 — inject_field [03_pt_tradition_modifiers.yml]
    status: reviewed
    feature: pt_traditions
    + tradition_modifier = { tradition_bureaucracy_cost_mult = -0.15 }

Patch 3 — inject_field [11_stellar_ai_over_stb_weights.yml]
    status: provisional
    feature: stellar_ai
    + ai_weight = { factor = 3 modifier = {...} }

Patch 4 — replace_in_item [mesh/85_stb_ai_weight_fix.yml]
    status: reviewed
    feature: mesh
    find:    factor = 3
    replace: factor = 5

Final compiled content (→ .dist/megapatch/common/buildings/):
    building_bureaucratic_1 = {
        category = government
        base_buildtime = 240
        tags = { building_government }
        tradition_modifier = { tradition_bureaucracy_cost_mult = -0.15 }
        ai_weight = { factor = 5 ... }
        ...
    }
```

`--show full` emits the full item body after every patch (verbose but
useful when diffs aren't enough). `--show last` is just the final
compiled output. `--patches 1,3` applies only selected patches for A/B.

**Implementation**: reuse the existing `compile_item` machinery but wrap
it to emit per-step snapshots instead of a single final result. The
compile ops already exist; trace is a visualization layer on top.

### `megapatch new-patch <directory>/<item_id>`

**Purpose**: scaffold a new patch entry into the right item file, creating
the file if missing.

**Why it's P0**: without it, devs copy-paste from another file to create
a new patch. Copy-paste guarantees schema drift (wrong field names,
missing required fields, stale rationale). A scaffold locks in the
canonical schema.

**Signature**:
```
megapatch new-patch <directory>/<item_id>
                    --type <override|replace_in_item|inject_field|insert_item|delete_item|no_override|prefer_mod>
                    [--feature <tag>]
                    [--source-mods 111,222,333]
                    [--rationale "short rationale"]
                    [--status provisional|reviewed|to-revisit|wip]
                    [--edit]                # open $EDITOR on result
```

**Behavior**:
1. Compute target path: if `_declarations`-type (no_override/prefer_mod)
   → append to `<directory>/_declarations.yml`. Else → create or append
   to `<directory>/<item_id>.yml`.
2. If file doesn't exist, create it with the canonical header
   (`directory:`, `item:`, empty `patches:` list).
3. Append a new entry with the chosen `type` and template placeholders
   for required fields (`content: |`, etc.).
4. Placeholders include TODO comments so the dev sees what needs filling.
5. If `--edit`, launch $EDITOR on the target file with cursor positioned
   at the new entry.

Example output for `megapatch new-patch common/traits/trait_psionic --type override --feature psionic_overhaul --edit`:
```yaml
# common/traits/trait_psionic.yml  (created)
directory: common/traits
item: trait_psionic

patches:
  - type: override
    feature: psionic_overhaul
    source_mods: []   # TODO: fill with mod IDs this consolidates
    status: wip
    rationale: |
      TODO: explain why this override exists
    content: |
      trait_psionic = {
        # TODO: paste and consolidate content
      }
```

### PatchLinter schema rules

**Purpose**: enforce the new schema at lint time. Every deviation becomes a
Finding routed through the existing linter policy.

**Why it's P0**: schemas without linters rot. Within a week of the reorg
someone will write `status: reviwed` (typo) and it'll ship without
complaint unless a linter catches it.

**Rules to add** (in `linters/builtin/patch_shape.py` — extend existing):

| rule_id | severity | what it catches |
|---|---|---|
| `PATCH_UNKNOWN_STATUS` | ERROR | `status:` not in {reviewed, provisional, to-revisit, wip} |
| `PATCH_MISSING_RATIONALE_ON_SURGERY` | WARNING | `type` ∈ surgery types (override/replace_in_item/inject_field/insert_item/delete_item) without `rationale` field |
| `PATCH_UNKNOWN_FEATURE` | INFO | `feature:` value not in the known-features registry (built from the union of all `feature:` values in the corpus — flags likely typos) |
| `PATCH_FEATURE_REGISTRY_STALE` | INFO | Known-features registry file out of date; regenerate via `megapatch fmt --update-features` |
| `PATCH_DEPENDS_ON_BROKEN` | ERROR | `depends_on:` references a slug that doesn't resolve |
| `PATCH_DECLARATIONS_ITEM_HAS_SURGERY` | ERROR | An item in `_declarations.yml` also has a per-item file (layout rule violation — item goes in one place only) |
| `PATCH_DECLARATIONS_INVALID_TYPE` | ERROR | `_declarations.yml` containing a `type:` that isn't `no_override` or `prefer_mod` |

All are PatchLinters (patch-input scope, pre-compile). They run in the
existing lint pipeline, so `PATCH_UNKNOWN_STATUS` blocks release builds
for first-party patches same as existing rules.

## P1 — ship shortly after

### `megapatch feature <name>`

**Purpose**: list every patch tagged with a given feature — the whole
cross-cutting concern at a glance.

**Why**: `feature:` tags are only useful if there's an ergonomic way to
query them. Without this command, they're just free-form strings nobody
reads.

**Signature**:
```
megapatch feature <name>
                  [--show items|patches|tree]
                  [--status provisional]    # filter by status
```

**Output** (default `--show items`):
```
═══ feature: political_integration ═══
12 patches across 8 items:

common/on_actions/on_yearly_pulse_country
    - insert_item (reviewed) [mesh/105_political_system_deep_integration.yml]
    - insert_item (reviewed) [mesh/118_ai_behavioral_coherence.yml]
common/on_actions/on_monthly_pulse_country
    - insert_item (provisional) [mesh/122_economic_political_feedback.yml]
common/scripted_effects/fire_political_coherence
    - insert_item (reviewed)
...
```

`--show tree` renders the feature's full surface as a directory tree.
`--show patches` lists every patch individually.

**Related**: `megapatch features list` — enumerate every feature in the
corpus with item/patch counts. Useful for discovering what features exist.

## P2 — follow-up

### `megapatch lookup <symbol>`

**Purpose**: find every patch that REFERENCES a symbol (scripted_trigger
name, trait id, event id, @variable), not just patches that target it.
Answers "what breaks if I rename this?"

**Signature**:
```
megapatch lookup <symbol> [--kind trigger|effect|trait|event|variable|any]
```

**Output**: list of `(directory, item_id, patch_slug)` that mention the
symbol, with context line. Walks the compiled output + patch content.

### `megapatch touches <mod_id>`

**Purpose**: list every patch whose `source_mods` includes a given mod.
Useful when a mod updates and we want to review our coverage.

**Signature**: `megapatch touches <mod_id>`.

### `megapatch fmt`

**Purpose**: canonical format for item YAML files. Auto-sort metadata
fields into a fixed order (`directory`, `item`, `feature`, `status`,
`patches`), normalize indentation, standardize `content: |` block
indentation. Idempotent — run twice gives same output.

**Why P2**: schema drift is slow. Manual reviews catch most of it during
code review. Fmt on CI is a nice-to-have, not a blocker.

**Signature**:
```
megapatch fmt [--check]           # exit non-zero if formatting differs
              [<paths...>]        # default: whole patch tree
              [--update-features] # refresh the known-features registry
```

## P3 — nice-to-have

### `megapatch status-report`

**Purpose**: summary of corpus health. How many patches are `wip`? How
many `to-revisit` and for how long? What's the distribution of `status:`
across features?

**Signature**: `megapatch status-report [--feature X] [--since 2026-01-01]`.

### `megapatch why <directory>/<item_id>`

**Purpose**: blame-like view — for each line of the compiled output,
show which patch contributed it.

**Why P3**: `trace` covers 90% of the use case (you see what each patch
changed). `why` is a polish feature for particularly-tangled items.

---

## Editor integration — deferred

Worth noting but out of this batch:

- **Syntax highlighting**: YAML highlighting already works. Schema-aware
  highlighting (warn on unknown `status:` values in the editor) is a nice
  upgrade — achievable via a JSON Schema or VS Code extension. Low cost
  once the schema is pinned.
- **LSP server**: hover docs for patch types, completion for `feature:`
  tags, jump-to-definition from `depends_on:` slugs. High effort, real
  payoff, worth prototyping after a few months of using the new layout —
  we'll understand the ergonomics by then.
- **Embedded Clausewitz highlighting inside `content: |` blocks**: plugs
  into the existing CWT support in VS Code via a region marker. Defer.

## Where the commands live

All P0–P3 commands are subcommands of `megapatch_compiler`
(`python3 -m megapatch_compiler <cmd>`), dispatched from
`megapatch_compiler/__main__.py` into per-command modules:

```
megapatch_compiler/
├── ingest/
│   ├── migrate_patches.py    # P0 — one-shot migration
│   └── parse_patches.py      # existing, extended for new schema
├── tools/
│   ├── __init__.py
│   ├── trace.py              # P0
│   ├── new_patch.py          # P0
│   ├── feature.py            # P1
│   ├── lookup.py             # P2
│   ├── touches.py            # P2
│   ├── fmt.py                # P2
│   ├── status_report.py      # P3
│   └── why.py                # P3
└── linters/builtin/
    └── patch_shape.py        # extended with P0 schema lints
```

No cross-module dependencies between `tools/*` modules — each is a leaf
that reads the DB or the patch tree and prints to stdout.

## Implementation batching

Three natural commits, in order:

1. **Schema + P0 commands** — parse_patches extension for new layout,
   migrate_patches, PatchLinter schema rules, trace, new_patch. Ships
   together with the reorg cut-over commit. This is the big one.
2. **P1** — feature command. One commit, one module. Ships same week.
3. **P2/P3** — each command is its own small commit. Ship as needed.

Tests follow the existing pattern: unit tests per module (synthetic
fixtures), integration tests via SyntheticProject. Every P0 command gets
unit + integration coverage before merge.

## Tradeoffs flagged

**Complexity**: 5 new P0 subcommands is a meaningful surface. Worth it
because each does exactly one thing, each is small (< 200 lines expected),
and none are speculative — every P0 maps to a specific Pain Point.

**YAML file explosion**: 4500 item files + 240 declarations files = 4740
files. Today we have 455. Git handles this fine (tens of thousands of
small files is a non-issue) but editor "find in files" operations scale
linearly. The tradeoff is accepted because the alternative (keep big
tangled files) is strictly worse for the dominant use case (touching one
item).

**Fmt as P2 is controversial** — you could argue it should ship with P0
to prevent drift from day one. Counter-argument: migration tool emits
canonical format, and if drift is caught by code review in the first
month, fmt is a solution looking for a problem. Revisit if drift does
occur.
