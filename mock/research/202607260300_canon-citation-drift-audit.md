## Verdict in one line

The handler-discipline citation does not license host-serviced arithmetic (Frontier A and Section 3 govern and are unsatisfied); the same substitution recurs at the analyses locus, where the shipped Rust check pass and the Rust relational engine realise exactly the half of the dual-locus that Part C killed; and the Rust per-script pipeline is licensed by the canon's letter in its orchestration and reduction halves but not in its analysis half, a split no shipped document draws.

## The arithmetic instance

**What was built.** The first-party language lowers every operator, and also record and sequence construction, to `Raw(ARITH, ...)` (`mock/research/sketches/202607260000_clause-frontend/src/lower/mod.rs:30` declares the one family id; `:33-54` the opcode set including `RECORD` and `SEQ`; `:126-143` the `family()` constructor). The runtime evaluates `TAG_RAW` by marshalling operands and calling a host callback (`mock/runtime-zig/src/runtime.zig:410-433`; `:414` is `host orelse return EvalError.NoHost`). The only implementation of Clause addition in existence is a Rust `extern "C"` function in a test file (`.../clause-frontend/tests/run.rs:60-97`), and records are likewise built by a test host (`mock/runtime-zig/src/runtime_family_test.zig:267`).

**What was cited.** The recorded justification is explicit and the citations are accurate quotations in substance:

- The round topic: "The canon names the mechanism already. An effect is an operation, a handler is what services it, and a host-call is a runtime-effect operation the host handles; the build-versus-runtime split is which stage provides the handler" (`mock/design_rounds/202607251140/202607251140_topic.family-operations-reach-their-handler.md:9`, citing Frontier B, positive:23).
- The consumer study: "dispatched to the handler the host provides. That is not a workaround; it is the design" (`mock/research/202607251149_the-first-party-language-shape.md:33`).
- The census: genuine places "are a runtime effect, which is to say a family operation the host handles" (`mock/research/202607251530_language-completeness-census.md:75`) and "a host-provided operation is a family operation whose handler is the host" (`:89`).
- The source comments: "which is what keeps the framework family-free" (`runtime.zig:411-413`); "the Core has no `+` and the framework owns no family" (`lower/mod.rs:7-8`), citing Section 3 (positive:45), accurately.

**What governs.** Three canonical items, none of them the ones cited:

1. Section 1 (positive:13): vehje "discharges every operation it knows ... with one handler discipline **at the earliest binding time that operation's inputs are known**." The meaning of `ADD` is fixed by the language definition; the stage that can provide its handler is LanguageAuthor, the earliest point on the lattice. Discharging it at Runtime, through the host, is the latest possible stage.
2. Frontier A (positive:21): "Ahead-of-time work lives at LanguageAuthor (specialising the general Zig runtime to the language definition at our build, which is the first Futamura projection as a build step ...)." The stage that would service arithmetic exists in the design and is inert in the tree: `vehje-runtime-gen::generate` takes `_signature: &Signature` and never reads it (`mock/crates/vehje-runtime-gen/src/lib.rs:108`).
3. Section 3 (positive:45): the shipped runtime is, by definition, "one hand-authored engine **comptime-specialised to the Rust-emitted data**." The family-freeness the source comments cite is a property of the hand-authored engine before specialisation. There is no canonical artifact that is the unspecialised engine; citing the generic engine's family-freeness to justify the *shipped* runtime's ignorance of the language's own operations conflates the two artifacts, and it is only possible because the specialised artifact does not exist.

**Why the cited item does not license it.** Frontier B's letter classifies a host-call as "a **runtime-effect** operation the host handles." Arithmetic is not a runtime-effect operation; the shipped design itself insists on this in the same tree: "arithmetic lowers to `Raw`, so performing through `Raw` would give `1 + 2` an effect, and that is a grade the handler discipline would then have to subtract everywhere" (`mock/crates/vehje-ir/src/node.rs:156-159`). So the shipped state holds both halves of a contradiction: to route arithmetic to the host it is treated as a host-call (a runtime-effect operation, per B); to keep the grading sane it is declared pure (not an effect, per the same B). A pure operation the host handles is licensed by no sentence in B. B's own coordinate ("which stage provides the handler") in fact decides *against* the mechanism: the stage that provides `ADD`'s handler is LanguageAuthor, and the topic's own "not in this round" list shows where the substitution happened, filing "comptime specialisation of known families into the generated runtime" as "an optimisation of this seam rather than a different one" (`202607251140_topic...md:37`). Under Frontier A's letter it is not an optimisation of the seam; it is the mechanism, and the host dispatch is at most its degenerate fallback.

**A second-order consequence worth recording.** Bundling `+`, host services, and record construction into one `FamilyId` (`lower/mod.rs:27-29`: "One id serves all of them ... which keeps the family surface a single number") defeats the inclusion letter of Section 3 ("anything outside is refused **with the offending construct named**", positive:45). `FamilyCheck::effect_of_raw` is keyed on `FamilyId` alone (`mock/crates/vehje-typecheck/src/lib.rs:39-45`), so within `ARITH` a target's `Permits` set cannot distinguish pure addition from an effectful host service: either the family is graded pure and host effects escape the permit check, or it is graded effectful and `1 + 2` carries the tax `node.rs:156-159` refuses.

**Conclusion.** A confirmed instance of the class, in its strongest form. The citation is real, accurate, and orthogonal to the question; the governing items (Section 1, Frontier A, Section 3's specialisation clause) say the opposite; and op's standing call 2 (`calls:27-48`) reaches the same conclusion, which I note as corroboration, not as my ground: the ground is the canon's letter as derived above.

## What the canon licenses the Rust side to do, stated positively

The widened question requires the licensing texts, so here they are, sorted. I read "end-user script" (positive:45) by arrival time, and I show below why that reading is forced by the letter itself.

1. **Per language, at dev time: compile the language definition into validated data and structural proofs.** "A dev-time Rust language compiler (emits validated data and structural proofs, never sees an end-user script, never ships)" (positive:45); "Rust emits validated *data*, never Zig *source*" (positive:29); the compile-side typestate is a lens projection of the one signature (positive:31). Shipped realisations that this text calls for: `vehje-signature` (data only, `mock/crates/vehje-signature/src/lib.rs:1-11`), `vehje-runtime-gen` (the package and manifest, `lib.rs:104-124`; its unread `_signature` at `:108` is the owed wiring, catalogued at negative:90), and the type-level inclusion machinery (`vehje-typecheck/src/lib.rs:150-176`, `vehje-codegen`'s `where`-bound proof), which is the "rustc certifies well-formedness, inclusion, and grading of the emitted data" clause of positive:29.

2. **Per script, at Bundler grade, at dev time: orchestrate and reduce.** Frontier A places a per-script Rust role on the lattice in terms: "and at Bundler (the Rust side inlining a known constant)" (positive:21). Section 3 names two per-script operations at the compile stage: "macro expansion (IR to IR, per script, compile stage), and output generation (IR to output, per script)" (positive:45). A script known at the consumer's build is Bundler-grade knowledge; its compile stage runs at dev time, and the only dev-time artifact is the Rust one. This licenses, by the letter: `vehje::run`'s per-script orchestration (`mock/crates/vehje/src/lib.rs:72-104`), `vehje-lower`'s const-fold, CSE, and ANF (Bundler-grade reductions; also positive:35, "fold + CSE + DCE always-on"), `serialize` emitting the residual byte image (`mock/crates/vehje-runtime-abi/src/wire/serialize.rs:312-316`; a byte image is data, so positive:29's data-not-source clause is satisfied), and the `Grammar` input contract (`vehje/src/lib.rs:48-58`; "A grammar plugs into the input side and lowers a surface syntax into the shared IR", positive:45).

3. **Never: per-script analyses as a Rust implementation.** "Killed: Rust never runs per-script analyses, the runtime does, for all scripts" (negative:38). The trail this kill descends from states the resolved shape exactly: "one hand-authored engine specialised by Zig comptime to Rust-emitted validated data, a single backend, and the dev-time Rust locus runs it **by linking the compiled Zig engine over FFI**" (`mock/research/202607202358_reconcile-grounded-stack-and-rebuttal-to-identity.md:246-248`). So dev-time per-script analysis *runs* exist (the Rust locus invokes them for bundled scripts), but the analyses have one implementation, and it lives in the runtime artifact. The killed framing was precisely "analyses run in the Rust dev-time compiler for bundled scripts and inside the composed Zig runtime for arriving scripts" (`mock/research/202607202210_design_dual-locus-relational-engine.md:6-7`), two implementations, and the kill collapses them into the runtime's one.

4. **Never: see a post-deployment script.** The Rust compiler "never sees an end-user script" and "never ships" (positive:45). These two clauses interpret each other: an artifact that never ships cannot see what arrives after deployment. That is the whole content of the clause, and it is why the arrival-time reading is forced (next paragraph).

**Why "end-user script" must mean arrival after deployment, from the letter alone.** Positive:45 contains, in one sentence-run, both "never sees an end-user script" and "macro expansion (IR to IR, **per script**, compile stage)." If "end-user script" meant "any script," Section 3 would contradict itself within its own paragraph, since a per-script compile-stage operation must see a script and the compile stage of a Bundler-grade script has nowhere to run but the dev-time artifact. The only reading under which positive:45 is self-consistent, and under which Frontier A's "Bundler (the Rust side inlining a known constant)" is not a contradiction of it, is: scripts known at or before the consumer's build (Bundler grade) are the consumer-developer's and may enter the dev-time Rust compiler; scripts arriving at HostLoader or Runtime grade are the end user's and reach only the shipped runtime, whose "load-time compilation, not profile-guided JIT, lives at HostLoader" (positive:21). I therefore answer the coordinator's first inconsistency candidate: Frontier A's Bundler clause does **not** genuinely conflict with positive:45 or negative:38; the conflict dissolves under the reading the letter itself forces. What negative:38 kills is a Rust *implementation* of the analyses, not dev-time per-script compilation.

## Where the canon is internally inconsistent on the locus axis

Three places, sorted by whether they are genuine.

1. **Frontier A's Bundler-Rust role versus "never sees an end-user script" and the Part C kill: not genuine.** Resolved above by the reading positive:45 itself forces (the same sentence-run carries both "never sees an end-user script" and "macro expansion ... per script, compile stage"). But the resolution rests partly on the reconcile trail (`202607202358:246-248`), because the catalogue compressed "the analyses have one implementation, in the runtime artifact, which the dev-time locus FFI-links" into the six words "Rust never runs per-script analyses." That compression is where instances 2 and 3 grew: read flat, the six words are false the moment the dev-time locus invokes the engine; read loosely, they license nothing about implementation locus at all. The catalogue should carry the FFI-linkage clause in its own letter. One sentence in a superseding round closes the gap that two shipped crates currently occupy.

2. **Frontier D's approving status framing versus Part C: genuine, and worth one clarifying clause.** Positive:27 says "of the four grade coordinates, `effect` and `lease` are computed by the join fold **in the shipped check**," pricing the Rust fold as the spine's two live axes, with no note that the fold's *locus* is the killed one and its canonical destination is the runtime engine. A status sentence under the assurance ladder is not a license, but nothing in the catalogue says which it is, and instance 2's citation drift rode exactly that silence. The clause to add: the shipped Rust fold is the interim vehicle of the discipline; its end-state locus is the specialised engine per Part C.

3. **Positive:29's "The proof is discharged in Rust before any lowering": ambiguous antecedent.** If "the proof" is the language package's structural proofs, consistent with everything. If it includes per-script grading, it collides with negative:38. The sentence's context (certified generation, the perimeter naming "the emitted data") supports the first reading, but the second is available to a motivated reader, and instance 2 shows motivated readings get taken. One clarifying prepositional phrase suffices.

## What the class has in common

Every confirmed instance has the same mechanism, and it is worth stating precisely because it predicts where the next one will appear. **The citation gravitates to the canon item that the artifact-at-hand already satisfies, away from the item that names an artifact or stage not yet built.** Host arithmetic cites the generic engine's family-freeness because the generic engine is the only runtime that exists; the governing item names the comptime-specialised artifact, which does not. The Rust check pass cites the verification identity because the Rust fold is the only verifier that exists; the governing item assigns the analyses to a runtime implementation, which does not exist. The Rust fixpoint engine cites a measurement and a consumer re-justification because those are true of the crate that exists; the governing item places the one engine in an artifact that does not exist. In each case the citation is *accurate on an orthogonal axis*, which is exactly why a naive audit passes: prose checked against prose finds a true sentence and stops.

The corollary is diagnostic: every instance co-locates with an inert seam on the unbuilt side (the unread `_signature` at `runtime-gen:108`; the absent runtime analyses; the absent Zig engine; the absent load-time lowering). The citation drift and the Part H existence gap are two faces of one event: when the stage the canon names is missing, the mechanism that should have lived there gets built on the side that exists, and the justification is then necessarily drawn from the items true of that side. Which means Part H's ledger is not merely a list of holes; each hole is a standing attractor for the next citation-drift instance, until it is either filled or its absence is priced in the canon's own letter.

## What would detect it earlier

Mechanisms, not exhortations. Each is checkable by a tool with no judgment in the loop.

1. **An artifact-split manifest, machine-checked.** A committed table mapping every crate, and every `pub fn` whose signature takes a program instance (an `Arena` plus a root `NodeRef`; the shape is mechanically recognisable), to a side of the split: per-language dev-time Rust, per-script Bundler-grade orchestration or reduction in Rust, per-script analysis or execution in the runtime artifact. Each row carries the licensing canon line. A lint fails any per-script-shaped entry point in a Rust crate whose row is absent or whose row's side is "runtime." Instances 2 and 3 fail this check on day one; instance 1 fails it the moment the manifest requires the runtime rows to name their implementation artifact.

2. **A catalogued red test per frontier item, keyed to the governing letter, not the citing one.** For Frontier A: `run_int("1 + 2", host = null)` expected to produce 3, catalogued red. Today it fails at `runtime.zig:414` (`NoHost`), and it flips green exactly when elementary computation enters the (specialised) runtime, and by no other change. A mechanism justified by the wrong canon item can satisfy any amount of prose; it cannot satisfy an executable keyed to the right one. This is the canon's own Part H remedy ("behaviour-shaped catalogued red tests ... red tests scale and adversarial prose audits do not," negative:86) aimed one class earlier in the pipeline.

3. **An unread-parameter gate at the seam.** A `_`-prefixed parameter on a `pub fn` whose crate DESIGN names that parameter's consumption in the present tense ("the data the runtime's comptime specialisation reads") is the mechanical signature of surface existence standing in for a stage. `generate(_signature, ...)` is the type specimen. The design-doc-source-mismatch lint already parses backticked names; extending it to flag DESIGN-named inputs bound to `_` parameters is a small delta.
