# The carrier matrix through the codegen + optimizer-soundness lens (Chris Fallin)

## Verdict in one line

The single-op-definition discipline and the JIT/stencil machine-code paths are genuinely sound and honestly measured; the optimize axis is soundness-clean (every transform is checked against the interpreter) but the headline "run the whole pipeline" story is not what the data actually shows once you look past the summary table, and the deliverable inverts the copy-and-patch terminology it claims to honor.

## What is codegen-sound

One definition of op semantics, actually enforced. `ops.rs:27-46` (`binop_body!`/`unop_body!`) is the single source every scalar dispatch cell and the const-folder (`optimize.rs:48-74`, `eval_op`) defer to. That is not decoration: it converts "the const-folder must agree with the interpreter" from a discipline into a compile-time guarantee, and it is the right fix for the exact defect class the module doc names (`ops.rs:7-11`, twelve binops hand-transcribed across seven sites in an earlier version).

Constant folding is a textbook, sound propagation, not a heuristic. `optimize.rs:106-134` only folds a node when every operand's `cval` is already `Some` (built strictly children-before-parents), `op::INPUT` is explicitly excluded from ever being constant (`optimize.rs:114`), so nothing depending transitively on runtime input is ever folded. This is standard sparse conditional constant propagation without the branch-lattice part (there are no branches in this IR), and it is correctly gated.

AC-reassociation is genuinely value-preserving, and for the right reason: wrapping `u64` `ADD`/`MUL` are exactly associative and commutative (`optimize.rs:376`), unlike floating-point `+`/`*`, so `eqsat_reassociate` (`eqsat.rs:377-449`) reassociating these operators is not the classically unsound "fast-math" reassociation that requires an explicit reassoc flag in a real compiler. The design's own scope statement is correct and important: it does not run a general e-graph to saturation and extract, because greedy extraction from cyclic e-classes (which associativity introduces) is a known-unsound hazard (`eqsat.rs:291-303`). Instead it computes a canonical AC normal form directly (flatten, sort, hash-cons, rebuild), which is sound, bounded, and acyclic by construction. That is a correct read of the real hazard egg/egglog-style saturating equality-saturation engines have to solve with dedicated cyclic extractors, and the carrier sidesteps it rather than mishandling it.

Fusion's eligibility check is exactly right, including the subtle case. `fusion.rs:74-97` fuses a producer into its consumer only when `refcount[i] == 1`. Because `refcount` is incremented once per *use* and not once per *distinct consumer* (`fusion.rs:38-51`), a self-referencing consumer such as `ADD(i, i)` correctly registers `refcount[i] == 2` and is correctly excluded from fusion, even though it has only one distinct consumer node. A cheaper "one consumer node" check would have missed this and silently dropped one of the two uses.

Liveness slot allocation is a correct linear-scan allocator. `liveness.rs:41-123` computes last-use by a single forward pass (last write wins, so it is always the true final reference), pins live-outs to `usize::MAX` so they never free, records operand slots before freeing so a node's own destination can legally reuse a slot an operand just vacated, and dedupes repeated operands in one node so a slot is never double-freed. This is standard, correctly ordered, and cross-validated against the interpreter's own output.

The machine-code paths are real, not simulated, and cross-checked three ways. `copypatch.rs` (direct instruction selection) and `stencil.rs` (`global_asm!`-based copy-and-patch) both emit and execute real aarch64 words under `MAP_JIT`/W^X/`sys_icache_invalidate` discipline (`copypatch.rs:198-274`, `stencil.rs:330-400`), and there are three independent cross-checks in place: each JIT path against the interpreter (`copypatch.rs:283-308`, `stencil.rs:409-434`), and the two JIT paths against each other (`stencil.rs:436-453`). The condition-code choices are correct and consistent between the two independently hand-written generators: unsigned `LS`/`HS` for `MIN`/`MAX` and unsigned `LO` for `LT` (`copypatch.rs:172-187`, `stencil.rs:138-176`), matching the interpreter's unsigned `u64` semantics. The `SHL`/`SHR` lowering to `LSLV`/`LSRV` is correct on a non-obvious point: ARM64's variable-shift instructions mask the shift amount modulo the register width exactly the way Rust's `wrapping_shl`/`wrapping_shr` do (`copypatch.rs:170-171`), so no extra masking code is needed and none was added.

The native-tier ceiling fix is a legitimate, well-diagnosed correction. `native.rs:1-31` documents the actual prior bug precisely: a comptime-visible two-instruction program let the optimizer partially evaluate the interpreter into native code, so the "1.2x" was native vs. native. The fix (opaque wire bytes, no inline fold competing with the interpreters' hoisted-fold discipline) is the right fix for that specific artifact, and the corrected ~2.6-4.3x per-execution ratio (RUN_SUMMARY finding 7) and ~1.5x throughput-ceiling ratio (finding 9) are internally consistent with the raw CSVs I checked (`carrier_native_*`, `carrier_native_ceiling`).

## Findings

1. **The reported optimize-axis numbers do not measure "the optimizer"; they measure only the downstream interpreter running the already-optimized program, and the optimizer's own cost is never reported anywhere in the deliverable.** `gen_matrix.rs:270-276` caches the entire `optimize()` call, including the `eqsat` pass, inside a `OnceLock` computed once per cdylib process, so `algo_ns` is pure post-optimization interpretation time; this matches the doc comment's stated intent (`optimize.rs:9-10`, "its cost is an honest part of the setup term S") and I confirmed the CSV rows are all `mode=warm`, i.e. genuinely past the one-time init. That part is *sound*. What is missing is that `S` itself, the wall time to run fold/CSE/DCE/eqsat, is never measured or reported anywhere in `RUN_SUMMARY.md`, any `carrier_optimize_*_findings.md`, or any CSV column. A decision-grade claim about whether vehje should run `eqsat` (or the whole pipeline) needs the amortization breakeven: how many downstream executions of a residual are needed before the optimizer's own cost pays for itself. That number is unknowable from this matrix as shipped. **Fix:** add a `carrier_optimize_pass_cost` cell family that times `optimize()` itself (not its output) per profile/size/strategy, so the report can state a breakeven instead of an unconditional "run the whole pipeline."

2. **The optimize.rs doc comment's central soundness-adjacent claim, "the CSE+eqsat combo recovers it" (the cross-consumer sharing eqsat loses), is empirically false on every profile I checked, and the bench's own numbers already show this if you look past the summary prose.** I instrumented `optimize()` directly (`mock/benches/carrier/src/optimize.rs`, calling the public `optimize` fn from a throwaway example against the six shipped profiles at N=4096): `cseeqsat` produces a program with the *exact same node count* as `eqsat` alone in every profile I tested (madd: 22785 vs 22785; tight: 11574 vs 11574; real: 3636 vs 3636; wideselect: 3679 vs 3679; leaf: 788 vs 788), and the RUN_SUMMARY's own timing numbers for `carrier_optimize_madd` show `cseeqsat` (3.573ms) and `eqsat` (3.573ms) within noise of each other, both ~142x slower than `all`, not "recovered" toward `cse`'s 601.74us. The mechanism: `eqsat_reassociate` already hash-conses fully within itself (`eqsat.rs:305-346`, its own local `cse_op`/`const_node` maps), so a downstream structural-CSE pass over its already-canonical output has nothing left to deduplicate; outer CSE can only catch exact duplicate `(op, operand-tuple)` nodes, and eqsat already caught every one of those. The sharing that is actually lost is cross-consumer: two different parents of the same associative op that each absorb a shared child's flattened operand list (`eqsat.rs:412-431`, the same-op absorption branch) rebuild that child's subtree independently once their own additional operands are folded into the sorted flat list, because the resulting sorted sequences almost never share a common prefix once interleaved with each parent's own unique leaves. Outer CSE, run once, structurally cannot recover a shared subexpression that was duplicated into two syntactically different trees. This is not a bug in the transform (value-preservation holds; I re-verified with an independent probe), it is a real instance of the well-documented e-graph *extraction* problem: choosing a representative per class (or, here, per rebuilt subtree) independently of the other classes does not, in general, minimize a DAG-shaped cost, only a tree-shaped one; this is exactly why the egg paper (Willsey et al., POPL 2021) treats DAG-cost extraction as a separate, harder problem from the tree-cost case the greedy extractor handles, and it recurs in every equality-saturation system that shares this shape. **Fix:** either (a) correct the doc comment to state plainly that CSE does not recover eqsat's lost sharing on this workload and that the win in `all` comes from fold+DCE, not from CSE+eqsat, or (b) if the real goal is to demonstrate recovery, make CSE re-entrant with eqsat (iterate flatten/hash-cons to a fixpoint, or hash-cons on the ORIGINAL node identity rather than the post-sort position) so the claim becomes true. As shipped, ship the corrected claim; do not ship the current comment as if it is a validated property.

3. **The empirical size data shows `eqsat` contributes nothing, and is measurably harmful, everywhere it was checked, which undercuts headline finding 6's framing rather than confirming it.** Extending the same probe to `cse+fold+dce` with and without `eqsat`: for `madd` and `tight` (the two profiles where the pipeline shows its largest win), the node count with `eqsat` included in `all` is bit-for-bit identical to `cse+fold+dce` without it (madd @ N=4096: 124 vs 124; @ N=16384: 345 vs 345; tight: 134 vs 134, 432 vs 432). For `real` (the profile RUN_SUMMARY says "there is nothing to fold and every level is a wash"), adding `eqsat` to the full pipeline makes it *slightly worse*, not neutral: 3602 nodes without `eqsat` vs 3625 with it @ N=4096 (14169 vs 14235 @ N=16384), a small but consistent and reproducible regression. So across every profile and size I checked, `eqsat`'s marginal contribution to the shipped `all` pipeline is exactly zero or negative; it never wins. RUN_SUMMARY finding 6 says "it only pays when paired with folding inside `all`," which reads as "eqsat is pulling weight in `all`." The data says the opposite: fold+DCE is doing all the work in `all`, `eqsat` is along for the ride, and standalone it is catastrophic (up to 142x). The correct, stronger conclusion for a canonical-design decision is not "ship the whole pipeline including eqsat"; it is "this benchmark gives no evidence eqsat should ship at all in its current form," which is a materially different design signal than the report currently states. **Fix:** state the finding as measured (no observed profile in this matrix in which eqsat's marginal contribution to the full pipeline is positive) rather than as "it pays off combined."

4. **DCE-alone and fold-alone are structural no-ops on this workload's DAG topology, which the report's per-strategy columns do not make clear, and a reader could easily misattribute the small deltas they do show to the passes' general strength or weakness.** The same probe: `dce` alone and `fold` alone both produce exactly the *same node count* as `none` (4096 for every profile at N=4096, verified directly). The reason is structural, not a bug: this generator produces a DAG where every node that has any consumer chain eventually terminates at some sink (a node with zero consumers, by definition of `sinks()`), so a node is dead under DCE if and only if it has no consumer chain at all, which essentially cannot happen for a node the generator actually created and wired into the program. DCE only has garbage to collect once `fold` has replaced a computed subtree's consumer-facing edge with a fresh CONST reference, orphaning the old subtree; that is why only the *combination* shrinks anything. The RUN_SUMMARY table nonetheless reports `fold` and `dce` as separately-timed columns with real, if small (2-17%), deltas from `none` (`carrier_optimize_madd`: `fold` 15.85x from base "all", `dce` 25.02x). Since node count is identical between `fold`/`dce`/`none`, those deltas cannot come from fewer nodes; they come from `fold` converting some node *kinds* to `CONST` in place (cheaper to interpret) while `dce`'s effect, being a genuine no-op here, is most likely measurement noise or a minor id-remap/locality artifact and should not be read as "DCE alone buys 3%." **Fix:** either report node-count-after-optimize alongside timing per cell (a one-line addition, the data is already computed in `prep`) so a reader can distinguish "fewer nodes" wins from "same nodes, cheaper op mix" wins, or explicitly caveat that fold/dce-alone columns on this generator measure op-mix effects, not their real shrink potential, which only shows up combined.

5. **The bench's own variant tag inverts the copy-and-patch terminology relative to the paper it credits, and `RUN_SUMMARY.md`'s prose inherits the inversion.** The file `copypatch.rs` contains the direct, per-node instruction-selecting codegen (`copypatch.rs:1-38` says so explicitly: "NOT the stencil-extraction mechanism of copy-and-patch... That mechanism lives in `stencil.rs`"), while `stencil.rs` contains the actual copy-and-patch mechanism (fixed `global_asm!` stencils, `memcpy` + hole-patching, no per-node instruction selection). The source-level doc comments are scrupulously careful about this distinction and cross-reference each other correctly. But `gen_matrix.rs:289-290` names the bench-visible variant tags `"copypatch"` (for the direct-codegen cell, `c::copypatch::JitCode`) and `"stencil"` (for the real copy-and-patch cell, `c::stencil::StencilCode`), so the tag a reader actually sees in `RUN_SUMMARY.md` and the raw CSVs calls the *non*-copy-and-patch technique "copypatch." `RUN_SUMMARY.md`'s finding 7 then says "the copy-and-patch JIT and the hand-written `global_asm` aarch64 stencil both hit 2.6 to 4.3x... the stencil occasionally edges copypatch," using "copy-and-patch JIT" to mean the variant tagged `copypatch`, i.e. the direct-codegen cell, the one technique the source code explicitly says is *not* copy-and-patch. A reader who takes the summary at face value walks away believing they have two measurements of copy-and-patch's cost when they actually have one measurement of copy-and-patch (`stencil`) and one of hand-rolled direct codegen (mislabeled `copypatch`) that the design explicitly built as copy-and-patch's *comparator*. This is a real terminology hazard for a canonical-design decision, because "copy-and-patch is cheap to maintain, ship it" (finding 7's conclusion, which I agree with on the data) is a claim about `stencil.rs`'s technique, not about the cell named `copypatch`. **Fix:** rename the `gen_matrix.rs` tags (`"copypatch"` -> `"direct"`, `"stencil"` -> `"copypatch"`, matching Xu & Kjolstad's own terminology) and correct RUN_SUMMARY's prose to say "the copy-and-patch stencil cell and the direct-codegen cell."

6. **Minor citation error, worth fixing since the whole point of citing the paper by name is precision.** `copypatch.rs:12` and `stencil.rs:3` cite "Xu and Kjolstad, PLDI 2021." Copy-and-patch compilation was published at OOPSLA 2021 (*Proc. ACM Program. Lang.* 5, OOPSLA), not PLDI. Low stakes, but a wrong venue on a paper cited specifically to ground a technique's provenance undercuts the "named real technique, not vibes" discipline the rest of the crate follows.

7. **The general, saturating e-graph engine that the module doc frames as answering "does a bounded rewrite window catch the reassociation explosion" is never wired into the bench matrix at all, and none of the six shipped generator profiles exercise a chain long enough to stress the bound that the production pass (`eqsat_reassociate`) actually uses.** `eqsat.rs:1-17` frames the whole file around reproducing the classic AC-reassociation explosion and showing a capped window catches it; that story is validated only by unit tests with hand-built synthetic chains (`k` in `{4, 8, 12, 24}`, `eqsat.rs:479-518`), never timed, never wired into `gen_matrix.rs`. The production path actually used by the `optimize` axis, `eqsat_reassociate`, is a different, simpler, non-saturating algorithm (flatten-sort-rebuild, `eqsat.rs:283-303`) that does not use the `EGraph`/`saturate`/`extract` machinery at all. Separately, I checked whether any of the six profiles' generated programs actually produce AC chains anywhere near the `EQSAT_WINDOW = 64` cap (`optimize.rs:82`): the observed node-count deltas for `eqsat` alone are modest (2-7%) everywhere except `madd`/`tight`, and that inflation comes from cross-consumer duplication (finding 2), not from hitting the cap on a single long chain. So the cap's own cost-bounding behavior, the reason `EQSAT_WINDOW` exists at all, is asserted correct by construction and validated in isolation, but never exercised or measured by anything a reader of `RUN_SUMMARY.md` would see. This is a scope gap, not a soundness bug: the module's most interesting claim (bounded beats unbounded on a real workload) is untested by the actual matrix.

## The optimizer + native soundness ledger

| cse | Yes, structural hash-consing, no semantic risk. | Same as fold. | Real, modest (~7-8% on madd/tight), consistent with a workload that has little literal operand-tuple repetition (the crate's own `interned_operands_gains_little_on_p_madd` test documents this directly). |
| dce | Yes, standard mark-and-sweep from live-outs (`optimize.rs:227-264`). | Same. | Not real alone on this generator (finding 4); only real in combination with fold. |
| eqsat (AC-reassociation) | Yes for THIS domain (wrapping integer add/mul are truly associative/commutative), but the value-preservation proof does not extend to any future float ops without an explicit reassoc gate. | Yes the transform's own cost is honestly excluded from algo_ns, but that cost is never reported anywhere (finding 1), and the transform's OWN output size can be 5x larger than input (finding 2/3), meaning `S` for eqsat-alone is plausibly the most expensive stage in the pipeline and nobody can currently tell. | Not real. Measured negative everywhere alone (up to 142x), measured zero-or-negative marginal contribution even inside `all` on every profile checked (finding 3). |
| cse+eqsat | Same soundness as eqsat. | Same gap as above. | Not real; empirically identical to eqsat alone (finding 2), contradicting the source comment's "recovers it" claim. |

| copypatch (direct codegen, mislabeled) | Yes, byte-checked against interp; correct condition codes and shift-masking. | Yes, codegen (instruction selection over every node) is a real, once-paid `S`, honestly excluded and structurally unavoidable for this technique (there is no way to amortize instruction selection away). | Real, ~2.6-4.3x, consistent across 6 profiles. |

| native_madd / native_ceiling | Yes, cross-checked against interp; the corrected (opaque, non-foldable) measurement is a legitimate fix of a real prior artifact. | Yes. | Real, ~1.5x for the O(N^2) throughput idiom; correctly and explicitly marked as not comparable to the per-execution native tier. |

## Novel angles the prior reviewers missed

1. **The eqsat non-recovery finding (Findings 2 and 3).** This required instrumenting `optimize()` directly to compare node counts across strategy combinations, not just reading the timing table; a reviewer working from `RUN_SUMMARY.md` and the raw CSVs alone would see `cseeqsat` and `eqsat` land at nearly the same wall-clock number and could plausibly read that as "yes, CSE recovered most of it, just not all," when the size data shows CSE recovered exactly nothing, in every profile checked. This is squarely an optimizer-soundness question (does the claimed transform interaction actually hold), not a microarchitecture-validity or interpreter-composition question, and it changes the design recommendation: the matrix as shipped is not evidence for shipping `eqsat`, it is evidence against shipping the AC-reassociation as currently implemented without either a genuine multi-pass fixpoint or a DAG-aware extraction.

2. **The copy-and-patch terminology inversion (Finding 5).** This is a codegen-technique-identity question specifically: which of the two JIT cells is actually the technique named in the paper the source cites, and does the report's own prose describe that cell correctly. It required cross-referencing the module doc comments in `copypatch.rs` and `stencil.rs` (which get it right) against the bench-visible tag names in `gen_matrix.rs` and the prose in `RUN_SUMMARY.md` (which invert it), a check that sits precisely in the "is the mechanism named correctly" territory of a codegen review and would not naturally surface from a benchmark-methodology or interpreter-composition audit.

## Open questions for the synthesiser

1. **Does the vehje canonical design treat "run the whole optimize pipeline" as a load-bearing recommendation, and if so, does it need eqsat at all given findings 2 and 3?** One path: drop AC-reassociation from the canonical pipeline until it is either made re-entrant with CSE or given a DAG-aware extraction; ship fold+CSE+DCE as the baseline optimizer, which this data actually supports unconditionally. The other path: keep eqsat in the design because it may pay off on IR shapes the six synthetic profiles do not cover (a real production program's arithmetic may have longer literal AC chains than any of `real`/`madd`/`tight`/`scatter`/`wideselect`/`leaf` produce), and treat this matrix as inconclusive-but-suggestive rather than as grounds to cut it. Both are defensible from the data; the tradeoff is "trust six synthetic profiles as representative" versus "keep an unproven-net-positive pass in the design on the chance real workloads differ."

2. **Is a follow-up bench run (timing `optimize()`/`eqsat_reassociate` itself, per Finding 1) worth doing before this matrix is treated as decision-grade for the optimizer axis, or is the qualitative direction (fold+DCE dominate, eqsat is unproven) already sufficient to lock the canonical design?** The tradeoff is measurement cost (another bench family, more wall-clock, another review cycle) against the risk of locking a design decision on a matrix that cannot currently answer "how expensive is the pass whose output we are running downstream."

3. **Should `stencil.rs`'s real advantage over `copypatch.rs`, namely compile-time cost (memcpy+patch vs. per-node instruction selection), be benched directly, given that the current matrix only measures the two techniques' *runtime* parity (which is the less interesting comparison; the paper's whole pitch is compile-time)?** This is a scope question (does the panel want a Finding-1-style follow-up for the native-codegen axis too) rather than a correctness question, and it interacts with question 2 (both would want the same kind of "time the pass itself" bench family added).
