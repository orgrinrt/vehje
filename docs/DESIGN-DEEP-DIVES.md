# Deepdive: certified generation and the two-artifact model

vehje's identity is the type system as the verification layer and certified
generation as the mechanism. This deepdive states the two-artifact model, what
certified generation actually certifies, and why the proof is compiled away
rather than carried.

## Two artifacts, and Rust entirely out of the runtimes

There are exactly two artifacts. The dev-time compiler is a Rust program that
compiles a language definition (a grammar, its families, its effects, its lease
rules, its targets), proves the language's disciplines sound, and emits validated
data (the family table, the effect masks, the lease-rule schema, the wire layout)
plus proofs carried in the structure of what it emits. It never sees a script and
never ships. The Rust crate ecosystem is this compiler.

The shipped artifact is a composed runtime written in Zig: one hand-authored
general engine (a parser, the analyzers, a macro expander, an interpreter, the
output targets) that the Zig compiler specialises at build time to the validated
data the Rust compiler emitted. It runs every program, whether bundled at build
or arriving at load, and it carries no Rust compiler and no LLVM at the consumer.

The crux precision, re-confirmed by the certified-generation sketch: the Rust
compiler emits data, not runtime source. The specialised runtime is produced from
that data by the Zig compiler's own comptime, which is the route chosen over
emitting foreign source because a metaprogram emitting foreign source is the
harder-to-certify path. The runtime internally has a compile stage and an execute
stage, two stages of one artifact, not two loci and not Rust. A host embedding
the runtime over the wire ABI may itself be written in Rust, but that host is a
consumer, not part of the runtime.

## What "certified" means, precisely

Certified generation means the language's typestate proves the composition sound
at language-compile time, and the proof is compiled into the structure of the
generated runtime rather than shipped as a checker. Concretely: illegal states
are unrepresentable in the generated engine, dispatch over the family set is
total, and the inclusion check folds to a constant mask comparison. The Rust
compiler typing its own generator and data is the first certification; the Zig
compiler typing the specialised engine is the second; both are at our build,
neither at the consumer.

The scope is stated honestly. "Certified" is partial evaluation plus per-instance
re-type-checking plus translation validation, not typed metaprogramming and not
verified compilation in the CompCert sense. It scopes to structural
well-formedness: the generated engine cannot represent an unhandled, unpermitted
operation, or a family it does not support, or a program whose effect set is not
included in a target's permitted set. Semantics are checked by a differential
harness (the grade-0 shadow of the assurance-indexed logical relation), not
proven. Termination is not claimed; there is a runtime budget, not a totality
axiom.

## The handoff and the manifest

The one place the story could leak is the handoff from the Rust-emitted data to
the specialised Zig runtime. It is closed by a content-addressed manifest
(`vehje-runtime-gen`): the manifest hashes each validated-data slice and the whole
package over the one structural-hash primitive, so the specialised runtime proves
at its own build that it was specialised from exactly this package. This is the
cheaper manifest-check interim of the full lens-projection handoff (both sides
generated projections of the one signature, differential-checked structurally),
which is the open handoff-staging question. The differential test over a census
corpus is defence in depth on the data handoff, not the primary assurance a
two-backend design would be forced to lean on, because the dual-locus split
dissolved to one comptime-specialised engine and one shared object is bit-identical
whether a Rust dev host or a C runtime host links it.

## Why compile the proof away

The runtime is a fast evaluator with no collector, no null, and no re-run of the
proof. Every static axis (family inclusion, effect inclusion, lease and region
validity, and assurance) is discharged before lowering and erased into the
structure of the residual and the generated engine, so the runtime inherits
proven-safe programs and re-runs nothing except the genuinely-unknowable-until-load
structural rejection of malformed input and the numeric and lease dynamic
residuals. This is what lets the type-system-as-verification identity coexist with
a runtime small and fast enough for the authoring and templating majority: the
verification is real and total, and none of it is present at the consumer.

# Deepdive: the output spectrum, from interpretation to transpilation

`vehje-codegen` turns a checked program into output. The question a first reading of that sentence
raises is what "output" means: does the crate interpret a program down to a value, or does it
transpile a program into another language's source text. The answer is that both are the same
operation aimed at different targets, and a target is a point on a spectrum rather than a member of
two disjoint categories. An interpretation target reduces everything to a value. A transpilation
target reduces nothing and re-expresses the program in another surface. Every real target, native
code, a game-configuration emitter, a document writer, sits somewhere between the two, and where it
sits is a staging choice made by the target's own implementation, not a fork in the framework's
contract.

This framing is not aesthetic. It decides what the framework has to build once and what a target
author has to build per target. If interpretation and transpilation were different operations, the
crate would need two contracts, two traversal engines, and two sets of proof obligations, and every
target would have to declare up front which side of the fork it lived on. Because they are one
operation, the crate needs one fold, one target contract, and one proof obligation, and a target's
position on the spectrum is an internal implementation detail the framework does not need to know
about.

A survey of how other systems solve the same problem settled the encoding this crate uses. Two
shapes recur across the literature: final encoding, where a term is generic over its interpreter and
adding a backend is free while adding a node kind breaks every backend, and initial encoding, where a
term is a concrete tree and adding a backend is free while adding a node kind edits every backend. No
production Rust compiler, not rustc, not rust-analyzer, not cranelift, ships final encoding as its
term representation, because Rust's lack of higher-kinded types and its forced per-instantiation
monomorphization strip away the ergonomics that make final encoding attractive in languages with
typeclass dictionaries. The mainstream resolution, and the one this crate follows, is a concrete
arena-held tree walked by ordinary generic functions: parse once into `vehje-ir`'s Core substrate, then
let a target close over that fixed representation rather than parameterizing the representation over
the target.

## Inclusion, not coverage

A closed-universe writer has to handle every constructor whether or not it can render it, and the
established resolution (seen in Pandoc's raw-content writers, which fall through to a warning on a
format they do not recognize) is a silent-drop contract: the writer degrades gracefully and the caller
finds out, if at all, from a log line. `vehje-codegen` takes the opposite contract. A target declares,
as a type-level set, exactly which families it supports and exactly which effects it permits, and a
program using anything outside those declared sets is refused outright, with the offending construct
named in the error. This is inclusion rather than coverage: a target is honest about a smaller
declared surface, and the framework enforces that honesty rather than hoping every target remembers to
guard every arm of a match. `Target` extends `vehje-ir`'s `TargetSets`, whose `Supports` and `Permits`
associated types are the type-level family and effect sets, built over the same `AccessSet` machinery
`hilavitkutin-api` already provides. Emission is bounded on the program's families being contained in
`Supports` and its effects contained in `Permits`, checked through `ContainsAll`.

## The Checked witness

The inclusion proof is not advisory. `emit` accepts only a `Checked<'_, T>`, and the only way to
produce one is to run the check for that target. The witness is minted in `vehje-check` because the
proof belongs with the prover, and `vehje-codegen` re-exports it because `emit` is where it is
consumed. `check_for` wraps the sanctioned mint: its `where` bounds, `T::Supports: ContainsAll<Families>`
and `T::Permits: ContainsAll<Effects>`, are the inclusion proof itself, derived from the target through
`TargetSets` rather than taken as free parameters a caller could fabricate. For a statically known
program the whole check discharges at compile time and costs nothing at runtime. For a program parsed
at runtime, the same proof runs as a bitmask comparison over family and effect ids, and the typestate
still makes the check unskippable: there is no code path that reaches `emit` without a `Checked`
value in hand, because nothing else in the crate can construct one. The obligation to check is
therefore not a convention a target author has to remember. It is a type the compiler refuses to let
you route around.

The one generic fold, `fold_core`, is the shared traversal every target folds over: a pre-order walk
over the Core substrate's twelve forms, invoking a target-supplied visit on each node before
recursing into its children. A family's own sub-structure attaches at `Raw`, reached through the same
fold rather than through a second traversal. A target never reimplements the walk; it supplies the
per-node emit logic and inherits the walk order, the same shape Racket's `render%` gives its mixins
and Pandoc's `Walkable` gives its writers, adapted to a monomorphised, no-alloc setting with no
trait-object dispatch anywhere in the framework layer.

## Proof-directed strategy selection

A target's emit logic still has to choose, per construct, how expensive a representation to produce:
interpret a value directly, lower to bytecode, or generate native code. The framework calls this
choice proof-directed strategy selection, and until an evidence-gathering effort measured it, the
choice rested on intuition borrowed from adjacent literature. The measurements, run through the bench
harness with every candidate compiled as its own isolated variant and cross-validated byte-exact
against an oracle, corrected that intuition on three points that now ground how a target's stencil
emitter and dispatch loop are built.

**The native ceiling is 1.0x to 1.5x over a good interpreter for scalar code, not a 10x keystone.**
Fairly measured, with the interpreter's data-dependent index kept non-vectorisable and the native
arithmetic kept opaque so the compiler cannot auto-vectorise the comparison to nothing, copy-and-patch
native buys roughly 1.0x to 1.2x across three representative regimes, and the wider composition study
puts the ceiling at up to about 1.5x. The interpreter's dispatch overhead is already small enough that
an out-of-order core hides most of it, so native code earns only a modest multiplier on scalar work.
The one regime where native wins by an order of magnitude needs auto-vectorisation, which a
copy-and-patch stencil cannot produce: a compiled path if-converts and vectorises where the stencil
emits a real, mispredicting branch, so the scalar stencil actually loses ground to a fully compiled
path as problem size grows. The honest reading is that the interpreter floor sits near native for
scalar code, and the transformative order-of-magnitude win belongs to a vectorising JIT aimed at the
rare consumer whose workload is genuinely compute-bound, not to the native tier in general.

**Plain switch dispatch wins for vehje's lean vocabulary.** The runtime design had imported tail-call
threading from the dynamic-language literature on the strength of reported wins over hand-written
assembly interpreters. The measurement does not carry over: across every tested case a plain switch is
fastest, with tail-call threading measured at roughly 1.7x slower. The reason is specific to vehje's
op vocabulary. Core is a flat, statically checked IR with roughly twenty-five primitives, small enough
that the switch's dispatch branch is well predicted and the extra machinery threading requires costs
more than it saves. Threading wins in the source literature only once an interpreter's op count runs
into the hundreds, which is not vehje's shape. A target's straight-line dispatch loop is therefore a
plain switch by default; tail-call threading is a measured-and-rejected alternative for this
vocabulary, kept off the critical path.

**The branch strategy is tier-dependent, and a target's stencil emitter must apply the tier-specific
map rather than a fixed shape.** Under interpretation, evaluating every arm of a branch unconditionally
is the worst strategy across the board, and the interpreter never does it. Under native code generation
the ranking can invert: for a cheap-arm, many-way, statistically unpredictable branch, a branchless
evaluate-all strategy wins by about 26% over a jump-table baseline, because it avoids the misprediction
the dispatch strategies pay for. For heavier arms or narrower branches, the one-arm dispatch strategies
tie or win outright, and evaluate-all loses. A stencil emitter that hardcodes one branch shape at scale
is not measuring a tier's ceiling honestly; it is measuring a strategy bug. The correct design grades
each region and selects the evaluator per grade, which is the actual content of proof-directed
strategy selection: the strategy is chosen by evidence about the region, not fixed once for the whole
program.

## Copy-and-patch as an opt-in accelerator

Given the ceiling above, copy-and-patch native code generation is positioned in the framework as an
opt-in accelerator a target may reach for, not as a dependency any target needs to function or as the
keystone that makes the framework fast. Its stencil emitter is the concrete site where the
tier-dependent branch map lives: the emitter selects branchless evaluate-all where the grade says a
cheap-arm, many-way branch dominates the region, and falls back to a single-arm dispatch elsewhere,
rather than emitting one shape everywhere and losing ground at scale. The mechanism itself, allocating
executable pages, writing a stencil, patching an immediate operand, toggling write-and-execute
protection, and invalidating the instruction cache, has been demonstrated feasible; what remains is the
stencil-extraction toolchain that turns a hand-written kernel into a patchable template, tracked as
deferred work rather than a blocker on the target contract this crate ships.

## Non-scope

`vehje-codegen` produces a `Checked` residual; it does not decide how that residual crosses to a
runtime, and it does not ship any concrete target. Every target, native code, a game-configuration
emitter, a document writer, lives in its own consumer repository with its own `Target` implementation
and its own choice of where on the interpretation-to-transpilation spectrum it sits. The framework's
obligation ends at the fold, the inclusion proof, and the compile-time composition that resolves a
target name to a monomorphised emit with no `dyn` dispatch anywhere in the call path.

# The Relational Engine: Whole-Column Fixpoint, Congruence, and Incremental Scaling

Three of the compiler's compile-stage jobs are the same computation wearing different schemas. The lease and
reachability inference grows a set of tuples to a fixpoint. The equality-saturation lowering grows a set of
equivalent forms to a fixpoint. The diagnostics witness reconstruction reads back the provenance of a derived
tuple. Rather than fork a bespoke fixpoint loop into each of those clients, this crate is one generic evaluator,
and each client defines its own relation schema over it. The engine names no IR type on purpose: it is a
mechanism, and a client is what couples a relation to the IR.

The engine is not the framework's runtime scheduler. The compiler does single-shot walks over a directed graph,
not morsel-driven frame execution, so this crate borrows the columnar storage contract and the bitmask algorithms
from the substrate and adds only the three things neither carries: fixpoint evaluation over a relation, congruence
closure for the e-graph client, and content-addressed incremental keying. Relations, e-class parents, and artifact
stores all live in caller-provided storage. The crate is `#![no_std]` with no allocation.

This document covers what the engine actually does and why it is shaped the way it is, grounded in the measurements
that settled each choice. The headline is that whole-column evaluation, the least clever of the available fixpoint
strategies, is the measured winner on the graphs the compiler actually sees, and the incremental layer answers the
one concern a growing stack of compiled artifacts raises: that load cost grows with the pile. It does not. Load
cost tracks the change, not the stack size.

## The relational core

A `Relation` is the schema a client implements for one relation: a tuple type (`Copy`, small, a columnar value)
and a bit slot that indexes the relation in the engine's 64-slot delta mask. A relation is a set of tuples the
engine grows to a fixpoint. Storage is the caller's: the client lends a `RelationSet`, a fixed-capacity column
with set semantics, whose `insert` returns true only when the tuple was newly added. That boolean is the whole
fixpoint signal. A round that inserts nothing new is the fixpoint.

A `Rule` reads body tuples and derives head tuples. The shipping shape is single-body: one body tuple derives at
most one head tuple, which is exactly the reach and transitive-closure shape the lease inference needs. `Engine`
is the evaluator. It holds an accumulated `Delta` and a round counter across evaluations, and drives every
relation a client defines. It terminates because the relations are finite-height lattices and the rules are
monotone: the set can only grow, it is bounded, so the loop halts.

The reachability lease fixpoint and the effect proof are the same bottom-up join over the graph, differing only in
payload. Both are bitmask propagation: the effect proof thermometer-encodes the grade so the lattice join is a
bitwise OR, the graded bind is the same OR, and the inclusion check is a subset test. The effect inference runs at
6.14 ns per node and the inclusion gate at 0.39 ns per node, so an 8M-node program discharges its effect proof in
about 3 ms. That the lease inference and the effect proof share one machinery, one DAG join, is why the engine is
generic rather than two hand-written passes.

## Whole-column evaluation, and why it beats semi-naive delta here

The obvious way to evaluate a monotone rule to a fixpoint is semi-naive: fire a rule only on the tuples that were
new in the previous round, so a round's work is proportional to that round's delta rather than to the whole
relation. It is the correct default for deep graphs, where the frontier is a small fraction of the accumulated set
and the per-round delta bookkeeping repays itself many times over. It is also more work to build: the engine has
to track, per relation, which tuples arrived when, and join only against those.

The graphs the compiler actually walks are shallow. The reach fixpoint over a realistic module graph closes in two
rounds. At two rounds, the delta bookkeeping never gets a chance to repay its own cost: whole-column evaluation,
which simply rescans the tuples present at the round's start and derives from each, wins outright. The measurement
is direct. The semi-naive reach fixpoint runs 8M nodes and 16M edges in about 50 ms, roughly 630 million edge-OR
operations per second, and whole-column OR beats delta semi-naive across that realistic shallow shape. So the
lease fixpoint ships whole-column, and the engine reserves the `Delta` type for the semi-naive path.

This is the crate's central discipline: ship the strategy the measurement selects, not the one the literature
flatters. Semi-naive delta evaluation is built where the bookkeeping repays itself, and whole-column is built
where it does not, which on the compiler's shallow graphs is the common case. The `evaluate` loop is the
whole-column strategy today. Its `FIXME` marks exactly where the semi-naive path and the provenance-semiring
grades attach, and the `Delta` type is already the change-set they will consume.

## Congruence closure for the e-graph client

Equality saturation needs one thing a plain relational engine does not carry: when two terms are proven equal,
their congruence closure (equal terms in equal positions are equal) must be maintained as the equalities arrive.
`Congruence` is that extension, a union-find over an e-class parent array the caller provides. It is stateless.
Every operation takes the caller's parent slice, so there is no allocation, and `find` uses iterative path halving,
pointing each visited node at its grandparent as it walks, flattening the tree over time with no second pass.

The closure is iterative, driven by a work-stack, never recursive. This is not a style preference. Recursion is a
hard wall on the runtime side: a recursive comptime kernel segfaults the compiler it targets at around 2500 depth
rather than reporting an error, and a recursive e-graph extractor hangs on the cycles congruence closure itself
creates. The same discipline that makes the comptime kernel a defunctionalized work-stack makes the closure and
the extractor work-stacks: iterative or it does not ship.

Congruence is what makes equality saturation safe to run at dev time. A proper e-graph saturated with
commutativity and distributivity grows a consistent 5.2x, linear rather than exponential, over four rounds
regardless of term depth, because hash-cons congruence deduplicates equivalent forms as fast as the rewrites
produce them. Linear growth is what validates equality saturation as a dev-time-only lowering, with a bounded
streaming window as the hard termination-and-memory safety mechanism. The `close` entry point unions a batch of
pending equalities today; its `FIXME` names the deferred half, re-deriving the congruence rule so a merge enqueues
the parents that may have become equal, which the equality-saturation client will need when it lands.

## The incremental scaling layer

A framework that compiles a growing stack of arriving artifacts invites one fear: that load time grows with the
stack, so a large project pays a large fixed tax on every build. The incremental layer is the answer, and it is
the same engine in differential mode plus content-addressed keying, a module here rather than a separate crate
because it is a mode of this engine, not a new mechanism.

The mechanism is a split of ownership. The framework owns the keying, the dedup, the differential recompute, and
the invalidation. The host owns the load policy and the storage backend, expressed as two traits: `Store`, the
host-lent backend keyed by content address, and `ArtifactSet`, the host-declared set of artifacts to maintain. No
I/O is baked in. Cross-artifact dedup keys shared subtrees by opaque content-hash values the client supplies (the
substrate content hash a client's structural hashing produces), so a shared subtree compiles once and a cache hit
is a proven-valid content-addressed artifact. The engine keys on content addresses and never inspects what
produced them, which is how its IR-free layering holds.

The measurements settle the load-bloat concern decisively. A 2000-module stack cold-loads in 4 ms. Editing one
module and warm-loading takes 0.003 ms: one recompile and 1999 cache hits. Load cost scales with the change, not
the stack size, which is the entire point. The cold load parallelises near-linearly, 7.7x at 8 threads on the
realistic wide-shallow override graph, with a 6.2 ms serial interner-merge tail that does not parallelise. The
warm incremental recompile is bimodal and statically knowable: about 1% of the stack recompiles for a typical
edit, up to about 40% for an edit to a foundational base module that most of the stack depends on. A reader
provisioning for the worst case sizes for the foundational-edit fraction; a reader estimating the common case
sizes for the 1%.

`warm_load` is the additive-edit case in the source: for each artifact, a store hit is reused as-is and a miss is
produced and stored and counted as one recompute. That is the case the 0.003 ms number measures. The general edit
with retraction is deferred (see below).

## What is deferred, and why

The engine ships the measured winners and marks the rest honestly, because a green benchmark on a strategy the
compiler never exercises would be worse than no benchmark.

Semi-naive delta evaluation is designed but not the default path. Whole-column is what ships as `evaluate`, because
on the compiler's shallow reach and effect graphs it is the measured winner and the delta bookkeeping does not
repay itself. Semi-naive attaches where a client's graph is deep enough that it does.

The full multi-relation worst-case-optimal join (leapfrog-triejoin with AGM bounds) is deferred. The shipping
single-body rule reads and writes one relation, which the reach and effect inference need and nothing more. A rich
multi-way rule set is what wants leapfrog-triejoin, and it lands when a client's rules need a multi-way join, not
before.

Differential retraction is deferred. The incremental layer ships the additive case: an edit adds and re-derives
its transitive dependents. General edit with retraction, a deletion that must un-derive everything that depended
on it, needs counted differential dataflow, which is real machinery and only pays off against an edit pattern that
deletes rather than rebuilds the affected set. It is deferred until a consumer's edit pattern actually retracts.

The through-line is that every deferral names its trigger. None is a permanent absence, and none is being skipped
to make a demo look fast. The reach and effect fixpoints run on whole-column because whole-column was measured
faster on their shape, and the harder general mechanisms wait behind a `FIXME` at the exact line they will attach,
so the client that first needs one finds the seam already cut.

# vehje-ir. Arena and Structural Hash Deep Dive

`vehje-ir` holds a program as a flat array of fixed-width nodes plus two
supporting side structures, all of them caller-provided memory. There is no
heap anywhere in this crate: the arena, the child-index pool, and the span
and grade tables are slices the driver allocates once and hands in, and
every construction operation is a bump append against a cursor. This
document covers how the twelve Core forms fit into one `Copy` slot each,
how the arena's child-index pool plays the same role as
`cranelift-entity`'s `EntityList`/`ListPool` pair, and how the structural
hash folds a subtree's content into one word without touching the heap or
crossing interner boundaries.

The arena's shape is not a stylistic choice. `vehje-ir` is the crate every
other framework crate depends on, so its per-node cost sets a floor under
everything built on top of it: the resolve walk, the check pass, the
lowering pipeline, and the interpreter's own node reads all pay whatever
the arena's layout costs. The record-layout question below, whether an
operand lives inline in the node or behind a pool index, and how many
operands fit inline before spilling, was measured rather than guessed, and
the measurement changed the design's answer more than once. That history is
part of what this document records, including a case where an earlier
result did not survive a later, more rigorous re-run.

## The no-alloc arena model

An `Arena<'a>` wraps three caller-provided regions and two bump cursors.
The node arena (`&mut [Node]`) holds one `Node` per slot, addressed by
`NodeRef`, a platform-width index newtype. The span side-table
(`&mut [Span]`) is parallel to the node arena, sized and indexed exactly
like it, so a diagnostic holding a `NodeRef` recovers its source location
through `arena.span(at)` without the node itself carrying a span inline.
The child-index pool (`&mut [NodeRef]`) is the third region, where every
form with variable-arity children (`Apply`'s arguments, `Match`'s arms,
`Handle`'s clauses, `Raw`'s payload) stores its child handles. A `NodeList`
is a `{ start, len }` pair into that pool, four bytes of index rather than
a per-node collection. This is the direct, hand-built equivalent of
`cranelift-entity`'s `EntityList<T>` paired with a `ListPool<T>`: instead of
every variadic node owning its own growable collection, which would mean
one allocation per node with children, every node needing a child list
holds a small handle into one shared pool, and the whole program's
variable-arity edges share that single backing region. The `GradeTable`
side-table `vehje-check` fills follows the same parallel-region discipline
as the span table: sized like the node arena, keyed by `NodeRef`, with
bounds-checked `get`/`set` so an undersized table surfaces as a diagnostic
rather than a crash.

Construction only ever appends. `Arena::push` writes a node and its span at
the current cursor and advances it, returning `Maybe::Isnt` if the region
is full rather than growing it; `Arena::alloc_list` copies a slice of refs
into the pool at the current pool cursor and returns the `NodeList`
handle, refusing rather than growing when the pool is exhausted. There is
no deallocation path inside the crate: the arena's lifetime is the
caller's, and it goes away in one release when the caller's region does.
Reads are plain indexed slice access; `list` clamps its returned range to
the live portion of the pool, so a malformed `NodeList` yields a truncated
or empty slice instead of reading past what has actually been written. The
`arena` module is kept free of vehje-specific policy on purpose, so it can
be lifted upstream into `hilavitkutin` (which owns the memory and storage
layer for the rest of the framework) once its shape has proven itself.

## The twelve Core forms as a fixed-width slot

`Node` is an enum over the twelve Core forms: `Lit`, `Var`, `Let`,
`Lambda`, `Apply`, `Project`, `If`, `Match`, `Iter`, `Interp`, `Raw`, and
`Handle`. Every variant is `Copy`, and the enum as a whole is one arena
slot: no variant owns heap memory, no variant carries a lifetime, and the
whole thing is sized once at compile time regardless of which form a given
node holds. A form's fixed-arity operands (`Let`'s `value` and `body`,
`Apply`'s `callee`, `Project`'s `base`) are inline `NodeRef` fields; its
variable-arity children go through a `NodeList` into the pool rather than
inflating the enum's size to accommodate the largest possible child count.
Names are `Str`, the interned handle from `hilavitkutin-str`, never a raw
string. `Raw` is the one typed escape hatch: a `FamilyId` plus a `NodeList`
payload, and it is how a consumer family's own node kinds attach to the
Core arena without the Core enum knowing they exist.

`Match` and `Handle` each carry a deferred payload on purpose rather than
by oversight. `Match`'s arms are a plain `NodeList` today; the pattern
representation pairing each arm with a scrutinee pattern lands with the
first consumer that actually matches. `Handle`'s clauses are similarly a
`NodeList` placeholder until the bounded multi-shot continuation encoding
is in place, at which point each clause needs an operation id, a
handler-body handle, and a resumption binder rather than a bare child ref.
Both mirror each other: the eventual shape is known in outline, but
committing to its exact encoding before a real consumer exercises it would
be guessing.

## The inline-operand question, and what the bench actually settled

The record-layout question that matters most for per-node cost is not
whether operands exist inline (they do) but how many operands a form can
hold inline before the rest spill into the child-index pool. Two format
questions sit under this crate's design, the exact node record width and
the exact inline-operand cutoff, and only one of them is settled.

Settled: pool indirection is the expensive path. A node whose operand is
reached through a pool index measured at 10.7 nanoseconds per node,
against 4.4 nanoseconds per node when the same operand lives inline in the
record, roughly two and a half times the cost, holding across the
call-fraction sweep the bench ran. The design's answer to "inline or
indexed" is therefore inline, without qualification: the child-index pool
exists for genuinely variable-arity children, not as a general indirection
mechanism for operands a form always has a fixed number of.

Not settled: the exact record width and inline-operand count. An earlier
measurement found a 24-byte record carrying three inline operands beating
a 16-byte record with two operands across every call fraction tested
(3.82 to 4.28 nanoseconds against 4.43 to 5.65 nanoseconds), attributed to
the wider record avoiding a pool spill on the hot binary-operation path,
with a corpus study backing three operands as the natural cutoff. That
result did not survive a later, more rigorous re-measurement through a
stricter per-variant isolation harness: on a sequential arena stream, the
wider record's density penalty and the narrower record's occasional spill
cost washed out against each other, and record width came back a null
result at scale. Because the later measurement is both newer and more
rigorous, it holds over the earlier one, so the exact inline-operand count
is an open measure-then-lock decision rather than a shipped 24-byte
commitment. The crate commits today to inline operands as a principle; a
specific width is locked once a corpus drawn from real consumers, rather
than a proxy corpus, exists to lock it against.

## Structural hashing: one definition, sound within one interner

`hash_of` computes a `StructuralHash` over an IR subtree by a post-order
fold: a node's hash mixes its own discriminant with the hashes of its
children, using an FNV-1a-style mix over 64-bit words. The fold also mixes
each node's leaf content: a `Var`'s interned name, a `Lit`'s tag and scalar
value, a `Project`'s key, a `Raw`'s family id. Folding leaf content is what
keeps structurally distinct subtrees from hashing to the same value;
without it, `Var(x)` and `Var(y)`, or `Int(1)` and `Int(2)`, would collide
on their shared discriminant alone. With leaf content folded in,
structurally equal subtrees hash equal and structurally distinct ones hash
distinct, the property hash-consing needs.

The one thing this hash is not is stable across interners. The leaf fold
for a `Var` or a string literal mixes the interned handle, a small integer
identifying a position in one particular interner's table, not the
string's actual bytes. That handle is stable for the lifetime of a single
compilation's interner, so two `Var` nodes naming the same identifier
within one compile hash identically, and the fold is sound for within
compilation hash-consing, its only current consumer. It is not sound
across two different interners or two different compiled artifacts,
because the same identifier can land at different handle values in two
separate interner instances, and the fold would then treat identical
source text as structurally distinct. Cross-artifact or cross-interner
identity is answered by a different mechanism: a byte-image hash computed
over the serialized wire form, interner-independent because it hashes the
actual bytes rather than a handle into a table. The two hashes solve
different problems and are not interchangeable.

`StructuralHash` is defined once in this crate rather than once per
consumer because three downstream mechanisms need the identical identity:
hash-consing during lowering, dedup keying in the incremental compilation
layer (which reads the underlying hash value directly rather than this
type, so that layer stays independent of `vehje-ir`), and the manifest a
later runtime-generation stage produces. Defining the fold separately in
each consumer would let identity drift out from under the
proof-preservation argument the incremental layer's soundness depends on;
one definition, read by three consumers, is what keeps that argument true.

# Deepdive: the two-stratum lowering design

Lowering sits between resolve/check and codegen: it rewrites the residual,
it does not discharge proofs and it does not emit target output. The crate
ships one stratum today, a bounded single bottom-up pass (constant folding
plus common-subexpression elimination, hash-consing over the IR's one
structural hash) that serves every build, including the load-time path a
runtime takes when a script arrives at runtime. A second stratum is
deferred: a dev-time equality-saturation e-graph, the flagged original
research the round set out to prove feasible. Both strata answer to the
same `Lower` entry through the `LowerStrategy` enum, so choosing one over
the other is a caller decision, not a shape change to anything downstream.

The design reads as conservative from the type signatures alone: a rewrite
side-table, a hash-cons table, a fixed rule set. This deepdive states why
each shape was chosen over the more obvious alternative, and what the bench
evidence settled versus merely sized.

## Redirecting rewrites instead of arena mutation

`ConstFold` and `Cse` never write to the node arena. They write to a
caller-lent `Rewrite`, a `NodeRef`-to-`NodeRef` remap sized to the arena and
filled with `Maybe::Isnt` on entry: a fold or a share records
`rw.redirect(from, to)`, and `Rewrite::resolve` follows the chain from any
node to its current representative, the lowered root being `root` resolved.
This exists because the arena is not the crate's to mutate. `vehje-ir` owns
its allocation discipline (a caller-provided region, no alloc, indices
assigned at build time), and a pass that inserted or removed nodes would
need write access a no-alloc, no-std crate does not have and should not
want. Redirecting sidesteps the problem: the arena stays exactly as a prior
pass built it, and lowering is a pure annotation layer over it.

`resolve`'s soundness rests on one invariant every redirect must uphold: it
always points to a strictly smaller arena index. `ConstFold`'s `If`-fold
redirects to the taken branch, which the `If` node contains and therefore
indexes lower; `Cse`'s share redirects the later-indexed duplicate to the
earlier-indexed original. Every redirect strictly decreases the index, so
the chain cannot cycle, and `Rewrite` is safe as a flat linear scan with no
cycle detection: the invariant is structural, not runtime-checked.

The cost is that a rewrite needing to create nodes cannot run through
`Rewrite` at all. A-normal-form hoisting is exactly that case: turning
`f(g(x), h(y))` into `Let` bindings plus an `Apply` needs new nodes the
side-table has nowhere to put, which is why `Anf` is a documented no-op
today. Redirecting an existing node and splicing in new ones are different
operations with different ownership requirements over the arena; `Anf`
lands behind a distinct mutable-arena rewrite path once one exists.

## Why CSE only shares variable-free subtrees

`Cse` hash-conses over `vehje_ir::StructuralHash`: a subtree hashing equal
to an earlier one is a candidate, confirmed by a full structural re-verify
(`structurally_equal`) before the redirect lands, so a hash collision can
never merge two subtrees that are not actually identical. The restriction
that makes this sound in this IR is narrower than plain hash-consing: only
a variable-free subtree (no `Var` node, no opaque `Raw` family payload) is
ever keyed. `cse_share` computes this bottom-up, returning whether each
subtree is variable-free; an unkeyed node's variable-free children still
key normally.

The reason is capture. Two occurrences of `Var("x")` are not
interchangeable the way two occurrences of the literal `7` are: each `Var`
resolves to whichever binder is in scope at its own position, and two
syntactically identical references can resolve to two different binders
under different `Let` or `Lambda` nodes. Sharing them would silently move a
reference to a different binder wherever the structural hash matched,
exactly the semantics a capturing substitution gets wrong. A literal means
the same thing wherever it appears, so sharing two equal literal subtrees
changes nothing. The test `cse_does_not_share_variables_avoiding_capture`
pins this: two `Var("x")` nodes under one `If`, neither redirects to the
other.

The restriction is conservative, not complete. A more capable CSE could
share alpha-equivalent bound subexpressions, the context-sensitive sharing a
binder-aware e-graph (the slotted and colored extensions named below) can
express safely. The cheap stratum shares only what is unconditionally safe
with no scope reasoning at all, the right tradeoff for a bounded single
pass running at load time.

## The node-count-reduction rationale

`Cse`'s doc comment states it plainly: its benefit is node-count reduction,
not per-op time. That is the measured result, not a hedge. A dedicated
bench of the cheap-lowering stratum found no time win from const-fold plus
CSE: an optimizing backend already performs its own CSE on the
recomputation a source-level pass would remove, so the hash-cons lookup is
overhead the backend absorbs regardless. What the bench found is a 76
percent reduction in node count on the corpus measured, and that is the
design-relevant result.

The cheap stratum runs at load time, on every arriving script, where what
matters is the size of what gets loaded and kept resident, not execution
speed an interpreter and a native tier already carry most of. A smaller
node count is a smaller arena, a smaller artifact to serialize across the
runtime C ABI, and less working set for every later pass. A time-flat bench
on this workload is not a failure: it measured the wrong axis for what the
pass is for, and recording that honestly keeps a future reader from
re-deriving a false time-savings claim from the crate's name.

## The deferred stratum: dev-time equality saturation

`LowerStrategy::Saturate` names a no-alloc, bounded, streaming
equality-saturation e-graph: union-find over e-classes, hash-cons congruence
closure, a rewrite set applied to a fixpoint rather than one bottom-up
pass, and cost-based extraction picking the best representative out of
each saturated class. Where the cheap stratum applies a fixed small rule
set once, saturation can apply an open rule set repeatedly, discovering
equivalences a single pass cannot (a fold rule only applicable after a
commute has already fired, for instance).

Two feasibility questions gated whether this stratum belongs in the design.
The first is growth: unbounded saturation can in principle blow up
combinatorially, since every rewrite adds equivalences without removing the
original form. A sketch saturated a small expression against fold and
commutativity or distributivity rules and measured a consistent 5.2x growth
factor across four rounds, independent of program depth, not exponential.
Hash-cons congruence is why: an e-node reducing to a form already present
in some class merges into that class instead of growing the graph, so size
tracks distinct reachable forms, not rewrite applications. That bound is
what makes saturation viable as a dev-time stratum with a bounded-capacity
arena rather than a research curiosity needing an arbitrary depth cutoff.

The second question is extraction, and it fails less gracefully: it hangs.
Once an e-graph has undergone merges, its classes can contain cycles, an
e-node in class A referencing class B whose canonical e-node references
back into A, because congruence closure merges classes for reasons
unrelated to the source tree's original acyclic structure. A recursive
"cost of this class is the minimum over its e-nodes of one plus child cost"
walk either loops forever on that cycle or explores exponentially under a
naive depth guard, and the feasibility sketch found exactly that: a
recursive extractor over a saturated graph did not return. The fix, and the
shape the deferred stratum commits to, is the standard egg-style
resolution: extraction is an iterative cost fixpoint over a work-stack, not
a recursive walk. Each class's cost iterates toward a minimum across every
class until nothing changes, and a cyclic e-node can never win that
minimization, because following the cycle only adds cost, never subtracts
it. The iteration is cycle-safe by construction and terminates in a small,
bounded number of passes.

A second, independent finding reinforces this: the comptime specialization
kernel on the runtime side of this framework hits the same wall, the host
compiler's own comptime evaluator segfaulting rather than erroring cleanly
at roughly 2500 levels of recursive evaluation. Unrelated to e-graphs, it
generalizes the same lesson: any pass whose recursive shape can grow
unboundedly with program size fails catastrophically, not slowly, unless it
is rewritten as an iterative fixpoint over an explicit work-stack. The
deferred stratum's extractor inherits this as a design constraint: its cost
computation and its representative-selection walk are both iterative
work-stacks.

## What ships and what does not

The cheap stratum's four pieces run in order under `LowerStrategy::Cheap`:
`MacroExpand`, `ConstFold`, `Cse`, `Anf`. `ConstFold` and `Cse` are real.
`ConstFold`'s only fold today is an `If` whose condition resolves to a
literal boolean, redirected to its taken branch; folding a primitive
operation over literal operands waits on the family payload encoding that
would let the pass read a `Raw` node's operation and operands generically.

`Anf` and `MacroExpand` are both no-ops today, for the same reason: each
needs to create nodes the redirecting `Rewrite` cannot create. A-normal
form hoists intermediates into fresh `Let` bindings; macro expansion
splices an expansion in place of a call, re-rooted with its own fresh
bindings even when the macro body already exists elsewhere in the arena.
Both land once the mutable-arena rewrite path exists. `Lower::lower` calls
them unconditionally and both currently return without touching `rw`:
there is nothing sound for either to do yet, and an unconditional no-op is
honest where a partial implementation would silently fail to normalize or
expand anything.

`LowerStrategy::Saturate` is reserved and falls through to `Cheap`. Nothing
about `Lower`'s public shape changes when saturation lands: the strategy
enum already names it and the entry already dispatches on it, so a caller
requesting `Saturate` today gets the cheap subset rather than an error, the
additive shape the two-stratum design exists to guarantee.

## `RuleTable` as the shared definition between compiler and runtime

`RuleTable` is the crate's one piece of validated data rather than pure
logic: a small struct of feature flags naming the cheap subset's active
rule set, defaulted on by `RuleTable::cheap()`. It exists as data because
the same table is what a runtime-generation crate packages for a runtime's
own load-time lowering of arriving scripts: the Rust crate is the
definition of the rule set, and the runtime side is a specialized execution
of that same definition, not an independent reimplementation that could
drift from it.

# vehje-resolve. Scope Chain Deep Dive

`vehje-resolve` answers one question for every `Var` node in a program:
which binder introduced it. The answer comes from a scope chain, and the
chain's shape is the whole design decision this document covers. A scope
frame in this crate is not an entry in an owned table that the walk builds
up and tears down; it is a value that lives on the resolve walk's own call
stack for exactly as long as the binder it represents is in scope, and it
reaches its enclosing scope by a plain reference rather than an index into
storage. No scope table is ever allocated, because the call stack already
is one.

This matters because `vehje-resolve` runs on every `Var` reference in every
program the framework compiles, and it runs before the check and lowering
passes, both of which depend on its output. A resolve pass that allocated a
scope table per call, or grew an owned vector of frames as it descended
into nested binders, would pay that cost on the framework's hottest
compile-time path. The borrowed chain avoids the cost entirely rather than
amortizing it, and the difference is measured, not assumed: resolving one
reference against the chain costs about 0.91 nanoseconds, several times
faster than walking an equivalent owned scope table. This document explains
the chain's shape, the recursive-binding rule that governs `Let`, the
`Resolution` side-table the later passes read, and where a consumer
family's own binding forms hook into the walk.

## The borrowed, non-allocating scope chain

`Scope<'p>` is a single binding frame: the name it binds, the `NodeRef` of
the node that introduced the binding, and a reference to its parent frame,
or nothing at the root. A chain of these is a stack of frames threaded by
reference, and each frame's lifetime is tied to the recursive call that
created it. `walk` (the core recursive descent over the arena) takes its
current scope as `Maybe<&Scope<'_>>`, a borrowed pointer rather than an
owned value, and every place the walk descends into a binder's body it
constructs a new local `Scope` on its own stack frame and passes a
reference to it down into the recursive call. When that call returns, the
frame's storage is simply the stack frame unwinding; there is nothing to
free because nothing was allocated in the first place.

`Scope::resolve` walks the chain outward from the innermost frame, checking
each frame's name against the target and following `parent` on a miss until
it either finds a match or runs out of chain. Because the chain is exactly
as deep as the current binder nesting, and no deeper, the walk's cost is
proportional to how far out the matching binder actually sits, the same
complexity an owned table lookup by scan would have, but without ever
materializing the table. The `frame_for` helper is the one place a new
frame gets constructed, called at each `Let` and `Lambda` site with the
current scope as parent, so a root frame (`Scope::root`) and a chained
frame (`Scope::child`) share one construction path from the walk's point of
view.

## Why this beats a scope-chain walk over an owned table

An owned scope table, a vector or map of active bindings that the walk
pushes onto entering a binder and pops on leaving it, is the obvious
alternative, and it works. The cost it pays that the borrowed chain does
not is bookkeeping: every push is a write into growable or pre-sized
storage, every pop is an explicit removal, and the table itself is a
resource the walk owns and must maintain correctly across every recursive
path, including early returns on a resolve error. The borrowed chain has
none of this to get wrong, because the "table" is just the sequence of
stack frames the recursion already creates and destroys as a side effect of
being a recursive function. The measured gap between the two shapes is not
marginal: the borrowed chain resolves a reference in about 0.91 nanoseconds
against several nanoseconds for the owned-table walk, a factor of roughly
six to fourteen times depending on chain depth and table shape, because the
borrowed chain has zero write-side cost and the owned table always has
some.

The same shape generalizes past name resolution. A flat, borrowed,
reference-chained frame is the right answer whenever a pass needs
scoped, LIFO-lifetime state during a tree walk and does not need that
state to outlive the walk or be queried from outside it. `vehje-resolve`
is the first crate to need this shape and the reference implementation
other Core-level passes reach for when they need the same pattern.

## The recursive-`Let` rule

A `Let { rec, name, value, body }` node's `rec` flag decides whether the
bound name is visible while resolving its own `value`. When `rec` is set, a
`let rec f = ... f ... in ...` construct can have its value reference `f`
itself, which is what makes recursive definitions resolvable at all: the
walk builds the frame for `name` before descending into `value`, so `value`
sees its own binder in scope. When `rec` is not set, the walk resolves
`value` against the scope that existed before the `Let`, so a `let f = f in
...` where the right-hand `f` is meant to reference an outer binding (or
nothing, if there is no outer binding) does not see the new frame; only
`body` does. The rule is one branch in `walk` and its recording twin
`walk_record` (`let value_scope = if rec.0 { Maybe::Is(&frame) } else {
scope };`), applied identically in both, and it is the entire mechanism
behind the difference between a self-referential binding resolving and an
accidentally-shadowed one failing to resolve. The test suite pins both
directions: a `rec` binding whose value references itself resolves, and
the same shape with `rec` unset does not, because without the flag the
right-hand `f` has nothing bound yet to resolve against.

## The `Resolution` side-table

`resolve` answers only whether a program's names all resolve; it produces
no record of which `Var` resolved to which binder. `resolve_into` is the
same walk over a variant, `walk_record`, that additionally writes into a
`Resolution<'a>`, a side-table wrapping a caller-provided
`&'a mut [Maybe<NodeRef>]` region sized like the node arena, exactly the
same parallel-region discipline the span and grade tables in `vehje-ir`
use. Every entry starts unresolved; each time `walk_record` resolves a
`Var`, it records the binder's `NodeRef` at the `Var`'s own arena index
through `Resolution::record`. The check and lowering passes read this
table by index (`Resolution::binder`) rather than re-walking the scope
chain themselves, so the resolve pass's work is paid exactly once per
program regardless of how many later passes need to know a variable's
binder. This is the same reasoning that puts `GradeTable` and the span
table in `vehje-ir` itself: a fact computed once about a `NodeRef` belongs
in a side-table keyed by that ref, not recomputed by every consumer.

## The family-extension resolve seam

`Raw` nodes, the escape hatch through which a consumer family's own
constructs attach to the Core arena, are opaque to both `walk` and
`walk_record` today: a family node introduces no Core-level scope frame and
is treated as a leaf for resolution purposes. This is a placeholder for a
real extension seam, not the finished design. A consumer family may define
its own binding forms (a pattern-matching construct with its own bound
names, a comprehension with a loop variable, anything the Core's `Let`,
`Lambda`, `Iter`, and `Handle` binders do not already cover), and those
forms need to extend the scope chain the same way Core's own binders do,
without the Core resolve pass needing to know the family's node kinds in
advance. The mechanism composes with the family-set typestate the rest of
the framework already uses: a family declares a resolve hook, the walk
dispatches to it when it encounters that family's `Raw` payload, and the
hook gets the current `Scope` chain to extend and hands back into the Core
walk for the sub-expressions it does not own itself. Until a real consumer
family exists to exercise the shape, the seam stays a documented gap rather
than a speculative interface, so the first extension is designed against an
actual need rather than a guess.

# Deepdive: value transport and the batched-column ABI

A produced value crosses from the runtime back to the host through a
value-arena and a reserve-then-commit sink, and the host-to-runtime interface
takes a column of records per call. This deepdive states the transport shape,
why it is one protocol for two boundaries, and the bench evidence that settled
the batched-column entry.

## The value-arena and the one-shot coroutine

The value is a value-arena: fixed-width value-node records, a flat child-index
pool, a self-contained byte blob, and relative index links, the same structural
family as the residual wire form, reused for produced values rather than IR. It
is closed and versioned (the framework owns producer and reader, so there are no
vtables), and evaluation-orthogonal (a native strategy emits the same
value-arena the interpreter does). The value serialises depth-first, children-before-parents, so
a parent records already-emitted child indices with no back-patching; a typed
structural decode over an untrusted arena is then linear and acyclic by
construction (child-before-parent makes acyclicity a single monotone index
check), which is what makes the untrusted-load path safe and fast.

The streaming producer is a defunctionalised one-shot coroutine whose suspended
frames are the chunks: each chunk is a self-contained mini value-arena, a parent
refers to an already-emitted child by chunk and index, and frontier boundedness
is the linearity of the continuation, which proves the cross-chunk lemma and the
oversized-subtree property as one linearity statement. This is the same
bounded-frontier one-shot-coroutine abstraction the compile-stage streaming uses,
so the frontier bound, the depth-cap sizing, and the acyclicity argument are
proven once and used at both ends. Region structure rides the arena: each value
node carries a region id through a region-table indirection, and region open and
close markers free a region's segment on stack discipline, no collector.

## Wire layout and the untrusted path

The zero-copy read the "wire form equals in-process form" claim depends on rests
on a declared, stable layout: the value-node records (`ValueNode` and the
`ValueList`, `BlobSpan`, `Region`, and `ValueTag` it composes) carry an explicit
`#[repr(C)]` layout, and `ValueTag` a stable declared `#[repr(C)]` discriminant
(the C-ABI default width; narrowing to a compact fixed width is part of the open
wire-spec decision below), so the
runtime reads a record at a fixed offset rather than at whatever offset the
default Rust representation happens to pick. The `ValueRef` and `RegionId` index
newtypes are `#[repr(transparent)]`. `ValueArena` itself is the in-process view
(it holds Rust slices over the lent backing), not a crossed wire type.

The untrusted-load safety has two halves, and only one has landed. The
child-before-parent order makes acyclicity a single monotone index check (the
structural half, in place). The bounds half is that every index read is checked:
`ValueArena::try_get` returns `Maybe<ValueNode>` for the untrusted path, and the
child accessor is clamped to the live pool, so a malformed arena yields a
`Maybe`/empty slice rather than a panic. The full validation pass
(`Reader::validate`) and a typestate that makes an unvalidated arena unreadable
through the safe path are the frontier: they are FIXME'd and tracked, because the
out-of-process residual story they belong to is not yet built. `get` stays the
trusted-path accessor, valid only after validation; `try_get` is the interim safe
option.

Two wire-spec details are deliberately still open (flagged for op, not decided
here): the exact `ValueTag` discriminant width, and the per-record byte layout at
the batched column entry's `BatchColumn.records` (the descriptor is specified;
the per-record shape the host fills is owed). Whether the wire form is host-native
(same architecture both sides, so the `USize` platform-width fields are fine) or a
cross-platform serialized form (which would need fixed-width fields) is the same
open question.

## One sink, two boundaries

The transfer contract is reserve-then-commit, an iteratee, a host-lent
object-capability whose backpressure is inherent. In-process it is a
`#[repr(C)]` struct of two function pointers plus opaque userdata; out-of-process
it is the executable's stdout pipe, where the OS pipe buffer is the
backpressure. Whole-value mode is the degenerate single-reserve case. The
backing memory is host-lent up front, so the runtime holds no output memory
after a call, which is what the no-alloc discipline forces and what makes the
wire form equal to the in-process form.

## The batched-column entry, and the bench evidence

vehje's real workload is per-record column evaluation: one residual over a
column of many records. The biggest measured throughput lever is vertical SIMD
interpretation (up to about 4.8x on a symmetric baseline), which needs the
boundary to take a column of W records per call so the runtime can vectorise
across them. So the decision is to expose one runtime-W batched column entry
taking W at least two.

The bench arc settled the shape and, importantly, its justification. The crossing
itself is nearly free (about 9 ns warm), which kills two tempting but wrong
designs: it kills "FFI is expensive, so the ABI must batch to amortise the
crossing" (the crossing is negligible against any interpret payload), and it
kills "the ABI must ship per-W monomorphised symbols" (a runtime-W entry with an
internal loop pays essentially nothing over the monomorphised forms at this
crossing cost). So the batched entry is justified by the vectorisation it enables
(the SoA win survives the object boundary byte-exact, 2.3x to 4.1x across residual
sizes), not by crossing cost, at every interpret tier. Crossing amortisation
becomes a live term only at the native and copy-and-patch strategy, where the payload
is cheap enough (a tiny native kernel amortises the crossing about 3x from W=1 to
W=256, and under realistic call-target misprediction the per-record crossing is
about 6x its warm cost), so the batched entry is justified there for the
complementary reason. Either way the runtime, not the ABI, owns the SIMD width.

The return contract follows from this: fallibility is a value property (an
`Outcome`-shaped value in the value-arena where a record fails), batch completion
is a stream property on the sink, and the SoA lane mask is an internal
mask-and-continue mechanism, so there is no separate status vector crossing the
boundary. Raw bench data lives in the bench history; the full-arc findings topic
is the durable record.

# Deepdive: dispatch over the wire ABI, and decoding what crosses back

`vehje-runtime-driver` sits on the compiler side of the C ABI boundary. It takes a `Checked` residual
produced by `vehje-codegen`, serializes it through `vehje-runtime-abi`'s wire form, hands it to the
embedded runtime, and reads back whatever the runtime produces. The crate's two halves, `dispatch` on
the way out and `Reader` on the way back, exist because crossing a C ABI boundary is a trust boundary
in both directions: the runtime must be handed a residual it can execute without re-deriving proofs the
compiler already discharged, and the compiler must treat whatever comes back as untrusted bytes until a
decode pass says otherwise.

This deepdive covers the dispatch entry and its tier tag, the safe reader and the validation pass that
makes an untrusted value-arena safe to read, the split between a trusted in-process path and an
untrusted path that must run the full decode, and how the runtime artifact itself gets linked into a
consuming binary. It closes with the batched-column entry, because the shape of `dispatch`'s payload
and the shape of the entry the bench arc settled on are the same question asked from opposite sides of
the boundary.

## Dispatch and the tier tag

`dispatch` hands a `Residual<'_>` to the runtime and maps whatever comes back into `vehje-ir`
diagnostics. The residual crosses tagged with a `Tier`: `Arena`, the flat serialized IR arena and the
reference semantics every other tier is checked against, or `Bytecode`, an optimized linear form whose
encoder is not yet built. The tier tag is narrower than it might look. It names only the internal
execution form the runtime chooses between, interpret the arena directly or run lowered bytecode; it is
not a native-versus-managed axis, and native code is not a third tier value here. Native is a
method-agnostic point on the output spectrum `vehje-codegen` already covers, selected per region where
a grade proves it wins, not a tag threaded through the wire ABI. Keeping native out of the tier
enumeration keeps the wire contract honest about what it actually decides: which serialized form the
runtime is holding, not which code path eventually executes it.

The current `dispatch` surface establishes the entry point and its error shape; the serialization
through the tier tag, the actual call into the linked or dlopen'd runtime, and the mapping from wire
diagnostics back to `vehje-ir::Diagnostic` are the next behavior gate on top of it. `DriverError` names
the three ways a dispatch can fail: the runtime rejects the residual outright, the residual cannot be
serialized at the requested tier, or a value that crosses back fails the structural decode below.

## The safe Reader and the untrusted-load contract

Whatever the runtime hands back arrives as a `vehje-runtime-abi::ValueArena`, the same structural
family as the residual wire form: fixed-width node records, a flat child-index pool, a self-contained
byte blob, and relative index links, serialized children-before-parents with no back-patching. `Reader`
is the driver's safe, bounds-checked view over that arena, the in-process consumer's counterpart to the
producer's reserve-then-commit sink on the way out. Wrapping an arena in a `Reader` costs nothing by
itself; the safety comes from `Reader::validate`, which a caller runs once before trusting any read
through the arena.

## The typed structural decode

`validate` is one linear forward pass over the node records, and every check in it is a bounds check
against a table the arena itself carries. For the root, it checks the root index is within the node
count. For each region-table entry, it checks the region's start-plus-length span lies within the node
count, using saturating arithmetic so a maliciously large length cannot wrap the check around instead of
failing it. Then, walking every node in order, it checks three things: the node's region id names a
real region-table slot, the node's blob span lies within the shared byte blob, and the node's child span
lies within the shared child-index pool. All three are bounds checks with the same saturating-arithmetic
discipline, so a corrupt span reports as out of range rather than overflowing into a false pass.

The check that makes the whole pass an acyclicity proof, not just a bounds proof, is the last one: every
child index a node names must be strictly below that node's own index. This is only a meaningful
invariant because of how the arena is emitted. The value-arena's producer, whether an interpreter
computing a value directly or a native strategy computing the same value through a different execution
path, always writes children before their parents, so a well-formed arena's child indices are, by
construction, monotone: strictly decreasing as you walk from any node back toward its children. A
decode pass that enforces the same monotonicity on the way in is therefore checking the one property
that both proves every child reference is already-defined data and rules out a cycle in the same
comparison. There is no separate graph-traversal cycle check anywhere in `validate`; the ordering
invariant the producer already guarantees turns cycle detection into an index comparison the linear scan
was already doing for bounds. A value-arena that passes `validate` has no forward reference and
therefore no cycle, which is what lets a later read walk the structure without a visited-set, a
recursion-depth guard, or any risk of looping on adversarial input.

## Trusted versus untrusted

The distinction the crate draws between a trusted and an untrusted path is about who produced the
arena and what they are allowed to assume as a result. The in-process trusted path, a native strategy
or an interpreter running inside the same process as the reader, may skip `validate` entirely and read
directly through the arena's `get` accessor, because the producer and the consumer share the same
invariants by construction and there is no adversarial gap between them. Any path where the value-arena
crossed a real trust boundary, most concretely the out-of-process residual story where a separately
built runtime artifact hands bytes back to the host, must run `validate` before a single read, and the
safe accessor for that path clamps every index to the live pool rather than trusting it. The framework
does not have a third option that skips validation and hopes; the typestate is built so an unvalidated
arena is unreadable through the safe path, and the choice to skip validation is available only to the
one caller who can prove, by construction rather than by inspection, that skipping is sound.

## Runtime artifact embedding

`vehje-runtime-driver` is the one framework crate with a `std` role, and the reason is entirely this
embedding. The Zig runtime is a separate build artifact, not a crate this repository compiles, and the
driver links it one of two ways depending on which side of the compiler-versus-embedded-host line the
consumer sits on. For the compiler layer, the runtime links statically into the single binary the
framework's distribution model ships, so the compiler-side dispatch and the runtime execution end up in
one process image with no dynamic loading step at all. Behind the `std` feature, an embedding host may
instead dlopen the runtime artifact at runtime, the one place in the framework where dynamic loading is
sanctioned, because the exemption cuts along the compiler-versus-runtime seam rather than being a
general escape hatch. If more than one runtime backend ever exists, they compose the same way every
other extension point in the framework composes: at compile time, through a generated match resolving a
name to a linked implementation, never through a `dyn` registry or a shared-object plugin host at the
compiler layer.

## The batched-column entry

The shape `dispatch` eventually serializes into is not a single record. vehje's real workload is
column evaluation, one residual run over many records, and the biggest measured throughput lever, up to
roughly 4.8x on a symmetric baseline, is vertical SIMD interpretation across a resident column, which
only pays off if the boundary hands the runtime a column rather than one record at a time. A rebuilt,
adversarially reviewed bench arc settled the shape and, more importantly, its justification, after an
earlier read had overstated both. The crossing itself is nearly free, about 9 ns warm, and that single
number rules out two designs that felt intuitive going in: it rules out batching purely to amortize a
supposedly expensive crossing, because the crossing is negligible against any interpret-tier payload
including the cheapest one measured, and it rules out shipping a family of per-width monomorphised
symbols, because a single runtime-W entry with an internal loop costs essentially nothing extra over a
monomorphised form at this crossing cost. So the batched-column entry earns its place for a different
reason at each tier: at the interpretation tiers, it exists because the SoA vectorisation win survives
the object boundary byte-exact, measured between 2.3x and 4.1x across residual sizes; at the native and
copy-and-patch tier, where the payload per record can be cheap enough that crossing cost is no longer
negligible, the same batched entry additionally amortizes the crossing itself, observed at roughly 3x
for a tiny native kernel run column-wise instead of record-by-record. Either justification lands on the
same conclusion: the ABI exposes one runtime-W batched entry taking W of at least two, with the runtime,
not the ABI, owning the SIMD width, and no separate amortization mechanism layered on top.

# vehje-runtime-gen: the validated-data package and its manifest

The framework's compile side proves things about a language once, at the language author's build, so the
runtime never has to prove them again at every script load. That proof does not cross into the Zig runtime as
more code to interpret; it crosses as data. `vehje-runtime-gen` is the crate that builds that data: it takes
a checked language definition and everything the compile stages derived from it, and compiles the whole thing
down into one validated-data package the Zig runtime's comptime specialisation reads while it builds itself.
Nothing in the package is executed by the runtime as instructions; all of it is read as values the runtime's
own build step consumes to specialise a hand-authored engine into a language-specific one.

This document covers the package's shape, the typed slice handles that let the package compose contributions
from several stage crates without knowing their internal formats, and the content-addressed manifest that
lets the specialised runtime prove, at its own build, that it was specialised from exactly the package it
claims to have been.

## Data, not source

The distinction between the package and ordinary generated source code is the crate's whole reason for
existing. A generator that emitted Zig source text naming every family, every effect, every lease rule as
control flow would be shipping a second compiler written in a template language, one copy per consumer
language, each one only as trustworthy as its own generation logic. The package instead is inert data: a
family table, effect masks, a lease-rule schema, binding-time defaults, a cheap-lowering rule table, a wire
layout, and a reserved stencil section. The Zig runtime's comptime evaluation reads that data at its own
build and specialises one shared, hand-authored engine against it. Illegal families become unrepresentable in
the specialised type system rather than merely unreachable in generated branches; there is one engine to
audit, not one generated engine per language.

This is also why the package composes rather than being written whole by this crate. Each data slice belongs
to whichever stage crate already owns the computation that produces it: the family table comes from
`vehje-ir` and `vehje-signature`, the effect masks and the lease-rule schema come from `vehje-check`, the
cheap-lowering rule table comes from `vehje-lower`, and the wire layout comes from `vehje-runtime-abi`.
`vehje-runtime-gen` defines none of these formats itself. Its discipline is composition: one definition per
mechanism, owned by the crate that already has to get that mechanism right for its own purposes, and one
aggregation point that binds the results together into a single package per language. A stage crate changing
its slice's internal format does not ripple through this crate, because this crate never inspects the
contents of a slice it did not produce.

## Slices and the package

`Slice` is the typed handle to one stage crate's contribution. It is what makes the composition rule
mechanical rather than aspirational: the package holds a set of slices, addresses each by its `SliceKind`
tag, and never has to know what is inside one to place it correctly or to hash it. `SliceKind` names which
validated-data section a given slice carries, the family table, the effect masks, the lease-rule schema, and
so on, so the package can compose and address its slices by kind without the composing code branching on
per-language content.

`Package` is the composed artifact: every slice a language's compile produced, brought together into the one
thing the Zig runtime's comptime specialisation reads. The reserved stencil section is part of the package's
shape from day one even though nothing produces it yet; the copy-and-patch stencil-extraction toolchain that
will eventually fill it is a separate, deferred piece of work, but the schema slot exists now so a future
producer has a stable place to write into rather than requiring a package-format break when it lands.

## The manifest, and why it exists

A package is only useful to the runtime if the runtime can trust that the specialised engine it built at its
own compile time actually came from that exact package, and not from a stale copy, a hand-edited one, or one
that silently drifted between the language author's build and the point where the runtime embeds it. The
`Manifest` is the mechanism that closes that gap: a content-addressed hash, built over `vehje-ir`'s one
structural-hash primitive, computed both per-slice and over the whole package. Because the hash is content-
addressed rather than a version number or a timestamp, any change to any slice's bytes changes its hash, and
any change to the set or ordering of slices changes the whole-package hash. The Zig side can then recompute
the same hash over the package it actually read at its own build and compare, proving by construction that
the specialised runtime binary was built from exactly this package and no other.

`generate` is the entry point that produces both halves together: it compiles a `Signature`, plus the stage
slices that signature's checked compile produced, into a `Package` and its `Manifest`. This is the call the
dev-time language compiler makes once per language, at the language author's build, to hand off the finished
artifact to the runtime side.

The manifest is explicitly framed as an interim mechanism, not the final answer. The design's eventual goal
is a full lens-projection handoff, where the relationship between the compile-side proof and the runtime's
specialised state is expressed as a real structural projection rather than a hash comparison. That handoff is
still an open design question. The manifest is the cheaper thing to build and verify in the meantime: it does
not prove the same thing a full lens would prove, but it proves the one thing that matters most for safety
today, that the runtime is running what the compiler actually produced, and it does so with a mechanism this
crate can ship now.

## The differential check, and where it fits

Trusting a manifest match is not the only check the design leans on. `DifferentialCheck` is the contract for
a harness that runs the specialised runtime and a reference implementation over the same census corpus and
confirms they compute the same thing. This is described in the design as the grade-0 operational shadow of a
stronger, formally-stated relation between the two: where the assurance-indexed logical relation is the
strong statement of equivalence, the differential harness is the empirical check that approximates it over
real programs. The harness strengthens an existing seam rather than opening a new one; this crate owns the
contract the harness implements, not a new verification mechanism bolted alongside the manifest.

Together the two are what the crate offers as its assurance story today: the manifest proves identity, the
differential check approximates correctness, and neither claims to be the eventual full proof.

## The third build locus, and what stays out of this crate

The framework's build has three loci that matter for the runtime family: the dev-time compile of a program
against a language, the once-per-language compile of the language definition itself, and the Zig runtime's
own build, which specialises against the package this crate emits. That third locus is a real, separate build
step: `build.zig` reads the package and the manifest, runs the same content-validation kernel Rust used to
produce the manifest, and confirms the match before it finishes specialising. `vehje-runtime-gen` owns the
entire Rust side of that arrangement, the package format, the manifest, and the differential-check contract,
but it does not own the Zig side. The `build.zig` step that actually performs the comptime specialisation and
the content validation lives in the runtime's own repository-level tree, not as a Rust crate, because it runs
under a different compiler and a different build system entirely. No Rust crate is the third locus; this
crate is only its emitter and its binding contract.

This is also why the crate stays out of two adjacent concerns that might look like they belong here. The
per-script wire format belongs to `vehje-runtime-abi`, a different cadence (per script, at runtime) from this
crate's per-language, dev-time cadence, with its own trust story. The embedding of the Zig runtime into a Rust
host, dlopen and dispatch over the ABI, belongs to `vehje-runtime-driver`. Keeping the package-and-manifest
concern, the wire-format concern, and the embedding concern in three separate crates keeps each trust story
legible: a no-trusted-emitter package format, an untrusted-load wire surface, and a host-side embedding
contract are three different problems, and folding them into one crate would blur which guarantees apply
where.

# vehje-schedule: the compile-side pass DAG

Every consumer that plugs into the framework brings its own family: node kinds, effect classification, and a
set of semantic checks and certified IR-to-IR macro passes that only make sense for that family. Those passes
have to run in some order, some of them before a Core stage, some after, some interleaved. `vehje-schedule`
is the crate that computes that order. It is small on purpose: it owns exactly one problem, ordering a set of
registered passes by their declared dependencies, and it solves that problem once per compile, not once per
pass.

The crate sits entirely on the compile side. It has no runtime counterpart and no runtime dependency: it is
`#![no_std]`, no alloc, and its only external dependency beyond `vehje-ir` is `arvo-graph` for the topological
walk and `arvo-bitmask` for the adjacency storage. The schedule it produces is consumed once, at the start of
a compile, and then discarded. This document covers what the DAG actually orders, why its remit is narrower
than the name might suggest, and where the crate stops and hilavitkutin's runtime scheduling begins.

## What gets scheduled

A `Pass` is a registered compile pass: something that reads and writes the IR, with declared dependencies on
other passes. The framework's own Core stages (resolve, check) register as passes, and a consumer's family
passes register alongside them at the same point. What the DAG orders is the union of both: the Core stages
plus whatever family-specific checks and macro passes a consumer contributes, all placed into one dependency
graph and walked once.

`PassDag` is that graph. It is built from registration plus each pass's declared dependency edges, and the
adjacency is backed by an `arvo-bitmask` `BitMatrix` over a compile-time capacity, the same primitive
`arvo-graph`'s other DAG algorithms use elsewhere in the stack. There is no dynamic allocation involved in
building or holding the graph: the capacity is fixed at compile time and the matrix is a stack value.

`Schedule` is the result of walking that graph: a topological order over the registered passes. The walk
itself is `arvo-graph::topo_sort`, Kahn's algorithm over the `BitMatrix` adjacency. It runs once. There is no
incremental re-walk, no re-ordering mid-compile, no dynamic re-scheduling as passes run; the whole point of a
single-shot topological sort is that the order is decided before any pass executes and then followed exactly.

A cycle in the declared dependencies is not a separate error path bolted on afterward; it falls directly out
of what `topo_sort` already returns. The algorithm reports how many nodes it managed to place in the order
(`valid_count`) alongside the order itself. On an acyclic graph every node gets placed, so `valid_count`
equals the node count `N`. On a cyclic graph, the nodes caught in the cycle never reach an in-degree of zero,
so they never get placed, and `valid_count` comes back strictly less than `N`. `vehje-schedule` treats that
gap as the cycle signal: `valid_count < N` is `ScheduleError::Cycle`, and the crate's job is then to name the
passes the walk failed to place, so the diagnostic points at the actual passes in the cycle rather than just
reporting "a cycle exists somewhere."

The other diagnostic the crate reports is a missing dependency: a pass that names a dependency on a pass ID
that was never registered. This is checked at DAG construction, before any walk runs, because a dangling edge
is a different failure than a cycle and deserves a different message.

## Why the remit is narrower than it looks

An earlier shape of the compiler treated resolve and check as two stages in a pipeline that needed explicit
sequencing, with `vehje-schedule` as the thing that ordered them as peers alongside whatever else registered.
That shape does not hold anymore. The compile-and-verify side of the framework is one object now, not a
pipeline of independently-scheduled stages: resolution and checking are folded into a single engine frame,
and there is no longer a genuine ordering question between them for this crate to answer.

What is left, and what the crate now exists for, is the one part of that old job that is still a real
scheduling problem: ordering a consumer's family passes against the Core stages. That is the actual extension
mechanism. A consumer's family-specific check might need to run after resolve has produced its side-table but
before check discharges the effect proof; a certified macro pass might need to run before the family's own
checks so the checks see already-expanded IR. Those orderings are declared, not assumed, and `vehje-schedule`
is what turns the declarations into one linear order the compiler follows.

This narrowing is a deliberate, provisional shape rather than a permanent architectural line. If it turns out
that family passes are best understood as handler instances of the compile-stage effect discipline the engine
already runs, the ordering problem this crate solves folds into that discipline and the crate goes away. It
is kept for now because it exists, it is small, and removing it ahead of that unification would be betting on
a piece of design that has not been proven yet. A crate that earns its keep by doing one narrow job well is
cheaper to delete later than a wrong abstraction is to unwind.

## Why the runtime does not use this crate

The compile side does single-shot DAG walks: build the graph once from static registration, sort it once,
follow the order once, discard it. That shape fits a fixed, known-in-advance set of passes running once per
compile. It does not fit the runtime at all. The runtime executes a residual against a live environment,
frame after frame, with execution units that are dispatched, retried, and re-entered continuously rather than
walked once and thrown away. That is hilavitkutin's job: a morsel-driven scheduler built for exactly that
shape of repeated, windowed, cache-local dispatch over columnar data.

Reusing `vehje-schedule` for the runtime would mean pretending the runtime's execution units are a static,
one-shot DAG when they are not. The two problems, compile-time pass ordering and runtime frame execution,
are different enough in shape that sharing one scheduler between them would force one side to bend into the
other's assumptions. `vehje-schedule` stays a compile-side, single-shot pass scheduler; the runtime side owns
its own scheduling story through hilavitkutin, and the two never cross.

## What is not built yet

The `Pass` trait as it stands names a pass and its dependencies by identity; it does not yet carry the
per-pass read and write sets over the IR that would let the scheduler reason about data access rather than
just declared ordering. Those read/write sets are meant to be an `arvo-bitmask` access mask, the same
primitive family the DAG's own adjacency already uses, and they are what would eventually let the scheduler
prove an ordering is safe from the access pattern rather than trust the dependency declaration alone.

Correspondingly, `PassDag`'s adjacency construction and `Schedule`'s actual call into `arvo-graph::topo_sort`
are not wired yet. The types exist, the intended construction is documented at each site, and the surface is
stable enough for a consumer to register against, but the DAG is not yet built from real dependency edges and
the topological walk is not yet invoked. Both land together with the first consumer family pass, because
that is the point at which there is a real dependency graph to build and a real order to prove. Building the
wiring ahead of a consumer to exercise it would mean guessing at a shape nothing has tested yet; the narrowed
remit described above is itself the product of one such guess turning out wrong once already.

# The Graded Algebraic Signature

A vehje program and a vehje language are two different data contracts, and
the split between them is why `vehje-signature` exists as its own crate. A
program is nodes in an arena: the Core forms, the families reached through
`Raw`, and the per-program grade annotations, all of which `vehje-ir` owns.
A language is the operation catalogue with its grades and disciplines: which
family operations exist, what each invokes, how each treats its operands,
and what the declared targets accept. That catalogue is a `Signature`.
Because the shape of one program never depends on the shape of the language
it is written in (a `Node` is a `Node` regardless of which families a
signature declares), every per-program pass depends on `vehje-ir` alone, and
only the language-build path depends on the signature. Keeping the two apart
keeps the one crate everything depends on free of language-definition churn.

The signature is a graded algebraic-effect theory. Its operations are the
language's family operations, each carrying a declared effect grade and a
per-operand coeffect discipline, and the aggregate also carries the schemas
the check and generation stages read: the lease-rule schema, the declared
target set, and the input-side grammar attachment. It holds data, not a
compiler. The compilation over it (emitting an interpreter arm, a
value-kind, and a stencil per operation, folding the inclusion check against
each target) belongs to `vehje-runtime-gen`, and the grade computation that
reads it belongs to the check pass. This document describes what the
signature declares, how the lease-rule schema encodes the link-or-consume
interaction as a function of an operand's effect, and where the signature
sits in the graded proof spine that `vehje-typecheck` implements.

The graded framing is load-bearing but narrow in what it asserts about the
shipped code. The effect axis is a graded monad in the sense of Katsumata's
parametric effect monads: an operation's effect grade is an element of an
ordered algebra, effect sets join by inclusion, and a coercion up the order
is always sound. The lease axis is a coeffect in the sense of Petricek,
Orchard, and Mycroft: a per-operand usage grade, not a per-operation
property of the conclusion, which is exactly the resolution a per-operation
effect flag loses across an operation with several operands. The signature
is where the per-family data those two axes consume is written down; what
ships in this crate is that data and the lookup over it. The soundness
argument that ties the axes together (one theorem, with staging soundness,
the gradual guarantee, and region soundness as corollaries, and the axis
interactions as its typing rules) lives in the check pass and its
proof-document target, not here. The signature does not prove anything; it
supplies the per-family axiom table the proof quantifies over.

## The operation catalogue

An `Operation` is one family operation in the algebraic-effect theory. It
names its `FamilyId`, its declared effect grade (an `EffectMask` of the
operations it invokes), and its per-operand coeffect discipline (a
`LeaseRule`). The `Signature` holds these as a caller-provided slice, one
entry per family operation, alongside the declared targets and the grammar
hook. The catalogue is built once per language, read by the check pass, and
composed by `vehje-runtime-gen`; it is borrowed, not owned, so the crate
stays `#![no_std]` with no allocation.

Reading the operations as an algebraic-effect theory rather than a flat
opcode table is what lets the effect set, the host-call boundary, and macro
expansion be three instances of one handler discipline rather than three
mechanisms. An effect is an operation; a handler services it; the inclusion
check restates coverage as the unhandled operations of a residual being
included in a target's permitted set. The effect grade on each operation is
the declared approximation of what that operation invokes, decided rather
than inferred probabilistically, and it is the input the check pass's
bottom-up effect inference reads at each `Raw` node.

## The lease-rule schema

`LeaseRule` is the per-family schema the check pass reads to compute the
reachability coeffect. Its single field, `consumes`, is an `EffectMask`
naming the effect operations under which an operand is consumed rather than
linked. From it the check pass derives the link-or-consume bit for each
operand: an operand is consumed when its declared effect meets the family's
consuming set, and linked otherwise.

This makes the bit a monotone function of the operand's declared effect.
Effect masks are thermometer-shaped, so their join is a bitwise OR and
inclusion is a subset test; enlarging an operand's effect can only move it
from link to consume, never back, because the consuming set is fixed. The
anchor for deriving the lease bit from the effect at all is that region
systems and effect systems are one system (Talpin and Jouvelot): retention
through a host boundary is itself an effect, so the link-or-consume
obligation is not an independent declaration but a consequence of the
operand's effect. Where the effect is precise, the rule is a lookup in the
effect table; where it is coarse, the reachability grade refines it. This is
the effect-coeffect interaction as graded def-use, not as a distributive
law, and it collapses the single most realistic unsoundness vector into the
already-tested effect table.

`Signature::lease_rule` performs the lookup: it scans the operation
catalogue for the given family and returns that operation's `LeaseRule`, or
the default link-all rule when the family is not in the catalogue. The
default is the conservative floor. A family with no declared consuming
effects links all of its operands, which is the degenerate immutable
strictly-nested case the lease axis ships first, before the grade lattice
grows into the mutable, aliased, and escaping cases.

## Target declarations

A `TargetDecl` is the language-level record of what one declared target
accepts: the `Supports` family set it handles and the `Permits` effect set
it permits. The inclusion check is folded from these. A residual is
admissible on a target when the residual's family set is contained in the
target's supported set and the residual's effect set is contained in the
target's permitted set, the family-inclusion and effect-inclusion checks the
codegen path runs before lowering. The declaration is data borrowed from the
caller's catalogue; the actual `Target` carrier a lowering backend
implements extends the `TargetSets` trait in `vehje-ir`, so the check pass
can derive a target's sets from the target itself without a dependency
cycle, while the signature carries the language-level record used to build
the language.

## The three projections

The node algebra has three views of the same operations, kept consistent by
construction rather than as three parallel sets. `Projection` names which
view a consumer wants, and `vehje-runtime-gen` reads all three to emit the
per-operation output. The eliminator projection is the IR a pass folds, the
`vehje-ir` `Node` forms. The introduction projection is the produced-value
domain: a family that adds a constructor gets its value-kind from the same
operation, so the value domain is not a separately maintained schema. The
introduction-compiled projection is the copy-and-patch stencil set, a
deferred producer whose schema slot exists from the start so that adding it
later does not reshape the signature. Because the three are projections of
one operation set, an operation cannot appear in the eliminator view and
silently go missing from the value view; the single catalogue is the source
all three descend from.

## The attribute-grammar seam

`GrammarHook` is the attachment point for an opt-in grammar-as-data
front-end. The framework mandates only that a front-end produce well-formed
IR; it does not mandate that the front-end be declarative. A consumer that
writes its own parser leaves the hook at `HandWritten`, the default and the
absent case. A consumer that provides a declarative grammar sets
`AttributeGrammar`, and the signature then carries the attribute-grammar
schema the general parser interprets, with the synthesised attributes an
L-attributed evaluation computes standing as the initial grades handed to
the check pass.

At present the hook is a presence flag only. The schema shape is deferred
until the first grammar-as-data consumer, because it should be shaped by a
real grammar rather than guessed at, and a hand-written front-end needs
nothing beyond the absent variant. The slot is reserved rather than filled,
which keeps the deferral honest: the seam is named and typed, and the schema
lands with the consumer that first needs it.

## Where the signature sits in the graded spine

The check pass in `vehje-typecheck` treats a term's typing as one judgment
whose context carries a per-binder coeffect grade and whose conclusion
carries an effect grade, a binding-time grade, and a per-property assurance
grade. The signature is the per-language data three of those coordinates
read: the effect grade on each operation is the graded monad's per-operation
element, the lease-rule schema is the coeffect's per-family axiom the
reachability inference consults, and the target declarations are the
inclusion order the effect grade is checked against.

The signature is a compile-side artifact read to build a language; nothing
in it survives into a residual. That is why it can ship as concrete data now
while the full logical relation remains a separate proof target: the
shippable core is the operation catalogue, the effect masks, the lease-rule
lookup, and the inclusion checks, and the metatheory certifies them without
the runtime carrying any of it. The signature is the input the one soundness
argument quantifies over, not a second copy of the proof.

# Deepdive: the graded proof spine

The three static proof axes plus assurance are one graded (co)modal judgment,
unified by construction rather than by analogy. This deepdive states the
judgment, why the axes compose, what lives in the proof versus in the runtime
types, and the proof-document target. It is the theory the check pass
implements; the pass ships the concrete runtime shadow of it, and the full
metatheory is a bounded writing task drafted alongside.

## One judgment, four coordinates

A term's typing is one judgment whose context carries a per-binder coeffect
grade and whose conclusion carries an effect grade, a modal grade, and, per
property, an assurance grade.

- Binding time is a graded necessity modality over the knowledge-source
  join-semilattice. The sources are the language author, the bundler, the
  host-loader, and the runtime, joined rather than chained, so a template known
  at build with data arriving at the host is a join, not a special case. The
  modal grade is when a value's inputs are known.
- Effect is a graded monad, the operations a construct invokes, which after the
  handler unification is graded algebraic effects: an effect is an operation, a
  handler services it, and inclusion-not-coverage is restated as the unhandled
  operations being included in a target's permitted set.
- Lease and usage is a coeffect (per-operand, not per-op), whose grade is a
  reachability qualifier. Making the lease a coeffect rather than an effect is
  the one place grading changes a design decision: it recovers the per-operand
  precision an effect-only filing loses. The reachability-lease deepdive covers
  this axis in full.
- Assurance is itself a grade, and the novel move at the spine is that it is not
  an independent axis but a projection of the modal grade crossed with the
  property. A property whose inputs are all early-bound discharges statically
  (high assurance, folded to a compile error); a property whose inputs arrive
  late is a bounded dynamic residual (low assurance). So "discharge each property
  at the earliest binding time its inputs are known" becomes a computation of the
  assurance grade from the knowledge-source lattice, and the guarantee inventory
  is a computed grade vector rather than a hand-curated list.

Effects and coeffects combine by the graded adjunction, which is demonstrated
implementable in the literature. There is one soundness theorem, with the
per-axis results (staging soundness, the gradual guarantee, region soundness) as
corollaries and the axis interactions (what happens when effect, coeffect, and
binding time meet on `Apply`) as its typing rules rather than unwritten case
analyses.

## In the proof, not in the runtime types

The scoping discipline is load-bearing: the grades live in the proof and in this
design's coherence argument, never in the runtime types. At the machine level
the axes are concrete closed enums and fixed-capacity bitmasks (about two enums
and two bitmasks), and the entire graded apparatus is compile-side and compiled
away. The runtime inherits proven-safe programs on every axis and re-runs
nothing except the genuinely-unknowable-until-load structural rejection of
malformed input and the numeric and lease dynamic residuals. This is why the
check pass can ship the concrete grade computation now while the full logical
relation remains a proof-document artifact: the shippable core is the grade
enums, the bitmask joins, and the inclusion checks, and the metatheory certifies
them without the runtime carrying any of it.

## The proof-document target

The proof document is `lambda_veh`: a two-level core over the twelve forms with
a region store indexed by a live-depth stack. Its theorems are T1 (staging
soundness), T2 (the gradual guarantee per axis), and T3 (region soundness,
restricted to the LIFO chain), plus the crux immutability lemma, the cross-chunk
lemma (discharged by construction), and backward-link acyclicity as the
load-checker totality argument. The store typing and reachability-respects-lease
invariants are fixed; only the per-family axiom table is experiment-dependent, so
the document drafts in parallel with the experiments. The highest-value original
work is the assurance-indexed gradual logical relation parametric over the
generated signature: it holds as a proof where assurance is high and degrades to
its operational shadow, the differential test, where assurance is low, so proof
and test are one object at two grades. The differential test ships (as the
runtime-generation differential harness); the full relation is deferred.

# Deepdive: the reachability lease axis

The lease axis proves region validity without a collector. Reachability types are
the primary paradigm: a value's lease grade is the set of binders it can reach,
and the compiler proves that a value never outlives the binders it reaches, so
regions free on stack discipline. This deepdive states the coeffect, the bounds
that keep it no-alloc, the sharing discipline, and the avoidance boundary where a
static proof gives way to a per-reference dynamic residual.

## The lease is a coeffect, and reachability supplies its grade

The arc arrived independently at "the lease is a coeffect" (per-operand usage,
not per-op world-change), and reachability types are a coeffect, so they are the
same structure approached from two directions. The lease coeffect's grade is a
reachability qualifier realised as a fixed-capacity bitmask over in-scope
binders, the same shape and inclusion primitive as the family and effect axes.
Three axes, one bitmask machinery, one inclusion check. The immutable
strictly-nested depth-lease (the qualifier collapsed to lexical nesting) is the
degenerate case and the risk valve: it ships first on the proven-cheap
metatheorem, and the grade lattice grows into the full qualifier additively,
unlocking the mutable, aliased, and escaping cases. The mutable-consumer
extension is the bet, over a proven floor, gated on the avoidance-rate
experiment.

## The two bounds that keep it no-alloc

A reachability qualifier is richer than a scalar depth, so both the naming set
and the escape set need bounds or the inference is not no-alloc.

The naming set (the in-scope binders a node reaches, width at most the per-scope
binder width) is bounded by the reachability-type binder rule, not by a bare
in-scope filter. At `Let` and `Lambda`, the reach set is not the naive union of
the children's reach sets; it is the body's reach set with the bound variable
eliminated by substitution, where the body reaches the variable spliced in the
bound expression's reach set, then the variable dropped. This is the avoidance
operation from reachability types. A filter that drops the variable without
splicing under-approximates and is unsound the other way (a value reaching
through the bound variable into a still-live outer binder would lose that reach
and be judged safe when it is not), which is why the sound rule fires at the
binder node and plain child-propagation plus the in-scope filter carries the
already-scoped set upward.

The escape set (the out-of-scope binders a value reaches) is bounded by region
promotion: the live-region count is bounded by the program's let-and-region
structure. Sharing uses Perceus exact-meet, not shared-implies-promoted (an
ML-Kit-style leak) and not copy-everything (exponential): a shared node gets the
exact meet of its referrers' reach-sets by a reversed referrer count finalised at
emission, which is reference counting as compile-time finalisation, and the same
information licenses in-place reuse.

## The effect-coeffect interaction, and where it gets its numbers

The effect-coeffect interaction is graded def-use, not a distributive law.
Retention through a host boundary is itself an effect, so the link-or-consume bit
is a monotone function of the operand's declared effect, read from the
`vehje-signature` lease-rule schema. This collapses the single most realistic
unsoundness vector into the already-tested effect table: where the effect is
precise, the link bit is a lookup; where it is coarse, the reachability grade
refines it. The measured cost is the same bottom-up bitmask join as effect
inference, differing only in payload.

## The avoidance boundary and the generational residual

Reachability inference is compile-side and erased into certified region structure,
so the runtime inherits proven-valid references with no collector and no
refcount. At the avoidance boundary, where a value escapes and its type cannot be
expressed without the escaped binder, the property's assurance grade drops and a
per-reference generational-reference check is the dynamic residual for exactly
that un-placeable reference, not a whole-value collapse. Avoidance succeeds gives
a static proof (high grade); avoidance fails gives the generational check (low
grade). This is the graded-assurance dial made concrete on the lease axis: the
residual has a home rather than being a parallel fallback. The closure-escape
case that `Lambda` makes first-class is the hardest case the forms surface, and
it is exactly what reachability types were built for. Absence, throughout, is an
explicit `Maybe` value, never a nullable reference.

The region-leak history is the cautionary tale banked: pure region inference
leaks (ML Kit needed a collector back, Cyclone shipped a hybrid). vehje's
position holds the immutable core pure-static and makes the mutable and escaping
fallback a reachability-type and generational-reference discipline, never a
collector. A CHERI output target is an optional hardware assurance grade for the
lease axis, additive rather than core.
