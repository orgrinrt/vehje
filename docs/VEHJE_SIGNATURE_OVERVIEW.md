# vehje-signature. Design

The language-level definition. Where `vehje-ir` is the per-program data
contract (nodes in an arena, families reached through `Raw`, per-program grade
annotations), `vehje-signature` is the per-language data contract: the full
operation catalogue with its grades and disciplines, from which the language's
runtime is generated. It holds data, not a compiler; the compilation over it is
`vehje-runtime-gen`'s. Every per-program pass depends on `vehje-ir`; only the
language-build path depends on the signature, so keeping it separate keeps the
one crate everything depends on free of language-definition churn.

## The graded algebraic signature

A `Signature` is the one source a language descends from: an algebraic-effect
theory whose operations are the language's families, plus the schemas the check
and generation stages read.

- `Signature`. The aggregate: the family catalogue, the effect operation set,
  the lease-rule schema, the binding-time defaults, and the declared target
  set. Built once per language at dev time, read by `vehje-check` and composed
  by `vehje-runtime-gen`.
- `Operation`. One family operation: its `FamilyId`, its declared effect grade
  (which operations it invokes), and its per-operand coeffect discipline (which
  operands it links versus consumes, the lease rule). The operations are the
  algebraic-effect theory the handler discipline services.
- `LeaseRule`. The per-family lease-rule schema `vehje-check` reads to compute
  the reachability coeffect: for each family operation, the monotone function
  from an operand's declared effect to its link-or-consume bit. Retention
  through a host boundary is itself an effect, so the rule reduces to a lookup
  in the effect table where the effect is precise and the reachability grade
  refines it where the effect is coarse.
- `TargetDecl`. A declared target's `Supports` family set and `Permits` effect
  set, the language-level record of what the target accepts, from which the
  inclusion check is folded.

## The three projections

The node algebra has three views of the same operations, kept consistent by
construction rather than as parallel sets:

- The eliminator projection is the IR a pass folds (the `vehje-ir` `Node`
  forms).
- The introduction projection is the produced-value domain: a family that adds
  a constructor gets its value-kind for free (content-as-values), so the value
  domain is not a deferred separate schema.
- The introduction-compiled projection is the copy-and-patch stencil set (a
  deferred producer; the schema slot exists day one).

`Projection` names which view a consumer wants; `vehje-runtime-gen` reads all
three to emit the interpreter arm, the value-kind, and the stencil for each
operation.

## The attribute-grammar attachment

`GrammarHook` is the attachment point for an opt-in grammar-as-data front-end:
where a consumer provides a declarative grammar, the signature carries the
attribute-grammar schema the general parser interprets, and the synthesised
attributes an L-attributed evaluation computes are the initial grades. This is
opt-in per D1; the framework mandates only that a grammar produces well-formed
IR, so a hand-written front-end leaves this attachment empty.

## Non-scope

- The per-program IR (`vehje-ir`).
- The compilation of the signature into a runtime package (`vehje-runtime-gen`).
- Any consumer's concrete families, grammar, or targets; the signature holds
  the schema shape, a consumer fills it.

## Dependencies

`vehje-ir` for the `FamilyId`, the grade types, and the `Family` trait;
`hilavitkutin-api` for the `AccessSet` sets; `notko` for `Maybe` and `Outcome`.
