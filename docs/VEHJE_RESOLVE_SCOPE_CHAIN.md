# vehje-resolve. Scope Chain Deep Dive

`vehje-resolve` answers one question for every `Var` node in a program:
which binder introduced it. The answer comes from a scope chain, and the
chain's shape is the whole design decision this document covers. A scope
frame in this crate is not an entry in an owned table that the walk builds
up and tears down; it is a value that lives on the resolve walk's own call
stack for exactly as long as the binder it represents is in scope, and it
reaches its enclosing scope by a plain reference rather than an index into
storage. No scope table is ever allocated, because the call stack already
is one.

This matters because `vehje-resolve` runs on every `Var` reference in every
program the framework compiles, and it runs before the check and lowering
passes, both of which depend on its output. A resolve pass that allocated a
scope table per call, or grew an owned vector of frames as it descended
into nested binders, would pay that cost on the framework's hottest
compile-time path. The borrowed chain avoids the cost entirely rather than
amortizing it, and the difference is measured, not assumed: resolving one
reference against the chain costs about 0.91 nanoseconds, several times
faster than walking an equivalent owned scope table. This document explains
the chain's shape, the recursive-binding rule that governs `Let`, the
`Resolution` side-table the later passes read, and where a consumer
family's own binding forms hook into the walk.

## The borrowed, non-allocating scope chain

`Scope<'p>` is a single binding frame: the name it binds, the `NodeRef` of
the node that introduced the binding, and a reference to its parent frame,
or nothing at the root. A chain of these is a stack of frames threaded by
reference, and each frame's lifetime is tied to the recursive call that
created it. `walk` (the core recursive descent over the arena) takes its
current scope as `Maybe<&Scope<'_>>`, a borrowed pointer rather than an
owned value, and every place the walk descends into a binder's body it
constructs a new local `Scope` on its own stack frame and passes a
reference to it down into the recursive call. When that call returns, the
frame's storage is simply the stack frame unwinding; there is nothing to
free because nothing was allocated in the first place.

`Scope::resolve` walks the chain outward from the innermost frame, checking
each frame's name against the target and following `parent` on a miss until
it either finds a match or runs out of chain. Because the chain is exactly
as deep as the current binder nesting, and no deeper, the walk's cost is
proportional to how far out the matching binder actually sits, the same
complexity an owned table lookup by scan would have, but without ever
materializing the table. The `frame_for` helper is the one place a new
frame gets constructed, called at each `Let` and `Lambda` site with the
current scope as parent, so a root frame (`Scope::root`) and a chained
frame (`Scope::child`) share one construction path from the walk's point of
view.

## Why this beats a scope-chain walk over an owned table

An owned scope table, a vector or map of active bindings that the walk
pushes onto entering a binder and pops on leaving it, is the obvious
alternative, and it works. The cost it pays that the borrowed chain does
not is bookkeeping: every push is a write into growable or pre-sized
storage, every pop is an explicit removal, and the table itself is a
resource the walk owns and must maintain correctly across every recursive
path, including early returns on a resolve error. The borrowed chain has
none of this to get wrong, because the "table" is just the sequence of
stack frames the recursion already creates and destroys as a side effect of
being a recursive function. The measured gap between the two shapes is not
marginal: the borrowed chain resolves a reference in about 0.91 nanoseconds
against several nanoseconds for the owned-table walk, a factor of roughly
six to fourteen times depending on chain depth and table shape, because the
borrowed chain has zero write-side cost and the owned table always has
some.

The same shape generalizes past name resolution. A flat, borrowed,
reference-chained frame is the right answer whenever a pass needs
scoped, LIFO-lifetime state during a tree walk and does not need that
state to outlive the walk or be queried from outside it. `vehje-resolve`
is the first crate to need this shape and the reference implementation
other Core-level passes reach for when they need the same pattern.

## The recursive-`Let` rule

A `Let { rec, name, value, body }` node's `rec` flag decides whether the
bound name is visible while resolving its own `value`. When `rec` is set, a
`let rec f = ... f ... in ...` construct can have its value reference `f`
itself, which is what makes recursive definitions resolvable at all: the
walk builds the frame for `name` before descending into `value`, so `value`
sees its own binder in scope. When `rec` is not set, the walk resolves
`value` against the scope that existed before the `Let`, so a `let f = f in
...` where the right-hand `f` is meant to reference an outer binding (or
nothing, if there is no outer binding) does not see the new frame; only
`body` does. The rule is one branch in `walk` and its recording twin
`walk_record` (`let value_scope = if rec.0 { Maybe::Is(&frame) } else {
scope };`), applied identically in both, and it is the entire mechanism
behind the difference between a self-referential binding resolving and an
accidentally-shadowed one failing to resolve. The test suite pins both
directions: a `rec` binding whose value references itself resolves, and
the same shape with `rec` unset does not, because without the flag the
right-hand `f` has nothing bound yet to resolve against.

## The `Resolution` side-table

`resolve` answers only whether a program's names all resolve; it produces
no record of which `Var` resolved to which binder. `resolve_into` is the
same walk over a variant, `walk_record`, that additionally writes into a
`Resolution<'a>`, a side-table wrapping a caller-provided
`&'a mut [Maybe<NodeRef>]` region sized like the node arena, exactly the
same parallel-region discipline the span and grade tables in `vehje-ir`
use. Every entry starts unresolved; each time `walk_record` resolves a
`Var`, it records the binder's `NodeRef` at the `Var`'s own arena index
through `Resolution::record`. The check and lowering passes read this
table by index (`Resolution::binder`) rather than re-walking the scope
chain themselves, so the resolve pass's work is paid exactly once per
program regardless of how many later passes need to know a variable's
binder. This is the same reasoning that puts `GradeTable` and the span
table in `vehje-ir` itself: a fact computed once about a `NodeRef` belongs
in a side-table keyed by that ref, not recomputed by every consumer.

## The family-extension resolve seam

`Raw` nodes, the escape hatch through which a consumer family's own
constructs attach to the Core arena, are opaque to both `walk` and
`walk_record` today: a family node introduces no Core-level scope frame and
is treated as a leaf for resolution purposes. This is a placeholder for a
real extension seam, not the finished design. A consumer family may define
its own binding forms (a pattern-matching construct with its own bound
names, a comprehension with a loop variable, anything the Core's `Let`,
`Lambda`, `Iter`, and `Handle` binders do not already cover), and those
forms need to extend the scope chain the same way Core's own binders do,
without the Core resolve pass needing to know the family's node kinds in
advance. The mechanism composes with the family-set typestate the rest of
the framework already uses: a family declares a resolve hook, the walk
dispatches to it when it encounters that family's `Raw` payload, and the
hook gets the current `Scope` chain to extend and hands back into the Core
walk for the sub-expressions it does not own itself. Until a real consumer
family exists to exercise the shape, the seam stays a documented gap rather
than a speculative interface, so the first extension is designed against an
actual need rather than a guess.
