# vehje-resolve. Design

The framework's Core-level resolve pass. Name resolution over the shared
Core binders (`Let`, `Lambda`, `Iter`, `Handle`, `Var`), generic over the
family set, with family-extension hooks for family-specific resolution. This
is a framework-owned Core pass, not a consumer pass: the shared IR is only
real, not nominal, when the passes are shared. `#![no_std]`, no alloc.

## Scope

- The resolve walk over Core binders, producing a resolution from each
 `Var` to the binder that introduced it. The binder forms are `Let` and
 `Lambda`, `Iter`'s loop variable, and `Handle`'s operation and resumption
 binders. A `Let` with `rec` set binds its name in scope for the bound value
 (a recursive binding, so the value can reference itself); a non-recursive
 `Let` does not. The rule holds in both `resolve` and `resolve_into`.
- `Scope`. A borrowed, non-allocating scope frame: each frame lives on the
 walk's own stack and chains to its parent by reference, so no owned scope
 table is allocated (measured at 0.91 ns per reference, well ahead of a
 scope-chain walk over an owned table). This is the flat shadow-stack shape.
- `Resolution`. The resolution side-table the walk produces, mapping each
 resolved `Var` handle to its binder handle, read by the check and lower
 passes so they do not re-resolve.
- Family-extension hooks: a family's own binding forms extend the walk
 without the Core pass knowing them, composing with the family set the way
 the typestate axes do. The walk descends into a `Raw` node's payload,
 resolving its child handles exactly as an `Apply`'s arguments (a `Var` inside
 a family node is a real reference and is resolved), rather than treating `Raw`
 as a leaf.
- `FamilyResolve`. The family-extension hook trait a consumer implements to add
 family-specific resolution (a family binding form) at a `Raw` node. Its method
 defaults to a no-op, because the base walk already descends into and resolves
 the payload's Core children. `resolve` and `resolve_into` are the Core-only
 entries (they use the default hook); `resolve_with` and `resolve_into_with`
 take a consumer hook. `CoreFamilies` is the no-op default the Core-only entries
 use.
- `ResolveError`. Resolve diagnostics (unresolved name, duplicate binding).

## Non-scope

- Surface-syntax resolution (use-trees, module paths, visibility). Those
 vary with a consumer's grammar and live in the consumer, not the shared
 Core pass.
- Type checking (`vehje-check`).
- Manifest and crate-graph parsing. That was the first-party language's
 concern; it moves to that consumer.

## Dependencies

- `vehje-ir` for the Core nodes and binders.
- `hilavitkutin-str` for interned name identity.
- `hilavitkutin-api` for the family-set typestate the extension hooks
 compose over.
- `notko` for `Maybe` / `Outcome`.
- `#![no_std]`, no alloc.
