# vehje. Architecture Design

> The embeddable, multi-input, multi-output IR framework. A grammar plugs
> in on the input side and lowers its surface syntax into a shared IR; a
> target plugs in on the output side, declares what it supports, and emits.
> vehje owns the shared substrate and the two contracts, not any one
> language. The rich general-purpose scripting language is one first-party
> consumer of the framework, named later.

## What vehje is

vehje is a framework, not a language. Its surface is a shared IR
representation, the machinery to lower into it and fold out of it, an
embeddable runtime, and the two contracts by which a grammar plugs into the
input side and a target plugs into the output side. It ships no first-party
surface syntax as part of the core.

The design authority for the framework is the extension-point design round
(topics `202607190650` through `202607192340` under `design_rounds/`), which
settled the identity, the input and output contracts, the exhaustiveness
mechanism, the effect model, the crate surface, the Core forms, and the C
ABI. Those topics are the oracle; this document is their shipping-contract
summary.

## The two contracts

A grammar owes the framework well-formed IR: it lowers its surface syntax
into the shared Core forms plus its own family node kinds. The framework owns
no front-end and mandates none; it offers opt-in front-end scaffolding, which
a consumer may reuse or replace with its own lexer and parser.

A target declares what it supports, and everything else is a proof obligation
against that declaration. A target names a type-level `Supports` set of the
families it handles and a `Permits` set of the effects it allows; emission is
bounded on the program's families being included in `Supports` and the
program's effects in `Permits`. The guarantee is inclusion, not coverage: a
program using a family or effect outside a target's declaration is refused,
with the construct named, never silently degraded. The machinery is
`hilavitkutin-api`'s `AccessSet` typestate, reused with vehje's own family and
effect marker types.

## Two sides: Rust compile side, Zig runtime side

The framework has a Rust compile side and a Zig runtime side, joined by a C
ABI defined and validated in Rust.

The compile side lowers a program to a `Checked` residual: it lexes and parses
through the consumer's grammar, lowers to IR, resolves and checks over the
shared Core and families, runs the family and effect inclusion checks, and
reduces every build-environment effect away. Constant evaluation and macro
expansion happen here, because they are build-environment reductions by
nature. The output is a residual proven to carry only runtime-executable
effects. It ships as a single static binary per target platform.

The runtime side executes the residual against the runtime environment. The
residual crosses the C ABI in a tier-tagged representation: a flat serialized
IR arena as the baseline (the reference semantics), an optimized bytecode as a
faster tier, and native machine code (through an LLVM or cranelift backend) as
the ideal endgame, at which the Zig runtime collapses to environment plumbing
around native code, the way a Rust binary's runtime is thin plumbing around
LLVM output. The tier is an optimization axis orthogonal to correctness: the
effect proof is discharged in Rust before any lowering, so choosing a tier
changes execution speed, never semantics. The runtime pulls no `std` and no
Rust runtime.

## The compile-time / runtime split

The split follows the effect axis, not a separate decision. Everything
parametrized over the build environment is the compiler's; everything
parametrized over the runtime environment is the runtime's. The compiler is
the only thing that ever touches the registry, `self`-context, or build
resources; the runtime never implements build-environment semantics, because
the effect proof guarantees no build-environment construct survives into the
residual it receives.

## Foundations

- `arvo` (sibling repo). Numeric primitives plus analysis. `arvo-graph` backs
  the pass DAG, `arvo-bitmask` backs the runtime family/effect bitmask checks.
- `hilavitkutin` (sibling repo). `hilavitkutin-api` provides the `AccessSet`
  typestate the two axes reuse, and `hilavitkutin-str` provides the interner
  string type. The Zig runtime uses hilavitkutin's morsel-driven execution;
  the compiler does single-shot DAG walks and does not need the frame runtime.

Reuse arvo and hilavitkutin. Do not reimplement DAG topology, bitmask ops,
sparse storage, the set typestate, or pipeline scheduling.

## Framework crate surface

- `vehje-ir`. The shared representation: the Core substrate forms, the
  `Family` extension trait plus effect classification, the family-set and
  effect-set typestate, the node builder, interner integration.
- `vehje-codegen`. The output machinery: the one generic fold, the `Target`
  trait, the inclusion and effect checks, `Checked` gating, and compile-time
  target composition (no `dyn`).
- `vehje-schedule`. The pass DAG over `arvo-graph`.
- `vehje-resolve`. The Core-level resolve pass, generic over the family set,
  with family-extension hooks.
- `vehje-check`. The Core-level check pass, generic over the family set, with
  family-extension hooks.
- `vehje-runtime-abi`. The tier-tagged C ABI and the residual serialization.
- `vehje-runtime-driver`. Compiler-side dispatch over the ABI and the Zig
  runtime embedding.
- `vehje`. The two public contracts, orchestration, and the
  distribution-composition entry point, with a reference distribution.

Offered opt-in, not shipped now: generic front-end scaffolding. It is
extracted once a live consumer proves the shared shape, not designed from
zero consumers.

## Consumers (separate repos, not this repo)

Grammars and targets are consumers of the framework, each a separate repo
bringing a grammar (a front-end producing IR), a family (node kinds plus a
`Family` impl plus effect classification), any family-specific semantic
checks, and one or more targets (a `Target` impl declaring its `Supports` and
`Permits` plus its lowering). The known census: the first-party general-purpose
language (named later), `vehje-jomini` (Clausewitz across five Paradox
titles), `vehje-w3`, `vehje-ts4`, `vehje-lua`, the native target, polka,
ikiuni's scripting language, viola's lint-authoring language, and mockspace's
procedural-documents language.

## Not in this repo

- Any consumer's front-end, family, or targets. Those ship as consumer repos.
- Game-specific vocabulary, bind targets, or content.
- The first-party language's surface syntax. It is a consumer, named later; a
  Python prototype of it lives outside this repo as heritage for when that
  consumer is built, not as an oracle for the framework.
