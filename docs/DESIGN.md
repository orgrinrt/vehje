## Two-language strategy

**Rust compiler + Zig runtime, joined by C ABI defined / validated in Rust.**

- **Compiler** (Rust): lex, parse, resolve, typecheck, transpile, codegen, scheduler. Runs at dev time. Distribution: single static binary. `#![no_std]` where practical, custom allocations.
- **Runtime** (Zig): executes macros, scratch variables, generative pipeline. Small, fast, embeddable. Talks to the compiler via C ABIs the Rust side defines + tests for soundness.
- **Build tooling / deploy / playset orchestration**: dogfood in Clause itself (via the runtime), consuming the Rust compiler binary. rustc/cargo pattern — the compiler does one thing, the tooling runs on top of what we shipped.

## Substrate

- `arvo` (sibling repo) — numeric primitives + analysis (arvo-graph for pass DAG, arvo-bitmask for artifact read/write sets).
- `hilavitkutin` (sibling repo) — pipeline execution engine. Used by the Clause *runtime* (morsel-driven execution of macros / scratch / generative), less so by the compiler itself (one-shot DAG walks don't need the frame runtime).

## Extension pattern

Game-specific targets land as separate repos that extend Clause:

- `clause-jomini` — Clausewitz (Stellaris / CK3 / HOI4 / Vic3 / EU4) grammar, bind targets (Country, Pop, Planet, …), codegen to Clausewitz script.
- `clause-w3` (future) — Witcher 3 script target.
- `clause-ts4` (future) — Sims 4 script target.
- `clause-lua` (future) — generic Lua target.

The extension point contract is TBD (one of the first session's design rounds).
